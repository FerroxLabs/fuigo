# Fuigo 1.0.26 release notes

This release follows 1.0.25. It warns at every start when a sandbox profile is set on Windows, where Fuigo has no sandbox, and keeps running. A turn started by another session's message that ends without any action is now shown and recorded as refused. An HTTP MCP server can read its bearer token from a file. A refused managed policy now says why. You can choose a model's context window with `/context-window` and show a notice for a model, both from your own configuration. The shell tool's two background settings become one wait setting. The Windows executable gets a larger stack.

## Sandbox

- **Warning when a sandbox profile cannot run on Windows.** The sandbox exists on Linux and macOS only. On Windows, a configured profile other than `off` used to be ignored with only a log entry. Fuigo now prints `Sandbox profile <name> is set but sandboxing is not available on Windows: commands and file tools run unsandboxed.` on stderr at every start, including headless runs (`fuigo -p`) before the first model request and `fuigo wrap` before its command starts, shows it as a notice when a session starts (once in headless `plain` output), and adds a `Sandbox warning` line to the `/status` view. Fuigo still starts and runs. With profile `off` or no profile, nothing changes, and nothing changes on Linux or macOS. The user guide's sandbox chapter now also states that on macOS the child-process network restriction is not applied, and that on Linux and macOS every profile except `off` and `devbox` refuses to start when it cannot be applied.

## Windows

- The main thread of the Windows executable now has an 8 MiB stack (it was the 1 MiB system default). A debug build of the pager overflowed the smaller stack at startup; the release build did not.

## Named sessions

These notes apply only when `features.peer_messaging` is on (it is off by default).
- **A turn started by a message from another session that ends without a reply is now shown and recorded as refused.** If the model ends such a turn with an empty reply, you see one notice in the transcript: "The model ended the turn started by a message from <name> [<ref>] without a reply." If the model provider stops the reply with a refusal, the notice reads "The model declined to act on the message from <name> [<ref>]." The name and reference are the sender's own claim, shown escaped. A turn you typed yourself is unchanged.
- **A turn started by a message from another session that makes no tool call is recorded as refused automatically.** This covers an empty reply, a provider refusal and a reply that has only text (the text is still shown as the model's reply). It is recorded as refused for that message only, with the reason "no action taken": the sender gets the same refused notice, a "notify when idle" request on the message is settled the same way, and the audit line says the refusal was automatic. A turn in which the model used any tool, or called `refuse_peer_message` itself, is not refused a second time. Unlike a refusal the model makes with `refuse_peer_message`, an automatic refusal applies to that message only: later messages from that sender are not held because of it (the sender name in a message is only a claim, and a forged message must not silence the real session).

## Tools and MCP

### One wait setting for shell commands
The shell tool now takes a single setting, `block_until_ms`, that says how long the call waits for the command. A command that finishes within the wait returns its output inline. What happens to a command still running when a positive wait ends is exactly what already happened when a foreground timeout ended, and follows your `toolset.bash.auto_background_on_timeout` setting: if it is on, the command keeps running in the background and the call returns a task id; if it is off, the command is stopped and the result says it was stopped after the wait and that `block_until_ms: 0` runs it in the background. A positive wait does not extend how long a command may live, and cancelling the turn ends it as before.
- Default wait: the foreground timeout a call without arguments always had (120 s, or `toolset.bash.timeout_secs`). The maximum is 300000 ms unless you lower it with `toolset.bash.foreground_block_budget_ms`; a larger request is lowered to the maximum, `0` is never changed. A call with neither `block_until_ms` nor the old fields behaves exactly as before.
- `block_until_ms: 0` starts a background task at once, with the same limits and the same refusal when background commands are disabled as before. It replaces `is_background: true` (the model-facing name was `background`).
- New setting `toolset.bash.default_block_until_ms` changes the default wait.
- The `timeout` argument is no longer offered to the model while background commands are enabled; its job is done by `block_until_ms`. With background commands disabled, nothing changes.
- Permission prompts, deny rules, plan mode, sandboxing and every other check are unchanged. Only how the agent asks changed.
For hook authors: the `tool_input` your `PreToolUse`, `PostToolUse` and `PostToolUseFailure` hooks receive for a shell command carries two computed fields, whatever the model sent. `is_background` is `true` exactly when the call runs as a background task (`block_until_ms: 0`, or the old `is_background: true` when there is no `block_until_ms`); a model that sends `block_until_ms: 0` together with `is_background: false` reaches your hook as `true`, so a hook that blocks background commands still blocks them. `may_background_after_wait` is `true` for a call that waits (a positive `block_until_ms`, or none) when your `auto_background_on_timeout` setting is on, meaning the command moves to the background if it outlives the wait; with the setting off it is `false`. Both fields are computed by the same rule the shell tool runs by. `is_background` will be removed in a later release; read `block_until_ms` in new scripts.
For ACP hosts: a tool call's `rawInput` for a shell command uses `block_until_ms`. A background command is one with `block_until_ms: 0`. Fuigo still accepts `is_background` and `background` on input, from a client or from a resumed session, and treats `is_background: true` as `block_until_ms: 0`; if both are present, `block_until_ms` wins. Hosts that detect background commands from `rawInput` should check `block_until_ms == 0` first and fall back to the old boolean.
The tool definition the model sees changed, so a new session starts with a cold prompt cache.

### A bearer token file for an HTTP MCP server
- **An HTTP MCP server can read its bearer token from a file.** Set `bearer_token_file` on an entry in your own `config.toml` to a file that holds the token; Fuigo reads it again for every request, so a token that another program rotates on disk applies without a reconnect. It is sent only as `Authorization: Bearer <token>` to that server's own URL, over `https` (or plain `http` to this machine). The file must be a regular file you own, with no group or other permissions (mode 0600 or 0400), no larger than 16 KiB, and not a symbolic link; the path must be absolute or start with `~/`. The setting is ignored, with a visible warning, in a project config, a project `.mcp.json`, a plugin, a managed or remote config, and a definition handed over by an editor. The setting is also dropped for a server whose entry a managed, requirements or campaign layer changes (a different `url`, `headers` or auth), and campaigns can no longer set or change any MCP server's `url`, `headers`, `bearer_token_file` or `bearer_token_env_var`. `$VAR` in the path is not expanded, and a token shorter than 16 characters is refused ("token too short"). A server that also sets `bearer_token_env_var` or an `Authorization` header, or whose file fails a check, is skipped with a one-line warning naming the server and the reason; other servers start normally. The token is never logged or shown. On Windows the setting is not supported in this release and the server that sets it is skipped.

## Managed policy

- **The refusal names why a managed policy was rejected.** When Fuigo refuses to start because the managed policy could not be trusted, the message now ends with one fixed sentence naming the category: `Reason: signed managed policy is invalid.`, `Reason: managed policy signature is missing.`, `Reason: managed policy file is missing.` or `Reason: managed deployment key changed.` The sentence appears in the terminal, in a headless run on stderr and to an ACP host. It contains no file content, path, signature or claim value. What is refused does not change.

## Models

- **Choosing a context window.** A model entry can list several context windows with `context_windows = [100000, 400000]` under `[model.<id>]` (or under `[model_providers.<id>]`, inherited by models that set neither `context_window` nor `context_windows`). `/context-window` shows the choices for the current model, marks the model default and the window in use, and `/context-window <size>` (`400k`, `1m` or a plain token count) selects one for the session. A size that the model does not list is refused and the list is shown. The selection sets the window that auto-compaction measures against, is kept when you switch to another model that lists the same size (otherwise the new model's default applies), is saved with the session and restored on resume, and is cleared if the model's server reports a smaller window. Values are bounded: zero is skipped with a configuration warning, sizes above 16,000,000 tokens and repeated sizes are dropped with a warning, and at most 16 sizes are kept per model. A model with one size, or none listed, has nothing to choose, and the command says so. The windows come only from your own configuration; nothing is fetched. A model-switch notification to connected clients now also carries `context_window_selection` when one is set; clients that do not know the field ignore it.
- **A notice for a model.** `notice = "preview: may change"` under `[model.<id>]` shows a short message in a banner above the prompt while that model is selected, and ACP clients receive it as `_meta.notice` on the model (additive and optional). The table form `notice = { severity = "warning", text = "...", label = "deprecated" }` sets the colour and a badge. The text is filtered as untrusted terminal text (control, escape and bidirectional characters removed, one line, 160 characters at most), starts with a fixed `notice:` tag and is never rendered as markdown or a link. It comes only from your own or your administrator's configuration, and a terminal 16 rows high or less hides the banner. The welcome screen before the first prompt does not show it yet.

## Known limits

The known limits listed in the 1.0.25 release notes stand unless an entry above says otherwise.

- There is no sandbox on Windows. A configured profile gives the warning described above and the session runs unsandboxed.
- For `fuigo wrap`, the Windows sandbox warning follows the profile in your configuration; a `--sandbox` option on the command line is not consulted.
- A campaign can add a new MCP server but can no longer change any setting of an MCP server that already exists in your configuration, including `enabled`.
- A model notice is shown above the prompt during a session. It is not shown on the welcome screen.
- `/context-window` and model notices read your local configuration only.
- `bearer_token_file` is not supported on Windows in this release: an MCP server that sets it is skipped with a warning (Fuigo keeps running). Use `bearer_token_env_var` there.

## Not taken in this release

- A footer line naming the model that served a reply is not included: nothing available to Fuigo reports that name.
- A change to how voice input discards stale events is not included: Fuigo's voice events already carry a session id and stale ones are dropped.
