## 1. The §2 answer (recorded before code)

**Answer: (b).** The main session's *initial* hook load does **not** append plugin hooks. Plugin hooks
only enter a session's registry after something triggers a reload. A plugin a user installs to enforce a
policy therefore does nothing on a fresh session until `/hooks reload`, `/plugins reload`, a plugin
add/remove/enable/disable (in any session, via the eager fan-out), or a trust grant.

### Corrections to the brief's premises

1. **`agent_ops.rs:4696` (now `:4732`) is not the subagent spawn path.** It is
   `spawn_and_register_session`, the *main* session spawn, taken only when the session's agent definition
   has inline hooks. Subagents never run `discover_hooks` when their parent has a registry: they copy the
   parent's `SessionHandle::hook_registry`.
2. **The §3 trust defect is real, but its mechanism is the stale handle snapshot, not the two
   predicates.** `project_scope_allowed` and `resolve_and_record(…, false)` agree on every verdict except the
   remote kill-switch input (`project_scope_allowed` passes `remote = None`): both re-read the store on a
   cached untrusted verdict and resolve fail-closed when unrecorded (`agent/folder_trust.rs:102-120,
   195-268`). What a subagent cannot see is the parent's *reload*: a mid-session `/hooks-trust` grant
   rebuilds the parent actor's `hook_registry` (a `RefCell` on the session thread), but the handle the
   subagent copies from still holds the spawn-time registry. The same staleness drops every
   reload-delivered plugin hook from every subagent.
3. **A gate gap on the existing reload path.** `reload_hooks_impl` re-appends plugin hooks from the
   session's *stored* plugin registry, which was built under the verdict current when it was built. After
   `/hooks-untrust` the hook reload re-reads the new verdict for disk hooks but re-appends project-scope
   plugin hooks that were admitted while the folder was trusted. Widening where plugin hooks fire makes
   this matter, so P07a closes it.

### Where plugin hooks will fire (the §4 decision) — as committed before code; see §2 for what audit changed

Plugin hooks fire wherever the session's own disk hooks fire, and nowhere else: the initial load of
every session (main and subagent), each reload, and subagents by inheritance from the parent's **live**
registry. No new event, dispatcher or firing site is added. Per site, the gate is the folder-trust
verdict for the session cwd, resolved by one predicate, and it decides both the disk project sources and
whether a `Project`-scope plugin's hooks are admitted. A subagent's hooks are a copy of its parent's
current registry, so it can never hold a hook the parent's gate did not admit.

## 8. P07b — NOT DELIVERED

A straight restore of what `e89bbd1` deleted was built and tested (branch **`strike/p07b-wip`**, `03309a72`, not on
`strike/p07`): `git revert e89bbd1 2bb2849c 87d2e355` (the `fuigo-hooks` half of `87d2e35` left alone so it stays
pager-only), a `disable_plugins` short-circuit on the `HookExecution` handler, and
`app/acp_handler/tests/plugin_hook_visibility.rs` (4 tests through the production handler; 4 mutants all red, focused
185 hook/lifecycle tests green). Its pre-gate audit (`audits/p07b-preaudit-astra.txt`) returned **DO-NOT-LAND**, and the
findings are design problems, not polish:

1. HIGH — tool hooks attach to `last_tool_call_entry_id()`: with two calls in a batch, A's post-hook lands on B and B's
   then overwrites it; tools without an ordinary row (task/goal/workflow) attach to an unrelated call or vanish. The
   `HookExecution` DTO carries no tool-call id, so a fix needs an additive shell field.
2. HIGH — a subagent's hook runs never reach its child view (`handle_child_session_notification` and child replay
   ignore `HookExecution`), so P07a makes child plugin hooks fire while P07b would still show nothing for them.
3. HIGH — the `[hooks: N]` badge is appended after a full-width tool header and is clipped off screen.
4. MEDIUM — denies reported twice (hook row + the shell's `HookAnnotation`); tests did not pin the screen buffer;
   hover hit-testing uses byte offsets; lifecycle rows inflate tool statistics; every attachment dirties full layout.
5. Reverting F045 (upstream 1.0.25, adopted in 1.0.20) makes **every** hook run visible again, from all sources, not
   only plugin hooks. That is a product decision.

**Recommended P07b scope:** do not revert. Add `tool_call_id` to `HookExecution` (additive), attach by id; route child
`HookExecution` to child views; keep F045's one-line failure and deny dedup; show a compact, width-reserved badge on
the tool row for plugin-origin runs only (decision for Sean whether all hook sources get it). The `strike/p07b-wip`
render machinery and tests are reusable for that.
