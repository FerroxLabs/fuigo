# R197: P197 D2 and D3 (session sweep put-back)

Branch `strike/p197-rename`, base `ac124b5a`. Tighten only.

## D2 (LOW) before and after
- Before: `rename_child_noreplace` (`persistence_sweep_pin.rs`, unix module) on `EINVAL`/`ENOSYS`/`ENOTSUP` looked up the
  destination and then ran a plain rename. An empty folder created at the old path in that gap was replaced.
- After: `put_back` (`persistence.rs`) calls the new `rename_child_noreplace_strict`, which on those errors renames
  nothing and returns `Unsupported`. `put_back` then takes its existing keep-aside path. The keep-aside rename itself
  keeps the old look-then-rename fallback: its target name `.fuigo-sweep-kept-<session>-<pid>` is ours, and the session
  must leave the `.fuigo-sweep-removing-*` name, which the next sweep deletes.
- Linux ext4 / macOS APFS: the no-replace call works, the strict function takes the same call and the same result as
  before (the raw call is only moved into `raw_noreplace`). The warning text was widened to also name the unsupported case.
- Other unix systems (neither Linux nor Apple) have no such call at all: a put-back there is now always kept aside.
- Windows: the changed code is in the `cfg(unix)` module. The Windows module only gained a one-line
  `rename_child_noreplace_strict` that calls its existing `rename_child_noreplace` (same behavior).

## What happens to a kept-aside session
It stays at `<cwd folder>/.fuigo-sweep-kept-<session>-<pid>` with all its files. Nothing restores it, and nothing deletes
it: no later sweep or start reads that prefix. The only trace is the existing warning
`SESSION_CLEANUP_PUT_BACK_ERROR`, which names the session path and the kept path (`dir`, `kept` fields) and the error.
No new restore logic was added (out of scope). More sessions can end up there on filesystems or kernels without
atomic no-replace rename (some network or FUSE filesystems, old kernels) and only when a session was marked
(attached) in the instant the sweep moved it aside.
Proposed release-note line (not added; common rule): "A session that is used while it is being cleaned up is kept under
a `.fuigo-sweep-kept-` name instead of restored on filesystems without an atomic no-replace rename."

## D3 (LOW, documentation only, no code)
An attach whose sweep-lock open failed, while the sweep's own lock succeeded, can bump `summary.json` after the sweep's
post-rename scan. The user then sees the session deleted and the load finds it missing. No code: the audit found no fix
beyond stating the window (a second scan after a pause would only shrink it); the sweep lock is held through put-back.
