## What changed (`crates/codegen/fuigo-shell/src/session/persistence.rs`, new `persistence_sweep_pin.rs`)

**1. MEDIUM (P178): an attach whose sweep lock fails for a reason other than contention.**
- Loads keep working on filesystems without usable locks: the mark still goes ahead unguarded (unchanged), and a sweep
  that cannot lock still keeps the session (unchanged, `try_lock_exclusive_pinned` → `None`).
- New: a sweep that CAN lock (the asymmetric case) looks at the session once more after its atomic rename, in the moved
  folder (step 5 of `cleanup_pinned_session`). Any mark that completed before the rename shows there (mtimes follow the
  inode); the session is then put back. A scan error also puts it back (fail safe).
- The put-back never replaces anything at the path (`rename_child_noreplace`: Linux `renameat2(RENAME_NOREPLACE)`, macOS
  `renameatx_np(RENAME_EXCL)`, Windows `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING`; elsewhere a lookup first). If
  the path was taken meanwhile, the session is kept aside as `.fuigo-sweep-kept-<session>-<pid>` (dot name: never listed,
  never removed by a sweep) and a `warn` names it.
- Astra r1 HIGH: a `.fuigo-sweep-removing-*` leftover is deleted only while its session's sweep lock is held exclusively
  (the sweep that moved it holds that lock until it has put the session back or committed to the removal), and only if
  its activity is older than the TTL. A leftover name that does not parse is kept.

**2. LOW (P178): a loader suspended past the TTL.** `mark_session_live` returns a `LiveMark` that holds the session's
sweep lock shared. `spawn_session_sweep` returns it; `session/new` and `session/load` bind it (`_live_mark`) until
`spawn_and_register_session` returns, which is after `spawn_session_on_thread` has taken `turn_owner.lock` shared. No
sweep can take the sweep lock exclusively meanwhile, so the session cannot be removed while it loads, however long the
load is suspended. (`spawn.rs` gets only a `cfg(test)` hook right before `TurnOwnerLock::acquire`.)

**3. P172/Fable: the folders above each session are pinned.** `PinnedDir`:
- Unix: every folder below the sweep root is opened `O_DIRECTORY|O_NOFOLLOW` relative to its pinned parent
  (`nix::fcntl::openat`); listing, `fstatat(AT_SYMLINK_NOFOLLOW)`, `renameat`, `unlinkat`, the recursive tree removal,
  the cache prune and the sweep's own lock files are all relative to pinned descriptors. Right before the rename the
  whole chain is re-checked (`still_at_path`: same dev/ino at the path) so that what the sweep read through paths (the
  activity scan, the lock an attach also opens by path) is what it acts on; and the look after the rename (item 1) fails
  safe if a path changed after that check.
- Windows: each pinned folder is a handle without `FILE_SHARE_DELETE` (`FILE_READ_ATTRIBUTES|FILE_TRAVERSE` access, as
  P154): it cannot be renamed, replaced or deleted, nor can any folder above it. Every child folder is checked from its
  own handle to sit directly in its pinned parent (final paths, P154's `final_path_windows` / `is_direct_child_windows`,
  now `pub(crate)` in `storage/mod.rs`), every deletion goes through a handle opened on the entry itself
  (`FILE_FLAG_OPEN_REPARSE_POINT`) and checked the same way (`FileDispositionInfoEx` POSIX|IGNORE_READONLY, classic
  fallback), and lock files are checked before their ACL is tightened (one created in the wrong place is deleted again).
  This covers the documented Windows quirk that an EMPTY held folder can still be turned into a junction in place.

**4. P172/Fable: Windows cache folder check→open.** The cache folder is opened once as the entry itself and checked from
that handle (a reparse point is refused), checked by final path to sit in the pinned session, and kept open while it is
pruned: the check and the open are one step.

**5. Test determinism.** `transport_errors_from_the_token_endpoint_do_not_carry_its_url` keeps its port bound (a
`TcpSocket` bound and not listening: connections are still refused) for the whole test, so no concurrent test can be
handed the port. Test-only change.

Files outside `persistence*`: `agent/mvp_agent/session_setup.rs` (2 bindings + `spawn_session_sweep` signature),
`session/acp_session_impl/spawn.rs` (cfg(test) hook), `session/storage/mod.rs` (two Windows helpers `pub(crate)`),
`auth/oidc/protocol.rs` (test), `fuigo-shell/Cargo.toml` (`nix` feature `dir`, no lockfile change).
**Concurrency with P164:** `session_setup.rs::attach_session_in_scope` (the resume/load path) and `storage/mod.rs` are

## Residuals (not fixed, with reasons)

- **Windows is source-only** (nothing compiled or run on Windows; Hetzner cannot cross-compile `ring`/`zstd-sys`/
  `aws-lc-sys`). The Windows code follows P154's Windows-verified patterns (`hold_folders_beneath_windows`, final-path
  checks) and Astra r3 checked the FFI signatures and constants; it still needs the RC smoke below.
- **macOS not compiled here** (`renameatx_np`/`RENAME_EXCL`, `nix::dir`, `st_mtime_nsec` read against libc 0.2.186 /
  nix 0.30.1 sources). A macOS `cargo check` (CI or one throttled Mac build) should run before release.
- **Asymmetric lock failure, last window:** an unguarded attach (its lock failed, the sweep's did not) whose `summary.json`
  open happened before the rename but whose mtime bump lands after the sweep's look in the moved folder: the sweep
  commits; the attach's load then finds no session ("not found"), the same outcome as resuming a session the TTL removed.
  Nothing is half-loaded or recreated. A put-back whose path was taken in the microseconds between rename and put-back
  keeps the session aside (`.fuigo-sweep-kept-*`, warn-logged), never deletes it.
- **Path-based reads are tied to the pins by a check, not by descriptors** (activity scan, the attach's own lock path):
  a same-user process swapping folders back and forth between the check and the rename can make the sweep judge one
  tree and rename another inside the pinned folder; it can never reach outside the sessions tree.
- **Tests:** the lockless test models an open failure of the lock file, not `ENOLCK` on the lock call; the pin tests are
  Unix-only.

## Release-note text (for `docs/release-notes-1.0.22.md`)

- **F (data integrity, follows P172 D1 / P178):** "The 30-day session cleanup is safer: a session being opened is
  protected until it is fully running however long opening takes; a cleanup that finds a session was opened while it

  longer undo each other; and the cleanup can no longer be led outside `~/.fuigo/sessions` by a folder swapped for a

  folder, and read-only cache files are cleaned up too)."
