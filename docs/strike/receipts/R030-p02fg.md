## P02f — start-up failure exit code
`fuigo-pager-bin/src/main.rs`: when `build_with_blocking_pool` returns `Err`, the process now calls `shutdown_and_flush_telemetry(RUNTIME_STARTUP_FAILURE_EXIT_CODE)` with **4** and a stderr line ending "(exit 4: Fuigo never started, nothing was run)". Exit-code space (recorded in the const's doc comment): `0` ok, `1` generic, `2` managed-policy, `3` headless permission denial, `4` start-up failure, `130`/`143` signals. 4 is the lowest free code, clear of `126`/`127` and `128+n`.

**Test:** `fuigo-pager-bin/tests/runtime_startup_exit.rs` spawns the real binary and reads `$?`. The failure is provoked, not stubbed: `ulimit -n N` for N in 5..=12 makes tokio's epoll/eventfd creation fail, so `Builder::build` returns `Err(EMFILE)`. Asserts at least one limit reaches "failed to start tokio runtime" (non-vacuous) and that EVERY run reaching it exits 4. Hermetic (`env_clear`, temp HOME and cwd, own process group SIGKILLed on a 30 s deadline, bounded stderr drain).
Finding while building it: an address-space limit does NOT work; a refused worker `pthread_create` is a tokio `expect` panic, i.e. SIGABRT under `panic = "abort"`, not an `Err`. So that startup path (`worker.rs:503`) still aborts with 134. See proposals. Probing also showed some descriptor limits die elsewhere (rc 134 from `tokio::signal` unix.rs:71, rc 1 from the policy lock); only the `Err` path from the runtime build gets 4. A unit test pins the code against all other codes.
