# R-xs-p13: peer messaging packet 13 (ACP surface and headless)

Branch `strike/xs-p13` from `hub/strike/xs-p9c`. Everything is behind `features.peer_messaging` (default off). Flag off: the capability key is absent (byte-identical object), `_fuigo/peer/*` answers as any unknown method (the dispatch arm is guarded by the flag), `fuigo -p` is unchanged (`--peer` is the only thing that sends anything).

## Wire contract (for hosts)
Capability: `result.agentCapabilities._meta["fuigo/capabilities"].peerMessaging = {version:1, methods:["_fuigo/peer/configure","_fuigo/peer/list","_fuigo/peer/list_held","_fuigo/peer/release"], operatorKinds:["attended","may_return","unattended"], events:[peer_held, peer_released, peer_refused, peer_expired, peer_reheld, peer_warning], errorCode:-32011, eventMethod:"fuigo/session_notification", defaultOperator:"unattended"}`.

Not opted in until `configure`. Every method needs `sessionId` and refuses unknown params (`invalid_params`).
- `configure {sessionId, optIn, operator?, policy?}`: `operator` required with `optIn:true` (`attended`=window present, `may_return`, `unattended`=no operator, the default posture; `unattended` holds are never released and a would-be hold is `rejected{no_operator}`). `policy` `accept` (default, still mode-equality gated) | `hold` | `refuse`. Reply `{sessionId, optIn, operator, policy}`. Calling it again (a reconnect) voids every token handed out before. The first opt-in registers the session with the inbox (arming the host if no entry point did: this is how `fuigo -p` is armed; `run_headless` is NOT edited).
- `list {sessionId, page?}`: `{sessionId, self:{address,name,ref}, page, more, rows:[{address,name,ref,relation}], text}`; names escaped and capped (64). Only opted-in sessions are listed to peers.
- `list_held {sessionId}`: `{held:[{heldId (opaque local id `h-<32 hex>`, a hash of the store key (sender + message id); the peer's own `message_id` is NEVER echoed: it is only length-capped, `fuigo-peer/src/wire.rs:106-112`, `envelope.rs:114`, so it may hold control or bidi characters), from:{ref,name,mode}, reasons:[..], detail, expiresAt, token}]}`. Each call issues fresh single-use tokens and voids the previous ones.
- `release {sessionId, heldId, token, action?:"release"|"refuse"}`: release goes through the admission handler and its atomic recheck at drain; reply `{result:"delivered"|"reheld"|"dropped"|"expired", expiresAt?, reason?}`; refuse replies `{result:"refused"}`.
- Errors: code -32011, `data.reason` one of `unavailable` (typed `peer_inbox_status()` reason text; includes a leader with a remote client attached: packet 9's process-level `remote_attached()` fact makes all four methods answer it BEFORE doing anything), `not_opted_in`, `no_operator`, `not_found`, `bad_token` (wrong or stale token of a live held row; a token already used, or an id this session does not hold, answers `not_found`: both are refusals, the store keeps no record of consumed ids), `expired`.
- Events (`fuigo/session_notification`, `update.sessionUpdate`): `peer_held {heldId, from, reasons, detail, expiresAt, counts:{held}}` (no token; ask `list_held`), `peer_released/refused/expired/reheld {heldId, detail}`, `peer_warning {text (fixed), subject (escaped), detail}` for protected-file change, guard kept with flag off, laundering refused. `heldId` is the same opaque id everywhere (`release` takes it). Sent only after the client opted the session in; one 1 s pump per opted-in session (the stop decision and registry removal are one step under a lock, so an opt-out/opt-in pair never loses or doubles the pump) ends on opt-out or session end. While a remote client is attached to the leader the pump stays alive (its lifetime follows the session's own opt-in, `PeerGate::client_opted_in`) and emits NOTHING; the held rows and the taken notices are announced after the client detaches, without another `configure` (Round 3). `heldId` hashes the full store key (sender address, a 0 byte, message id).

## Headless
`fuigo -p --peer` (hidden flag; ignored with a warning in the TUI) sends one `fuigo/peer/configure {optIn:true, operator:"unattended", policy:"accept"}` after the session opens; failure (flag off) aborts with a message. Without `--peer` no code runs. Held => rejected (no operator); delivered follows packet 4's unattended rule.

## Client-authored send: NOT built
The design lists `fuigo/peer/send` in the row 13 method set but states no authorship rule for an ACP client: S2.6 says the inbox cannot produce a human origin, row 12 gives the human-authored send to the TUI only, S4.5 says Fuigo cannot prove a human clicked, and the envelope has no human-authored field. Per the brief (build only if clearly allowed) it is not built; an ACP client cannot author a peer message.

## Tests
`extensions/peer_tests.rs` (real admission store behind a fake session): configure opt-in/out, validation, typed unavailable, remote-attached answers unavailable for every method and silences the pump, hostile ids never echoed, valid release, single use/replay, wrong/stale/foreign/expired tokens, tokens die on reconnect, refuse, unattended cannot release (hold rejected), event pump once-only + escaped + no token + pump does not void tokens. `agent/mvp_agent/tests/p13_peer_acp_tests.rs` (real `ext_method`): capability absent flag off and rest byte-identical on, flag-off unknown-method equality, remote-attached unavailable for all four methods, not-opted-in refusal, unknown session. `headless_tests.rs`: request shape, deadline bound, default off.

## Not done / limits
- Stated limits (owner-accepted or by design):
  - The gateway cannot address one client connection (`forward_fire_and_forget` has no client id; the leader sends a session notification to every subscriber of the session, `leader/server.rs` ~2531-2594). So every LOCAL client subscribed to the session receives the peer events; the remote case is closed by emitting nothing while `remote_attached()`.
  - No per-connection session ownership: any LOCAL client of the same user attached to the same process can configure, list and release for a resident session, and a release token seen by another local client works until it is used, re-issued (`list_held`/`configure`) or expired. Same-user local clients are the operator surface (the same-uid limit of the design).
  - A client declares its operator kind; Fuigo does not verify it.
  - Headless `--peer` configures operator `unattended` with policy `accept`: a message from a sender in the SAME permission mode with a matching operator kind is delivered and acted on with nobody watching (owner decision 38: equal mode delivers, also unattended); anything that would be held is rejected (`no_operator`).
  - `fuigo/peer/send` is not built: the design gives no authorship rule for a client-written message (above).
  - A replayed token answers `not_found`, not `bad_token`: telling them apart needs a record of consumed ids that the store does not keep.
- Release of a `sender_denied` row (S7.2, S4): the hold exists so a human who saw the denial note can release it, so a released row is delivered even though `decide` still says Hold for that sender (`peer_admission.rs` `check_at_drain`, `Qualification::Released` arm); otherwise it could never be released. The release is accepted only from an operator that can answer (`unattended` gets `no_operator`), and at the drain everything else is judged again: flag, opt-in (and a remote client attached, now part of `inputs()`), policy and operator snapshot, the mode snapshot, the integrity hold and the body hash; only the reason the human saw (`sender_denied`, `policy hold`, `mode mismatch`, `loop_guard`) is waived. The denials the message carried are installed at release (packet 7; `peer_admit_tests.rs` `s7_3_released_message_carries_denials_and_a_matching_request_is_denied_and_reported`). Test: `p13r2_a_released_sender_denied_row_is_delivered_but_every_other_reason_is_rechecked`.
- No send (above). No test drives the real actor drain for the ACP release through the wire (the store's release and drain are used; packet 4's tests cover the actor).
- Disconnect is detected only by the client calling `configure` again (tokens die then) or `list_held`; there is no connection-close hook.
- Files outside the list: `session/{handle,peer_admission}.rs`, `acp_session_impl/peer_admit.rs` (read-only held snapshot, tokens untouched), `peer_inbox/host.rs` (`ensure_session_registered`), `fuigo-pager/src/app/{cli,event_loop}.rs` and `fuigo-pager-bin/src/main.rs` (the flag).

## Round 3
- Pump vs attach (`extensions/peer.rs` `pump_tick`): `remote_attached()` is re-read synchronously immediately before EACH emit (no await between the check and the `forward_fire_and_forget` call). A held row is marked announced only when emitted; taken notices stay in the pump's `pending` queue until emitted (the session queue itself is drained by `take_notices`, so the pump keeps what it took). Sufficiency of check-then-send: `agent/app.rs` sets the attached fact (`hold_peer_attach`, lines ~811 and ~840) BEFORE the relay sender is published (`*agent_to_ws_tx.lock() = Some(tx)`, lines ~812 and ~841). Stated limit: `forward_fire_and_forget` is NOT synchronous to the subscriber list: it only does an unbounded-channel `send` (`fuigo-acp-lib/src/gateway.rs` `enqueue`, ~315-333), and the leader fans the notification out later; an event sent just before an attach could therefore still reach a subscriber added after it. The gateway was not redesigned. Test: `p13r3_an_attach_during_the_pump_awaits_emits_nothing_and_loses_nothing`.
- Pump lifetime (`run_pump`): follows `client_opted_in()` (ignores the attached fact). Test: `p13r3_the_pump_survives_a_remote_attach_and_announces_after_detach`. Single-pump guarantee unchanged.
- Unattended integrity hold (`peer_admission.rs` `decide_fresh`): a NEW message with the integrity hold up and nobody who can answer is refused `no_operator` (nothing stored). A row already accepted and stopped at turn start is still held (`r3f_stopped_row_with_no_operator_is_held_not_refused`). No other hold is added by `decide_live`. Test: `p13r3_a_new_message_with_integrity_up_and_no_operator_is_refused_not_stored`.
- `heldId` (`held_ref(from, message_id)`): hashes sender + 0 byte + message id; `HeldSummary` and `PeerNotice` carry the sender address (empty for notices not about a held message). Test: `p13r3_two_senders_reusing_a_message_id_have_distinct_held_ids_and_release_their_own_row`.
- After the final audit (coordinator): the pump's waiting queue is capped at 64 notices, oldest dropped first. Stated: notices still waiting in the pump when it stops (opt-out or session end) are lost (held rows stay in the store); during a long attach the session's own 64-notice ring also drops its oldest, so an old warning can be gone after detach; release matches the message id and the token, so for one message id reused by two senders the token decides which row is released.
