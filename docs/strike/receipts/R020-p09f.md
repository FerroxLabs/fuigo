## 2. Design notes and judgments

### 2.1 F1 in detail

- **Not dropped, deferred.** `recover_interrupted_turn` boxes the append future. If it is still pending at
  `RECOVERY_APPEND_TIMEOUT`, it returns `Deferred(DeferredRecovery)`, which holds:
  - the pending future;
  - the turn and its marker line;
  - a *shared* turn-owner lock, from `RecoveryGuard::into_shared`;
  - a registry entry naming the open `turn_started` by its `ts` and its own `prompt_id`.
- **Why the shared hold fixes (c).** Actors in any process share the lock and run. No recovery, here or in
  another process, can take the exclusive lock until the append resolves. So no second marker.
- **When the deferred recovery is finished.** `load_session` finishes it only *after* `spawn_and_register_session`.
  By then the actor has taken its own shared lock, and a late marker can be sent to a live session (a).
  - If the load fails before that point, the `DeferredRecovery` is dropped, and its `Drop` removes the
    registry entry. The append still lands (it is already queued), the turn stays open, and the next load
    reuses the marker. This is the existing idempotent path.
- **Closing exactly once, before any later turn (b).** A process-global registry (`DEFERRED_CLOSURES`, a mutex
  over a map from session dir to open turn) decides who closes the lost turn:
  - `finish` closes it when the append commits, while holding the mutex;
  - `turn.rs` calls `close_deferred_turn_before_new_turn` right before every `turn_started`. If an entry for its
    session is still pending, it closes the lost turn then, under the same mutex.

  Whichever runs first removes the entry, so the turn is closed once and always before the next turn starts.
  The fast path (no pending recoveries at all) is one mutex acquire plus `is_empty()`.
- **Cross-process guard.** Every closure first checks that the newest turn event is still the lost turn's
  `turn_started`. A turn started by *another* process sharing the session is never closed in its place (M19).
- **Judgment: closing before the marker commits.** An actor in this process can close the lost turn *before*
  its marker commits, when the actor starts a turn first.
  - If that append then fails (`NotCommitted`), the interruption is closed in `events.jsonl` with no marker
    in `updates.jsonl`; it is logged at warn.
  - I accepted this. The alternative, leaving the turn open while the next turn runs, loses the interruption
    just the same: the next turn's `turn_ended` hides it (the v3 bug). Gating the new turn until the append
    resolves would trade a liveness hazard for nothing, since the turn's own persistence queues behind the
    marker anyway.
- **Late delivery is a broadcast.** The marker goes out live with no `target_client_id` and no `persist_data`,
  so every subscriber of the session gets it. It is sent only if the session is still resident; otherwise the
  next load replays it from disk.
- **Possible duplicate on a replaying load.** If the late marker commits *before* the load's replay reads
  `updates.jsonl`, the client sees it twice: once replayed, once live, with the same `eventId`.

### 2.2 What is still not airtight (stated, not fixed)

- **A non-timeout failure.** If the append fails within the bound (`NotCommitted` or `AcknowledgementLost`,
  v3's path, unchanged), the turn stays open, but only until this process runs another turn in the session.
  That turn's `turn_ended` then hides it, as before.
  - R017a's corrected N2 row and the code's log text now say this. F1's fix covers the timeout path, which was
    the finding.
- **A late append that fails after the bound.** Same consequence, with the same log.
- **Lock conversion atomicity.** `into_shared` converts the `flock` in place on Unix.
  - On Linux the conversion is done under one hold of the inode's lock-context spinlock, so there is no
    unlocked moment. I believe this from memory of `flock_lock_inode`; **I did not re-read the kernel source
    in this packet.**
  - BSD/macOS document a conversion as possibly non-atomic.
  - On Windows the code unlocks and then relocks.
  - In the non-atomic cases, a different process's non-blocking recovery could slip into the gap and append a
    second marker.
- **The F2 bound fails the load after replay.** The lock wait happens in `spawn_session_on_thread`, after
  `load_session` has already replayed the transcript. The client therefore receives the replay and then the
  error. A retry replays again.
