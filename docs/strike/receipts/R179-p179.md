## Caveats first
- **Target "within 1.5x of v1.0.21 on every input": MISSED on two inputs, met on all others.** With 5 keys, 10 MB
  realistic JSON takes 0.09 s against 0.03 s (3x) and 100 MB percent/JSON text 0.83-0.94 s against 0.26 s (3.2-3.6x).
  That cost is P163's decoded views (percent, JSON, JSON twice: one decode-and-search pass each), not the cut-off check;
  it is a fixed cost per view, so with 100 keys the same texts are 5-6x FASTER than v1.0.21. This packet roughly halved
  it (P163: 0.36 s and 1.72 s) with a bulk copy of plain bytes in the views. Going further means dropping or merging a
  view, which is a P163 behaviour decision, not a speed fix.
- **No slower than P163 on any input: met** (table below).
- **LOW right neighbour (Fable): NOT changed, deliberately.** The symmetric reading Fable proposes (also accept the raw
  byte after an in-blob form) would redact the base64 of `abcdefgo` + e-acute followed by an escaped `/`, which P163's own
  test `p163_an_escaped_neighbour_is_read_as_what_it_decodes_to` (Astra r2 #3) requires to stay unchanged; Fable's repro
  (form followed by `%41`) has the identical structure, so no context-free rule satisfies both. Astra r1 agreed
  (`YWJjZGVmZ2%41` is also the base64 of `abcdefg` + a backtick). The behaviour is pinned in
  `p179_the_right_neighbour_of_an_in_blob_form` (a cut or non-escape tail is redacted, a complete wrong-bits escape or
  wrong-bits base64 char is kept). This is the evidence contradicting the brief's "make the right side symmetric".
- One Astra LOW left open: while the tail table is built, the per-spelling scratch holds one `u16` per char boundary of
  that one spelling before it is deduplicated (bounded by twice that spelling's length, freed per spelling; the stored
  table itself is capped). Not fixed, below the bar.
- Timings come from a box shared with four other live rp.sh lanes: expect noise of 10-20 %; each tip input was run
  twice.

## What changed and why
1. **MEDIUM, `Index::cut_off`.** `CutOffTails` (built lazily at the first truncation mark, so ordinary text pays nothing):
   a 64 Kbit bitmap of the last two bytes of every admissible cut-off beginning (each char boundary at or after the
   spelling's floor, every spelling) plus the sorted `(last two bytes, spelling)` pairs. A mark is checked only against
   the spellings whose beginning can end the way the text before it does, at either end it already considered (`mark`
   and `mark - trim`); candidates are sorted and deduplicated so the callback sequence is exactly the old loop's.
   Beginnings shorter than 2 bytes make their spelling an always-candidate (never skipped). Past `MAX_TAIL_PAIRS`
   (4M pairs, 32 MB) the table is dropped and a bitmap hit stands for every spelling (the brief's bitmap-only shape),
   so memory stays bounded for very long values.
2. **Bulk copy in the decoded views** (`Escapes::plain_run`, both decode levels of `scan_view`): runs of bytes that
   begin no escape are copied with their source map extended per byte, instead of one token at a time. Added after the
   benchmark showed the percent/JSON path was the remaining cost; not in the brief, same file.
3. **LOW right edge:** not changed (see caveats); repro added as a test.

## Release-note text (for `docs/release-notes-1.0.22.md`)
F: Scrubbing text dense in ellipses is back to (and past) 1.0.21 speed: 10 MB with 100 recorded keys takes 0.04 s
(P163 30 s, 1.0.21 3.6 s), the 4096-spelling worst case 0.04 s (P163 292 s); decoded percent/JSON views copy plain
bytes in bulk (100 MB of percent-encoded text 1.7 s to 0.9 s). Removes the P163 speed caveat on K24.
K (stays): with very few recorded keys, text that is mostly percent/JSON escapes costs about 3x what 1.0.21's scrub did
(one decode pass per view); an in-blob base64 form followed by a complete wrong-bits escape such as `%41` is read as
another value's base64 and kept.
