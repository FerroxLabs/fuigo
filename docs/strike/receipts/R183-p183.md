## Items and fixes
1. **Whole-file parse failure (fuigo-config `validation.rs`).** Startup now goes through `validate_requirements_from`, which reads
   each requirements file ONCE (`validate_requirements_file`) and checks loadability and P162's `version_overrides` rule on that one
   text, so the file cannot change between the checks.
   - System file (`/etc/fuigo/requirements.toml`) and the forced MDM payload: present but unreadable, not UTF-8, not TOML, a
     dangling symlink at the file or at its directory, or (MDM) forced with a missing/non-string value: **refuse to start**
     (exit 2), error `requirements at <file> could not be loaded: <redacted detail>; refusing to start without its policy`.
     The detail is location + parser kind only (`toml_error_detail`), never the offending line.
   - User-home file (`$FUIGO_HOME/requirements.toml`): **warn loudly and start**, unless fail_closed applies, in which case refuse.
     fail_closed applies when `FUIGO_MANAGED_CONFIG_FAIL_CLOSED=1` or the broken file's own top-level `fail_closed = true` is still
     readable: the real TOML parser reads the longest parseable prefix of whole lines (at most 64 KiB, bounded re-parses), and for
     invalid UTF-8 the whole lines before the first bad byte. The warning is returned by the new
     `validate_requirements_with_warnings()` and printed by `fuigo-pager` (`main.rs`) on both startup paths, because tracing is
     not set up yet there.
   - **Why warn, not refuse, for the user layer:** it matches P162's user-layer rule (a user layer with bad overrides keeps running
     on its base pins unless fail_closed). The file is user-writable, so refusing buys no security against its owner (who can
     delete it), and it would brick the CLI on a truncated cloud-cache write. The env and the file's own flag still let an admin
     make it refuse.
   - Astra r3 HIGH (inherited, not a P183 regression): a system file that validated at startup and broke before the later config
     load was silently dropped there. `load_admin_requirements_layer` now keeps the last validated/loaded copy of the system layer
     when the file is present but no longer loads (loud `tracing::error!`); removing or emptying the file still removes the policy.
2. **Test-version bypass (`loader.rs`).** New `policy_semver()`: `FUIGO_TEST_VERSION` is honoured only in a dev build (no stamped
   `FUIGO_VERSION`) and only when it parses; otherwise the compiled version. Used by `validate_requirements_value` and by
   `apply_version_overrides_with_registered` (so the loader no longer strips patches unapplied on a garbage value either). If even
   the compiled version could not parse, a fail_closed/admin layer refuses.
3. **Vanishing hooks (`loader.rs`).** `hook_config_layers_at`: the user-home requirements layer joins P162's keep-base branch, so
   its base hooks stay when its `version_overrides` are bad (P162 had done this for the managed-policy tiers only).
4. **`inspect` label (fuigo-shell `inspect/mod.rs`).** `describe_requirements_file` now says
   `not loaded: <redacted error>; no pins from this file` or
   `version_overrides refused (<redacted error>); base pins kept` / `...; no base pins in force`, and the text view prints it.

## Behaviour changes (for the release notes)
- A system or MDM requirements layer that exists but cannot be read or parsed now stops Fuigo at startup (exit 2). Before, it was
  silently ignored. This includes a dangling symlink and a forced MDM value of the wrong plist type.
- A broken user-home requirements file prints `Warning: requirements at ... could not be loaded ...` at startup (and refuses with
  fail_closed).
- Release builds ignore `FUIGO_TEST_VERSION` for policy; dev builds ignore a non-semver value.
- User-home requirements hooks with bad `version_overrides` now run (base hooks) instead of vanishing.

## Release note
S: Managed requirements no longer fail open when a whole file is broken: a system or MDM requirements layer that cannot be read
or parsed (including a dangling symlink or a wrong-type MDM value) stops Fuigo at startup with an error naming the file, and a

### Trust rule for an admin path (item A)
An admin source is trusted only if the OPENED object (one descriptor, opened `O_NONBLOCK`, `fstat` before any read) is a regular file owned by root with
`mode & 0o022 == 0` (P169's `admin_owned`), AND the directory holding the entry (as the path names it, through any symlink) and the directory holding the file it
finally resolves to are each owned by root and not group/other-writable. A final symlink is FOLLOWED and the target judged by the same checks on the same
descriptor (chosen over `O_NOFOLLOW` because `/etc/fuigo` or a file behind a root-owned symlink is a legitimate setup; a link to a user-owned file, a device or a
fifo fails the checks). Anything that exists and fails (device, fifo, socket, directory, dangling link, wrong owner, writable directory) is `Err` = "broken", never
absent or blank; the validated copy is kept, or the lock-down applies when there is none. Only a trusted regular blank file clears the copy. Not checked: ancestors above
the holding directory (`/`, `/etc`): the platform's own; checking them would reject shared sticky parents. Code: `policy_sources::admin_object_trusted`,
`open_admin_file`; used by `validation::read_admin_bytes` and `read_layer_strict`.
Cache key (`managed_settings_cache_key`): the sources Debug (carries content or the error) PLUS whether a validated copy exists for each source path. A copy that
appears or is dropped changes the key. `managed_hooks_only_pin` has no copy dependency and keeps the sources key.

**Absence rule.** If this process holds a validated copy of an admin source and the source is now ABSENT, the copy stays in force, on both readers (`kept_copy_of_absent_admin_file`; `absent_admin_layer` in `policy_sources.rs`; `managed_settings_json`). Choice: COPY ONLY, no lock-down, because that is what the round-10 TOML requirements reader does for a deleted file (it returns the copy); a lock-down would make the engine stricter than the requirements path for the same event. A dangling symlink is still broken (copy + lock-down). A process that never saw the file treats absence as no policy. Unlink-then-create: the copy holds during the gap and the new valid file replaces it on the next read; rename-over never shows absence.
