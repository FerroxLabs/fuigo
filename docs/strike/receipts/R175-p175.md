## Rules implemented

Three-outcome model (`branch_switch.rs`, `TreeListing`): every tree is `NotPresent` (the NAME does not resolve; skipped
only when the tree is optional), `Listed(names)`, or `Undetermined` (over the 16 MiB cap, 2 s child limit, spawn or git
error, unexpected exit, malformed output, a name that resolves but whose tree cannot be read, a sha that is not a tree).
`Undetermined` always keeps the floor. `NotPresent` is decided by `rev-parse --verify --quiet <name>` (exit 1, or 128 for
the dying forms such as `@{upstream}` with no upstream) and only after the tree lookup failed. A damaged tree makes
`rev-parse X^{tree}` answer an unrelated commit id (seen with git 2.43), so the sha is checked with `cat-file -t`.

### Batching design
Round 1 of the check runs two children side by side: discovery `rev-parse --is-bare-repository --show-toplevel
--glob=refs/replace/*` (bare state, root, replace-ref presence) and `cat-file --batch-check` fed `<rev>` and
`<rev>^{tree}` for every tree (one output line per input, `<rev> missing` for an unresolvable name, so each failure is
attributed to its own ref; the object type comes from the same line, which replaces the old `cat-file -t`). Round 2:
one `ls-tree` per DISTINCT tree id, side by side (HEAD and target on the same tree are listed once). Forms that DIE
instead of printing `missing` (`@{upstream}` with no upstream) end the batch child; the lines already printed say
which rev it was (not present, as exit 128 was before) and ONE more batch child resolves the rest.
Worst case: with a replace ref the resolve runs twice (with and without `--no-replace-objects`) and trees are listed
in both views (union judged); plus one extra resolve child per dying rev (pull: `@{upstream}`, stash: `stash@{N}`);
plus `for-each-ref` + a re-resolve for a remote-only branch (rare); plus the work-tree listing after an earlier
`git commit`; plus one `symbolic-ref` for an unborn HEAD; plus one `config` child for submodules. All bounded by the
2 s per child and 8 s overall limits, unchanged. Regression test: `p175_item1_common_case_child_count_is_bounded`
(<= 3 children same tree with ONE listing; <= 4 with two trees), counted behind the `SPAWNED` test seam.

## Part B (decision 11): an earlier write into the git directory unsettles the branch-switch plan

### Rule
An EARLIER non-git segment unsettles the plan (as an earlier git verb does) only when one of its write targets resolves
inside `<repo>/.git/**`, where `<repo>` is the nearest ancestor of the switch's effective cwd (planner `cd`/`pushd` and
`git -C` tracking) that has a `.git` directory. Opaque commands (`npm test`, `make`, `./x.sh`) have no write target and add no prompt;
read-only commands likewise. Code: `exec_risk.rs:1000` (`branch_switch_plan_with`, the check at ~1138-1150, before the
existing `(Some(_), Some(_)) if unsettled` arm); `branch_switch_plan` is a wrapper passing no facts.

### Reuse of the destination analysis
The targets are the P166 `ShellWriteFacts` the protected-file floor already builds per request (`BashEvaluation.write_facts`,
built by `ShellWriteFacts::from_tree`): redirect targets plus `command_targets` (`shell_access.rs:2793`, which calls
`command_words_destination_writes` for cp/mv/ln/install/rsync/scp/ditto/pax and the writer-operand extractor for tee, dd of=, ...).
New in `shell_access.rs`: `git_starts` (start byte of each git command, 2756/2992), `writes_into_git_dir_before` (3060) and
`writes_into` (3065), which walk the same targets and the same `bases()` cwd chain (3027) as `protection_in`, and a small
`lexical_clean` (3168, folds `.`/`..`; no filesystem). The manager passes `&evaluation.write_facts` at both call sites.
Ordering: a target counts only if its start byte precedes the n-th git command (n = the planner's git-segment ordinal).

### Behaviour on the edge shapes
- Destination cannot be determined: `Unpinned` and `opaque_write` (expansion redirect) name no path and do not count here (the
  floor treats them as its own sensitive/opaque case and prompts independently); an unpinnable preceding `cd` or `~user` target
  counts (floor: Sensitive). Nothing new was invented.
- `.git` FILE (worktree/submodule pointer) and `GIT_DIR`: the existing analysis does not resolve them; not built. With a `.git`
  file, `is_dir()` fails, so no rule applies (unchanged behaviour).
- Another repository's git dir (`cp x other-repo/.git/refs/heads/main && git checkout main`): not inside this repo's `.git`, so it does not unsettle.
- If the git-command ordinal cannot be matched (fewer git commands in the facts than segments) the position limit is "anywhere".

## Part B round 2 (Grok r1)

### Fixes
1. BLOCKER symlink spelling. `writes_into_git_dir_before` resolves the git dir once with `resolve_following_symlinks` and, per write
   target, compares the lexically cleaned path (old rule) OR its resolved path (symlinks followed, missing leaf keeps the resolved parent).
   Same-line `ln -s SRC DEST`: the facts now record symbolic `ln` commands with two operands; an earlier one whose SRC (read from the cwd,
   from DEST's parent, or inside DEST) is the git dir or inside it counts as a `.git` write. So `ln -s .git g && cp x g/refs/heads/main &&
   git checkout main` and `ln -s .git/refs/heads/main ref && cp x ref && ...` are Undetermined.
   Resolution failure (loop, depth cap 40, unreadable link, ENOTDIR): the target COUNTS (fail closed). Safe for everyday commands because
