   in the agent's environment, so children that inherited it (`!` bash mode, client terminals, the external auth

## 4. Behaviour changes for Sean (plain words, with a one-line release note each)

**B1 — the saved API key is no longer in the agent's environment (the big one; needs Sean's yes).**
Before: at `initialize` the agent copied the key saved in `~/.fuigo/auth.json` into its own `FUIGO_API_KEY` (only if
that variable was empty), and `fuigo/setApiKey` did `set_var("FUIGO_API_KEY", key)`. Now the key is held in process
memory and read where the environment copy used to be read. A key the LAUNCHER exports as `FUIGO_API_KEY` is used and
inherited exactly as before; nothing changes for users who start Fuigo with the key exported.

What a user with a saved (not exported) key will notice, established from the code (survey of every spawn site,
verified at the decisive points: `fuigo-tools/src/util/shell_env_policy.rs:217` and `:96-101`,
`fuigo-config/src/loader.rs:717-719`, `fuigo-hooks/src/runner/command.rs:512-535`, `key_discovery.rs:268`):
- **Children that inherit the agent's environment with no name-based strip no longer see the key:** commands run in
  `!` bash mode, terminals a client opens (`fuigo/terminal/create`, PTY tabs), the external auth command
  (`auth_provider_command`) and its refresh, the status-line command, notification hooks, git / gh (and any git hook
  or credential helper they run), the `fuigo update` child and the restart after an update. `echo $FUIGO_API_KEY` there
  is now empty.
- **Unchanged, because they never received it:** the model's shell tool, hooks, stdio MCP servers, LSP servers and
  `[auth_provider.*]` helpers. Each strips `FUIGO_API_KEY` / `FUIGO_CODE_API_KEY` by name before spawn, whatever the
  user's `[shell_environment_policy]` says. So **a stdio MCP server that calls FluxRouter never inherited the key**,
  before or after this packet.
- **Config that names the key by `${FUIGO_API_KEY}` / `$FUIGO_API_KEY` no longer finds the saved key.** Those strings
  are expanded from the process environment (per session, after `initialize`, which is why they used to see the copy):
  MCP server `env` / `args` / `command` / `url` / `headers`, hook commands and HTTP hook URLs, plugin hook commands, any
  other `config.toml` string such as `api_key = "${FUIGO_API_KEY}"`. An unresolved reference is left as the literal
  text, so e.g. a stdio MCP server configured with `env = { FUIGO_API_KEY = "${FUIGO_API_KEY}" }` (the way such a server
  got the key before) now receives the literal `${FUIGO_API_KEY}`, and a hook command using `$FUIGO_API_KEY` is not run
  ("hook not executed: required env var(s) not set"). Left this way on purpose: these strings are templates for child
  processes and command lines, which is exactly where the key is not supposed to go implicitly.
- **Still works, routed to the in-memory key:** inference, the tools / auxiliary key, the key probe, a model's
  `env_key = "FUIGO_API_KEY"`, the sampler's `env_http_headers`, an MCP server's `bearer_token_env_var`,
  `oauth_client_secret_env_var` and `[oauth] client_secret_env_var` naming `FUIGO_API_KEY` (Astra r3/r4; never the
  runtime key a client supplied for inference), `fuigo/getApiKey`, and nested `fuigo` runs (they read `auth.json`
  themselves).
- **Display:** `/provider` no longer lists `FUIGO_API_KEY = …` for a key that came from `auth.json`
  (`key_discovery::discover` reads the environment).

Supported ways to pass the key explicitly after this change: (1) export `FUIGO_API_KEY` in the shell that launches
Fuigo: everything above then behaves as before, including `${FUIGO_API_KEY}` expansion; (2) for an MCP HTTP server,
`bearer_token_env_var = "FUIGO_API_KEY"` (works with the saved key); (3) the key's value written into a stdio MCP
server's `env`, a hook's `env` map (stored verbatim, not expanded) or `[shell_environment_policy] set = { … }` for the
model's shell tool (all put the key in a config file); (4) a client terminal request's `env`. There is no supported
way to hand the SAVED key to a child by reference; proposal 2 offers one for MCP `env` if Sean wants it.

Release note: *Fuigo no longer copies your saved API key into its own environment, so programs it starts
(terminals, `!` commands, git, your auth helper) no longer see it; if a script, hook or MCP server config relies on
`$FUIGO_API_KEY`, export the key before starting Fuigo.*

**B2 — attribution and auth log fields hold a fingerprint, not key characters.** `key_suffix`, `sent_key_prefix`,
`current_key_prefix`, `key_prefix`, `rt_prefix`, `*_key_prefix` keep their names; their values are now
`sha256:<4 hex>/len=<n>` instead of the last 12 (or first 8) characters. A dashboard or query that matches on a key
tail stops matching; comparing two fields of the same record (stale-snapshot detection) still works.
Release note: *Diagnostic logs identify credentials by a short fingerprint (`sha256:ab12/len=40`) instead of their
last characters.*

**B3 — a response Fuigo cannot parse is reported by category and position.** The error (shown to the user) and its
log line used to quote serde's message, which quotes part of the response; now `serialization error: Data error at
line 1 column 347` (or `Data error` when the parser gives no position). Handling is unchanged (same error kind).
Release note: *When a provider's response cannot be parsed, the error now says where, instead of quoting the
response.*

**B4 — `fuigo trace` prints `Deploy:   configured`** instead of the first and last four characters of the deployment
key (all of a key of 11 characters or fewer). Release note: *`fuigo trace` no longer prints any part of the deployment
key.*

**B5 — the sampler's debug log lists request header names only**; it used to print the values of every header whose
name did not look sensitive (a `Cookie` or `x-credential` header included). Release note: *Debug logs no longer
contain request header values.*

**B6 — URLs in logs lose their userinfo, query values and fragment** (sampler, relay incl. the CONNECT proxy URL,
model-list resolution, session-credential warnings; a transport error's logged text). Returned errors are unchanged.
Release note: *Logged URLs no longer show passwords or query-string keys.*

**B7 — `session/new` and `session/load` debug lines log metadata only** (cwd, number of MCP servers, whether `_meta`
is present) instead of the whole request, which printed MCP header and env values. Release note: none needed (debug
logging).

**B8 — the external auth command is named by fingerprint** in logs and in its error messages
(`failed to start auth provider (command sha256:ab12/len=40): …` instead of the command line).
Release note: *Errors from the external sign-in command no longer repeat the command line.*

**B9 — `Debug` output of secret-bearing types prints `<redacted>`** (developer-facing; panics and `{:?}` logs).

**B10 — User-Agent:** a session origin whose product name cannot form a header value now gets the agent's own
User-Agent; before, a `user-agent` configured in `extra_headers` survived in that one case.

### 13.0 What is NOT met, or needs a decision, first

1. **A saved key is never filled into a URL, and that is narrower than the brief (Sean decides).** The brief lists MCP
   `url` and the P70a receipt listed HTTP hook URLs. An unexported `${FUIGO_API_KEY}` in an MCP server's `url` or an
   HTTP hook's `url` stays the literal text. Reason, found the hard way over ten audit rounds: a URL is an identifier.
   Fuigo records it (`fuigo/mcp/list` and `servers_updated` to the client, `events.jsonl`, OAuth credential-store ids,
   reconnect and discovery logs, `HttpInfo`, DNS-failure text) and so does its HTTP stack (reqwest's connector logs the
   destination at DEBUG), and none of that can be scrubbed reliably. What works instead: an MCP **header**
   (`headers = { Authorization = "Bearer ${FUIGO_API_KEY}" }`) or `bearer_token_env_var = "FUIGO_API_KEY"`; for an HTTP
   hook there is no header option, so only `export FUIGO_API_KEY` (which expands in URLs exactly as before P70a).
   Also not filled: a model's `extra_headers` (they also come from the remote model catalogue and its disk cache, so a
   catalogue entry could otherwise aim the key at its own endpoint; `api_key` and `env_key` are the spellings that
   work) and an MCP server's `command` / `cwd`.
2. **The audit ended LAND-WITH-FOLLOWUPS, not LAND, after twelve rounds; three findings are open.** No BLOCKER/HIGH
   in the last two rounds (f11, f12). Open: f12 #1 MEDIUM (a `setApiKey` between config conversion, where
   `bearer_token_env_var` resolves, and server construction, where a header reference resolves, can give one HTTP MCP
   server two key versions); f8 #1 **HIGH as Astra rated it, not fixed** (a reference COMPOSED from another variable,
   `${PREFIX}$${FUIGO_API_KEY}` with `PREFIX = "$"`, defeats the `$$` escape); f8 #3 MEDIUM (a `$$`-run before the name
   inside another variable's modifier, `${OTHER:-$$FUIGO_API_KEY}`, stops that outer expression from expanding). The
   last two are stated limits in `credential_env.rs`: config values are expanded in several passes (the loader, MCP's
   second `expand_strings`, the hooks parser, a shell), so escape provenance cannot be kept exactly without redesigning
   config loading. Both need the config author to write them and the key still reaches only the destination that
   author configured. Rounds f9-f12, briefed with these as stated non-claims, did not raise them again. I did not
   downgrade f8 #1; Sean or the coordinator decides whether it blocks.
3. **Any config source can name the key, and so can an ACP client.** Project config after folder trust, plugins,
   server-managed config, `.mcp.json`, `~/.claude.json`, `~/.cursor/mcp.json`: as with the old environment copy.

4. **Consent is per hook child, not per occurrence.** A command hook whose command or `env` names the key gets
   `FUIGO_API_KEY` in its own child environment; everything that child runs can read it.
5. **A model's `api_key = "${FUIGO_API_KEY}"` is unit-tested, not end to end** (`first_own_credential`).
6. **`/proc/self/environ` cannot detect a leak into the process environment**, although the brief asks for it: it

   assertion removed) SURVIVED, as predicted. The assertions are there; the detectors are `std::env::vars` and the children that

### 13.2 What it does (the design that stands)

- **One resolver** (`fuigo-config/src/credential_env.rs`, moved down from `fuigo-config-types`, which re-exports it):
  the shell installs `read_named_key_env_without_runtime` when it loads or sets the saved key. For `FUIGO_API_KEY` it
  answers a `setApiKey` key, then an exported key, then the key from `auth.json` (the order the old environment copy
  gave); never the runtime key an ACP client supplied for inference; no other name is routed through it.
- **Late binding.** Config loading (`expand_env_vars_in_string`) expands `${FUIGO_API_KEY}` from the process
  environment only, as before P70a: an exported key behaves exactly as it always did. An unexported reference stays
  the literal text through everything that reads, shows, records or re-saves config. It is resolved
  (`resolve_first_party_key_references` / `read_first_party_key_references`) only where the value is used:
  an MCP stdio server's `args` and `env` values at spawn and an MCP HTTP server's header values when its client is
  built (`fuigo-mcp` `start_mcp_server`, one key snapshot per server); a model's `api_key` in the runtime credential
  (`first_own_credential`); a command hook's child environment (`fuigo-hooks` `hook_child_env`).
- **Hooks.** Parse-time expansion never writes the saved key into a hook's command line. At spawn, a hook whose
  parsed command references `$FUIGO_API_KEY` in any shell form (also nested, `${X:-$FUIGO_API_KEY}`, and through an
  `env` alias the parser substituted) gets `FUIGO_API_KEY` in its own child environment, applied after the policy
  strip; a `${FUIGO_API_KEY}` inside one of its `env` values is resolved (`env = { MY_TOKEN = "${FUIGO_API_KEY}" }`);
  an `env` entry named `FUIGO_API_KEY` wins. The "required env var(s) not set" pre-flight sees the injected key.
  **A hook whose config does not name the key gets nothing**: a script that reads `$FUIGO_API_KEY` from its inherited
  environment still finds it empty, saved or exported, because every hook child has the name stripped. That is the
  point of P70a and is unchanged.
- **Escape.** Before the name, `$$` is an escape for `$`: `$${FUIGO_API_KEY}` in an MCP `env` / `args` / `headers` value
  arrives as the text `${FUIGO_API_KEY}`. The expanders keep a `$`-run before the name unexpanded (they cut the string
  there; no masking) and the destination decodes it; in a hook command the shell's own rules apply (`$$` is its PID).
  Limits: 13.0 item 2.
- Nothing writes the key to Fuigo's environment.

### 13.3 Final user-visible behaviour (replaces the third bullet of B1 in section 4) and release notes

With a SAVED key (entered at the prompt / `auth.json` / `fuigo/setApiKey`) that is not exported:

| where | gets the saved key? |
|---|---|
| `!` commands, client terminals, git / gh, status line, notification hooks, auth helper, update restart | no (P70a) |
| a stdio MCP server, a hook, an LSP server, the model's shell tool, by inheritance | no (never did) |
| MCP stdio `env = { X = "${FUIGO_API_KEY}" }`, `args = ["--key", "${FUIGO_API_KEY}"]` | **yes**, that server only |
| MCP HTTP `headers = { Authorization = "Bearer ${FUIGO_API_KEY}" }`; `bearer_token_env_var = "FUIGO_API_KEY"` | **yes** |
| hook `command = "... $FUIGO_API_KEY ..."`; hook `env = { X = "${FUIGO_API_KEY}" }` | **yes**, that hook's child only |
| a hook script reading `$FUIGO_API_KEY` that the hook's config does not name | no |
| model `api_key = "${FUIGO_API_KEY}"`, `env_key = "FUIGO_API_KEY"`, `env_http_headers` | **yes** |
| MCP `url`, HTTP hook `url`, MCP `command` / `cwd`, model `extra_headers` | no (literal text); export the key |
| Fuigo's own records of the config (`mcp/list`, session events, logs, settings saves) | show `${FUIGO_API_KEY}` |

With an EXPORTED key everything behaves as before P70a, with one edge: a `$`-run written directly before the name
(`$${FUIGO_API_KEY}`) in a field that is not late-bound (a URL, `command`, `cwd`) now arrives as written instead of
losing one `$`.

New behaviour, not a restoration: a `${FUIGO_API_KEY}` inside a hook's `env` VALUE is resolved (hook `env` values
were never expanded before, for any variable); MCP servers passed by an ACP client in `session/new` have their
`args` / `env` / header references resolved.

Release notes:
- Saved-key note (replaces B1's): *Fuigo no longer copies your saved API key into its own environment, so programs
  it starts (terminals, `!` commands, git, your auth helper) no longer see it. Explicit `${FUIGO_API_KEY}` references
  in your config keep working: in an MCP server's `env`, `args` and `headers`, in a model's `api_key`, and in a hook's
  command or `env`, the saved key is handed to that one place. Programs that relied on inheriting `FUIGO_API_KEY`
  must reference it explicitly, or you export it before starting Fuigo.*
- *A saved API key is not filled into URLs (an MCP server's `url`, an HTTP hook's `url`) or a model's
  `extra_headers`; use an MCP header, `api_key` / `env_key`, or export the key.*
- *Write `$${FUIGO_API_KEY}` in an MCP server's `env`, `args` or `headers` to send the text `${FUIGO_API_KEY}` itself.*
- User guide: `fuigo-pager/docs/user-guide/02-authentication.md`, "A saved API key stays inside Fuigo".
