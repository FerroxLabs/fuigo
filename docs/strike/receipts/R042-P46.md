## 2. Analysis per flake

### 2.1 Flake 1 — pager fork refusal (`chat_kind: false`)
`plant_local_build_session` writes under `fuigo_dirs::fuigo_home()`. At `bf8514ee` the production lookup
(`chat_mode_refuses_local_build_load` → `resolve_local_session` → `fuigo_home()`) resolved the home again from
`FUIGO_HOME` and `HOME`. Tests in the same binary rewrote those at any time: `FuigoHomeFixture` (set and never restored),
the `OnceLock` homes in `cta_e2e`, `acp_handler::tests` and `effects::tests`, and `setup_fuigo_home_in_tempdir`. A row
planted in one home and looked up in another counts as "not on disk", so `ForkSessionReady` loaded it (`chat_kind: false`)
instead of refusing it. P21 (`21b48d9a`..`491a0e72`) moved every such writer into its own process and extended
`enforces_own_process_keys` to `fuigo_pager-*`. At `ac7bfe92` the remaining raw writers all call
`require_own_process_for("FUIGO_HOME")` (checked with git grep). A reader-side fix I drafted at `bf8514ee` (rerun the plant
tests in their own process) was dropped as redundant.

### 2.2 Flake 2 — MCP-pool child request not found
The original log already showed that the child completed (`failures == 0`) and that the parent's request was found. A
temporary diagnostic that dumped every chat request on failure captured the failing run (`logs/f2-diag2-1.log`, sha256
`f597ffe9e958e16ba76203a01ba51b950ad99ab1ba7dc5c8f98fbefc7917561a`, 192-way stress, binary from `0242a1b5`):
```
P46DIAG [35] turn_idx=None nmsg=2 tools=["session_title"] last={"role":"user","content":"<user_query>\nReply with the word done and nothing else (000).\n</user_query>"}
P46DIAG [36] turn_idx=Some("1") nmsg=3 tools=[... "search_tool", "use_tool", ...] last={"role":"user","content":"<system-reminder>\nMCP server connected:\n- parent-pool-fixture (1 tool)\n ..."}
```
Request [36] is the child's main turn (`turn_idx=1`, the child tool set, `[system, probe prompt, reminder]`), and it
advertises both meta-tools. The behaviour under test held. The test's assumption that the probe prompt is the last
message is wrong: MCP reminders are pushed as a user message (Astra r4 confirmed `push_user_message`). The matcher now
looks at every user message, and the tool assertion is unchanged. Astra r2 and r4 judged this a justified assertion
correction, not a loosening.

### 2.3 Flake 3 — "smoke check exceeded 100 ms"
`CHECK_TIMEOUT = 100 ms` is a **product budget**. The check runs on the tool-result path of every workflow write, and it
is what cuts off a nonterminating script (`loop {}`). The verdict tests depended on a **test-only assumption**: that a
`spawn_blocking` hop plus disk and trust reads plus validation always fit in 100 ms of wall time. `snapshot_authored_workflow`
and `check_snapshot` now take the budget. Production passes `CHECK_TIMEOUT`. The verdict tests pass 120 s.
`nonterminating_workflow_times_out_promptly` still passes `CHECK_TIMEOUT` and still asserts the literal
"exceeded 100 ms". `dropped_check_releases_permit_after_cancel` also stopped using 100 ms: with a host stall over
100 ms, its timeout and its 20 ms sleep became ready together, and `select!` picked one at random.

### 2.4 Flake 4 — interleaved token rotation (a product defect)
The diagnostic capture (`logs/f4-diag-auth-1.log`, sha256 `44cc92abe97414a27af99e04ea49b656ff97cadd09c2a11d7f2231f35a57dde4`):
```
P46ENRICH start key=key-v1 ...733.96   P46ENRICH start key=key-v2 ...733.69(+0.74 s)
P46ENRICH auth update enrichment done 11        (v1's merge wrote)
P46ENRICH auth update enrichment skipped 9      (v2's merge: sibling_rotated)
P46ENRICH final disk=Some(("key-v1", Some("rt-v1"), Some("team-alpha")))
```
v1's enrichment read v1 under the file lock. `update(v2)`, whose callers do not all hold that lock (the login paths, and
this test), wrote v2. v1 then wrote v1 back. The refresh token was reverted, and a reverted refresh token is later spent
twice and fails with `invalid_grant`. This was not a slow host racing a 3 s deadline; the data on disk was wrong. Fix (final form):
one process-wide reentrant `storage::auth_state_lock()`, taken by `update`, `save_without_enrichment`, the enrichment
merge (from its read through its in-memory write), `remove_scope_impl` with its in-memory drop,
`prune_stale_inherited_scopes` (which now re-reads under both locks), `store_api_key` and `clear_api_key`, `clear_inner`
and `with_inner_write`. Lock order: file lock, then the state lock, then `inner` / `permanent_failure`. The enrichment
also skips when memory no longer holds its credential (`superseded_in_memory`). The tests use a `cfg(test)`
`EnrichmentGate` to force each interleaving. They no longer wait for load to produce it:
- `enrichment_task_preserves_interleaved_token_rotation` parks v1's merge after its checks and before its write. It
  requires `update(v2)` to be recorded waiting on the lock while v1 is parked, and unfinished. It then releases v1 and
  waits for both enrichment completions. It asserts disk and memory both hold v2 with the profile.
- `enrichment_does_not_resurrect_a_credential_cleared_from_memory` parks the merge before it takes the lock, clears
  memory, releases, and asserts nothing was restored.
- Both tests run in their own process, because they park while holding the process-wide lock.
- The siblings `update_writes_disk_before_user_enrichment` and `enrichment_overlays_team_login_placeholder_user_id`
  waited on a 5 s clock. They now wait on the completion count. Their field assertions are unchanged.

### 2.5 Flake 4b — `compute_proactive_sleep_dark_wake_returns_backoff` (found during P46)
Under load at `9941822b` it failed 2/25 with `left: 300s right: 1s`. `is_dark_wake` reads `FUIGO_AUTH_FORCE_DARK_WAKE` on
every call, and the two tests that write it (`serial(force_dark_wake_env)`, a group no reader takes) did so in the shared
process. Both now rerun in their own process (Astra r5: no other writer in the crate).

## 7. Proposals (outside P46's ownership; not fixed here)
- **P-1 (HIGH, Astra r2/r6):** `store_api_key` / `clear_api_key` and the bare login `update` callers (oidc, device-code,
  external provider) do not take the cross-process `auth.json` flock. A sibling process can still roll back tokens.
  `update`'s doc claims "caller holds the file lock", which is false for the login paths.
- **P-2:** `auth::subscription::tests::{cancelled_and_timed_out_login_release_listener, callback_state_rejected_before_exchange_and_storage}`
  fail under load. They rebind a just-released loopback port.
- **P-3:** `auth::attribution::tests::*mint_age*` assert a 0–5 s / ±N s wall-clock window, and fail when the host stalls.
- **P-4:** `app::edit_highlight_worker::tests::{double_submit_prunes_pending_after_latest, run_job_succeeds_on_temp_file}`
  flake under load in the pager suite.
- **P-5:** `enrichment_aborts_when_disk_user_changes_mid_flight` (2 of 21 at the parent) assumes `/user` (300 ms) outlasts
  the test's 50 ms before it writes the "intruder" entry, and the intruder write takes no lock. Under load, the merge can
  write between the intruder's read and its write. A gate (`EnrichmentGate::BeforeMerge`) would make it deterministic.
- **P-6:** A child that inherits a connected MCP pool sometimes gets "MCP server connected" appended after its prompt and
  sometimes does not, depending on timing. Whether the model is told is nondeterministic.
- **P-7:** Running a pager test binary directly (not through cargo) writes insta `.snap.new` files into
  `crates/codegen/fuigo-pager/crates/...` unless `INSTA_WORKSPACE_ROOT` is set.
