## 1. Defect (P38-F R021 §10, pre-existing)

A new run's journal file was first written at the run's first journaled step. `Ctx::record` and
`Journal::dispatch` call `initialize_recovery`, which wrote the v2 header lazily. A run paused or stopped before
that step therefore left no file. On resume, `Journal::load` read the missing file as empty with
`restored: true, versioned: false`. The first dispatch or record then hit `initialize_recovery` with
`restored == true` and returned `LegacyBoundary` (journal.rs `initialize_recovery`, old ~289-295), so the resume
failed.

## 2. Fix, and why

**Positive evidence = the v2 header written at run creation.** The new `Journal::create(path)` creates the dispatch
sidecar (empty) and then the journal holding exactly `V2_HEADER`. Both files are created with `O_EXCL`
(`create_new`), each `sync_all` plus a parent-directory sync. Before that, `create` refuses if either file
already exists. `WorkflowManager::launch`, new-run branch, now calls `Journal::create` when there is a session dir
(`Journal::new(None)` stays for the in-memory case). If `create` fails, launch removes the store registration
(`store.remove`) and returns `LaunchError::Journal`, before `tracker.start_run` and before any engine starts.

A run paused or stopped before its first step now reloads as a **header-only v2 journal**: `versioned = true`,
empty sidecar, no entries. `initialize_recovery` is then a no-op and `replay` returns `None` for seq 0, so the
run starts afresh from seq 0 with nothing to replay. That is the same run id, script, args and effort, all
immutable as before.

**Legacy detection is unchanged.** `load` and `initialize_recovery` are untouched. A missing file, an empty
file, a header-less file with entries, or a torn header (truncated as a torn tail, leaving it empty) is still
`restored && !versioned` and still yields `LegacyBoundary`. Absence alone is never read as "fresh".

**Judgments (please check):**
* **J1, rejected alternative: "missing file means fresh".** In the legacy format, `record` runs only *after* the
  effect. A legacy run whose first `spawn_agent` went out and was never recorded also leaves no file. A missing
  file therefore cannot tell "nothing happened" from "an effect happened unrecorded". Mutant M2 shows the tests
  reject this approach.
* **J2, rejected alternative: tracker/run-record metadata.** `journal_path` and the store's `args.json` /
  `script.rhai` were written by older versions too, so neither identifies the journal format. Adding a format
  field to the run record would touch `tracker.rs` and persistence. The header already *is* the format marker
  that `load` checks, and writing it earlier needs no new on-disk concept.
* **J3, consequence: runs created by a pre-P45 build** that paused or stopped before step 1 have no file and
  **stay unresumable** (`LegacyBoundary`, fail closed). The fix is forward-only, by design and per the
  "never absence alone" rule. Their error message still says "legacy workflow journal …". I did not change it.
* **J4, call site.** The brief said "minimal resume call site". The correct site is the *creation* path in
  `launch()`, not the resume path: the resume path needs no change once creation writes the header. The edit
  is in the same function, in its `None` (new run) arm.
* **J5, crash ordering.** The sidecar is written before the header. If a crash happens after the sidecar but before
  the header, the file is missing or torn, which reads as legacy and fails closed. In any case `launch` has not
  yet called `tracker.start_run` / `persist_now` at that point, so the run is not resumable at all. A header
  present without a sidecar is impossible through `create` (and `load` already rejects it: "missing recovery
  metadata must fail closed").
