## Item 2: change
- New `fuigo-tools/src/util/read_deny.rs`: `ReadDenyFilter` built from the call's Read-deny globs (same set and
  same semantics as ripgrep's `--glob !<deny>`, relative to the session cwd; `ignore::overrides`). `None` when there
  are no globs, so a session without read rules does no matching at all (the short-circuit).

  denied directory is not entered. Listing a denied directory itself prints the header and no children. A denied

- `grep` with an explicit `path` that is (or physically resolves into) a denied file/dir: refused with
  "Error: <path> is excluded by a read rule and cannot be searched." (exit 2, like the gitignore refusal). ripgrep
  reads explicit file arguments even against `--glob !`, which the red test proved.
- Decision (grep names): a denied file's name is not returned (recommended no; satisfied by the excludes).

## Round 4 (Grok r3): ripgrep JSON records

**Design.** Text output cannot be attributed to a file safely (a notice line has no NUL and glues to the next record; names may hold `:`, `|`, a newline). With read rules present every ripgrep SEARCH now runs with `--json` and `util/rg_json.rs::RgJsonStream` consumes the typed records: `begin` opens a file, the path is decoded (`text`, or base64 `bytes`; undecodable = file dropped), judged ONCE by `ResultFilter` (as written and by canonical place), every `match`/`context` is attributed to that file (a record naming another path drops the rest of the file), and `end` closes it (`binary_offset` and `stats.matched_lines` are fields there). The stream RE-RENDERS the text the tools already parse, for allowed files only: `--heading` content (`N:`/`N-` lines, `--` between non-adjacent context groups, blank line between files), `path:count`, `path`, and the OpenCode `path|N|text` form; head limits, byte caps and totals run downstream of it, so they count only allowed output. Anything outside `begin`..`end`, unparsable, or unknown is dropped (fail closed). `-l`/`-c` are not passed with `--json`; they are derived from `end` (`-l` runs with `--max-count 1`). With NO read rules the tools run exactly the text invocation as before. `--files` (OpenCode glob) keeps `--null` (`RgNullStream::new_files`): records are one path each and ripgrep prints no notice into that stream. Codex `grep_files` with no rules is `0e5a6b09`'s invocation again (`current_dir(cwd)` always, no `--null`, newline parse); with rules it uses `--json`.

**The "total" rule (finding 3).** The two-probe sampling is gone. A directory D is pruned (name hidden, never entered) only when (a) the rule is the catch-all `*`, or (b) a rule's TEXT is exactly `P/**` or `P/**/*` with `P` free of `* ? [ ] { }` and `\`, and `P` equals D or an ancestor of D in one of the spellings the policy offers for D (`path_match_forms`: absolute, cwd-relative, `./`-relative, physical-cwd forms), compared as strings with a `/` boundary; or (c) `**/P/**` or `**/P/**/*` with a literal `P`, considering only D's cwd-relative spellings (an absolute spelling is simply not claimed). A trailing-slash rule (`P/**/`) is NOT total (it matches only paths that end in `/`, so the matcher allows the files). Every other rule shape enters the directory and judges each child by the matcher. Why this is sound: for a literal `P`, `P/**` and `P/**/*` match every path strictly under `P` in that spelling (checked by the unit test, which asserts for every pruned case that children `a`, `.hidden`, `a/b`, `a/.b/c.md`, `x.rs` are denied by the matcher). A non-total rule can only cost time (the directory is walked and each child judged); it can never hide an allowed file, and it never reveals more than a name the policy does not deny. A directory's own name is hidden only when it is pruned, so `**/*[0-9]` and `**/[!.]*` keep `src` visible (its children are judged), while `secrets/**`, `secrets/**/*` and `<abs cwd>/secrets/**` still hide `secrets`. **The fix (audit `grok-p198-r4.md`, HIGH `rg_json.rs:109`).** The parser kept ONE "current open file", so a record of
another file (ripgrep searches in parallel and writes JSON lines under a per-message lock, so records interleave) marked
the open file not allowed and dropped allowed matches. Now every `begin`/`match`/`context`/`end` record is attributed by
the `path` it carries (`text` or base64 `bytes`; undecodable: dropped). State is a map path -> `FileState` (verdict
judged once on first sight with `ReadDenyFilter` as written and by canonical path, buffered lines, counters). A file's
block is rendered when its `end` record arrives. A record for a path with no `begin` creates the state and is judged then.
No `-j1`, no `--sort`.

- **Bound.** Lines are dropped while buffering: at most `MAX_FILE_BUFFER_BYTES` = 5,000,000 per file (the tools' own
  `MAX_STDOUT_BYTES`, so a block that large is cut by the tool anyway) and `MAX_TOTAL_BUFFER_BYTES` = 32,000,000 over all
  open files; ripgrep has one open file per search thread. Denied files buffer nothing (verdict first).
- **End of stream.** A file with records but no `end`: an ALLOWED file is emitted as received (lines; or its path in
  `-l`; or the count of matched lines seen in `-c`; no binary notice); a DENIED file is dropped. Unfinished files come out in
  first-seen order, after the finished ones.
- **Ordering.** Files come out in the order of their `end` records (before: in `begin` order, one block at a time).
  With several threads ripgrep's text order is not fixed either, so this is the same class of nondeterminism and the
  existing tests compare sorted lines. Contents of each file's block are unchanged. opencode `grep` and `glob` sort by mtime
  themselves, so their order does not depend on this; fuigo_build `grep` and codex `grep_files` keep ripgrep's order.
- **`summary` records and records without a path:** ignored as before.

## Part G, count mode (owner override)

Problem: with a read rule present, count mode re-rendered counts from `--json` (`end.stats.matched_lines`); `rg -c` prints
something else when the pattern can match a newline under `-U`.

Observed on the box (ripgrep 14.1.0), `rg -c` vs `end.stats` `matches`/`matched_lines` (flags the tool passes: `-U --multiline-dotall`
only when `multiline`):
| fixture / pattern | `rg -c` | `matches` | `matched_lines` |
|---|---|---|---|
| s.txt `FAKE FAKE FAKE`, `FAKE`, no -U | 1 | 3 | 1 |
| s.txt, `FAKE`, -U | 1 | 3 | 1 |
| s.txt, `FAKE\|\n`, -U | 4 | 4 | 1 |
| m.txt (`FAKE a\nX\nZZZ\nFAKE c\nY\n`), `FAKE a\nX\|FAKE c\nY`, -U | 2 | 2 | 4 |
| m.txt, `FAKE.*FAKE`, -U (dotall, one span) | 1 | 1 | 4 |
| t.txt `ab\nab ab\n`, `ab`, -U | 2 | 3 | 2 |
| `x*` (empty matches) with or without -U | 3/5/1/2 (lines) | 6/22/15/9 | 3/5/1/2 |
| `^`, e.txt/m.txt/s.txt/t.txt | 3/5/1/2 | equals lines | same |
| binary file (NUL after a match) in a directory search | omitted by `-c` | n/a | n/a |

Rule: ripgrep counts MATCHES when the searcher is multi-line AND the matcher can match a line terminator, else matching LINES.
The JSON stats do not decide it (`-U FAKE` and `-U FAKE|\n` on s.txt have matches 3 vs 4 but both lines 1, and `-U ab` shows
matches 3 where `-c` is 2), and deciding it needs ripgrep's regex analysis.

Chosen approach: the robust alternative. Under rules, count mode no longer asks for `--json`; it runs ripgrep's own `-c --null`
(`path NUL count \n`, with the same other flags) and `RgJsonStream` in the new mode `RgJsonMode::CountNull` drops each record whose
path the `ReadDenyFilter` (via `ResultFilter`) denies, and prints the others as `path:count`. It reproduces `rg -c` by construction
(ripgrep computes the number, including binary-file omission), leaks nothing (only names and counts are printed, a denied record is
dropped whole) and a denied file is in no total (the tool sums the lines it receives). The JSON `Count` mode stays in the code,
exercised by its existing unit tests, but the tool no longer selects it. The no-rules path is untouched.

Tests (`util/search_proof_tests.rs`): `count_mode_under_rules_equals_rg_dash_c` (9 pattern/-U cases over a 5-file tree, rule
