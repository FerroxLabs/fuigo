## What changed
- Compaction commit queues `_fuigo/compaction_checkpoint` (marker + file, <=4 MiB) and now also a Flush, so an idle session uploads it.
- Pull writes `compaction_checkpoints/<id>.json`, rewrites the marker path, rebuilds `chat_history` from the summary. Id is a plain token.
- Upload fallback (`remote/client.rs`): a save carrying checkpoints that gets a 4xx other than 401/403/408/429 is retried once without them (normal messages never dropped); one warning; the refusal is remembered for the process (not for 413, which may be one oversized checkpoint). The retry's success is required before remembering. Auth failures are returned unchanged with no retry.
- Security (pre-existing hole): a pulled `_fuigo/session/update` compaction marker had `checkpoint_file` joined unsanitised. Pull now requires a plain-token id and rewrites the path (else drops the marker). Because sessions pulled by older versions are already cached on disk, every reader of a marker's path (history rebuild, jsonl checkpoint read, compaction witness, replay x3) goes through `contained_checkpoint_path`, which only follows exactly `compaction_checkpoints/<token>.json`.

## Open / unverified
- Backend behaviour is unverified: nobody has uploaded to the live service. The fallback makes either outcome safe. The summary is kept remotely only if the backend accepts the `_fuigo/compaction_checkpoint` method; if it refuses, saves still succeed and a pulled session resumes without its summary (as in 1.0.20).
- LOW (open): after a 413 every successful filtered retry logs the warning again (the 413 exemption skips the once-only guard).
- Accepted: after a refused-then-filtered save the omitted checkpoints are not re-queued (pending is cleared on success), so a later upload does not resend them. If a backend stored part of a rejected body before the 4xx, the retry could duplicate normal messages; needs backend atomicity, unverified.
