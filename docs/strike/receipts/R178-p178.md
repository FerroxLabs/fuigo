## What changed (`crates/codegen/fuigo-shell/src/session/persistence.rs`, `agent/mvp_agent/session_setup.rs`)

**1. MEDIUM, Windows: idle sessions were never removed.** P172 renamed the session folder while the sweep held
`turn_owner.lock` and `sweep.lock` open INSIDE it; NTFS refuses to rename a directory with any handle open beneath it.
Now:
- the sweep lock lives NEXT TO the session: `<cwd folder>/.fuigo-sweep-lock-<session>` (dot name, never listed);
- the sweep (1) takes the sweep lock exclusively and holds it until the session has left its path, (2) takes
  `turn_owner.lock` exclusively (no live actor anywhere) and **closes it at once**, (3) re-checks activity, (4) renames
  atomically, (5) unlinks the sweep lock while still holding it, then releases it;
- a failed rename now logs at `warn` (a Windows session held open by another program is kept, visibly);
- an orphaned sweep lock (its session `NotFound` before and after taking the lock exclusively, older than the TTL)
  is removed.

**Why the race stays closed.** An attach marks (bumps an mtime) while holding the sweep lock shared, and an actor only
starts after its attach's mark. So for every interleaving:
- a mark that completed before step 1 bumped the session, and step 3 (under the sweep lock) sees it and keeps it;
- a mark that started before step 1 and still holds the lock shared makes step 1 fail: kept;
- a mark that starts after step 1 waits (asynchronously, ≤ 5 s, else `SweepBusy`) until after step 5; it then
  re-checks `summary.json` at the old path, finds nothing, and the load fails "not found" — nothing is recreated;
- an actor alive at step 2 holds `turn_owner.lock` shared for life: step 2 fails, kept. Closing the sweep's own
  `turn_owner.lock` handle before the rename opens no window, because any actor that starts after step 2 belongs to a
  mark covered by the three cases above;
- on Windows, a handle anyone else holds inside the folder makes the rename fail: the session is kept whole.
P172's mutants still die on the new code: m11 (attach does not take the sweep lock) and m13 (delete in place, no
rename), plus new m14 (sweep lock released before the re-check/rename), m15 (sweep lock back inside the folder), m16
(`turn_owner.lock` held through the rename). See Mutants.

Linux/macOS outcomes are identical to P172: the same sessions are kept or removed under the same interleavings
(every P172 sweep/race test passes unchanged in substance; only the lock-file location differs, and the locks are
held over the same critical sections).

**2. LOW: a `summary.json` that cannot be bumped.** `mark_session_live` now:
- bumps `summary.json` while holding `summary.json.lock` exclusively (Astra r1 HIGH: the worktree identity repair,
  `storage/summary_write.rs::repair_worktree_identity`, records the summary's mtime, rewrites it and restores the
  older mtime under that lock, which could erase a mark — inherited from P172);
- if the summary cannot be bumped (read-only, sharing violation, sidecar lock busy past 5 s or unavailable), bumps
  `updates.jsonl` instead (the repair never touches it);
- if neither can be bumped, the load fails with `MarkLiveError::Unmarkable` ("This session was not loaded: Fuigo
  could not record that it is in use … Make those files writable … and retry"), unless — **while holding the summary
  lock** (Astra r2 HIGH) — the session's newest activity is under 23 h old (no sweep, minimum TTL 1 day, can remove it
  in the next hour). `SessionSweepBusy` became `MarkLiveError::{SweepBusy, Unmarkable}`.

**3. LOW: activity from top-level files only.** `session_last_activity` now scans the session's subfolders too
(`compaction_checkpoints/`, `prompts/`, `subagents/<id>/…`, `terminal/`, anything else): regular files only, never a
symlink, folder mtimes ignored (the cache prune changes them). Bounded: 20 000 entries and 8 levels; past either bound
the scan fails and the session is kept, never judged on a partial look. The top-level `turn_owner.lock` is not
activity.

## Residuals (not fixed, with reasons)

- **MEDIUM (Astra r3, inherited from P172 `6a57cd89:persistence.rs:3683`):** a NON-contention error on the sweep lock
  (e.g. `ENOLCK`) lets the mark proceed unguarded. On a filesystem without advisory locks this is safe (the sweep
  cannot lock either and keeps the session); the hole is an *asymmetric, transient* lock failure in the attaching
  process only. Fixing it means failing (or delaying 5 s) every load on lock-less filesystems (NFS/SMB without locks),
  an availability regression vs 1.0.21. Recommendation: keep for 1.0.22, revisit with a guard handed from the mark to
  the actor (next item), which removes the dependence on timestamps entirely.
- **LOW (inherited):** the mark's protection is a timestamp, not a guard held until the actor takes
  `turn_owner.lock`; a loader suspended past the TTL (or past the 1-hour margin of the recent-use exception) is not
  protected. Comment corrected in `b750edadc`. Real fix = carry the shared sweep guard through `load_session_inner` →
  `spawn` (outside P178's files).
- **LOW:** the waiter-across-unlink test handshakes via `/proc/self/fd` on Linux only (1 s pause elsewhere), and no
  test pauses a mark between its summary check and its lock open (a late opener creating a fresh lock inode; reasoned
  safe by Astra r3: it re-checks and finds no summary).
- **INFO:** the NTFS double proves the handle-lifetime property only (this process's descendant handles); it does not
  model foreign handles, sharing modes, `LockFileEx`, delete-pending names. `LockWait::Unsupported` on the summary lock
  cannot be produced on Linux (no test).

## Windows smoke checklist for the 1.0.22 RC (coordinator; real NTFS, isolated `FUIGO_HOME`, fresh process per sweep — the sweep runs once per process)

1. **Idle removal (the regression):** create `sessions/<cwd>/idle/{summary.json,updates.jsonl,prompts/p.txt}`, backdate
   all to 40 days, start fuigo on another session. Expect `SESSION_CLEANUP_RM_SESSION` for `idle`, the folder gone, and
   no `.fuigo-sweep-lock-idle` / `.fuigo-sweep-removing-*` left in the cwd folder.
2. **Foreign handle keeps it whole:** same, but hold `idle\updates.jsonl` open from another process (e.g. PowerShell
   `[IO.File]::Open(...)`). Expect `SESSION_CLEANUP_RM_SESSION_ERROR: session kept` at **warn** (os error 5), every file
   intact; close the handle, restart: removed.
3. **Live actor keeps it:** keep a 40-day-idle session open in a running fuigo; start a second fuigo. Expect it kept.
4. **Attach vs sweep:** resume the 40-day-idle session in one process while a second process starts (sweeping):
   either the session loads whole and stays, or the load fails "not found"/retry — never loads and then loses files.
5. **Unbumpable summary:** mark `idle\summary.json` read-only (attrib +R); resume it: loads; `updates.jsonl` mtime is
   now; a parallel sweep keeps it. Then also `attrib +R updates.jsonl`: resume fails with "This session was not
   loaded: Fuigo could not record that it is in use …"; nothing is created.
6. **Subfolder activity:** 40-day-old top-level files plus a fresh `subagents\c\updates.jsonl`: kept.
7. **Leftover/crash:** kill fuigo during a sweep of a large idle session; restart: the `.fuigo-sweep-removing-*` folder
   is removed, the session never reappears in the list.

## Release-note text (for `docs/release-notes-1.0.22.md`)

- **F (fix, follows P172's D1 line):** "On Windows, the 30-day session cleanup now actually removes sessions nobody has
  used for the whole period (it previously kept them because it held files open inside the folder it was moving). Work
  saved only inside a session's subfolders (subagents, checkpoints, prompt offloads, terminal logs) now counts as use,
  so such a session is never removed. If Fuigo cannot record that an old session is in use (its files are read-only
  or locked by another program), it refuses to load it with a clear message instead of risking its removal mid-load."
- **K:** no 1.0.21 K row; nothing shrinks. Note under Windows/known limits: "Session cleanup on Windows is verified by
  the RC smoke only."
