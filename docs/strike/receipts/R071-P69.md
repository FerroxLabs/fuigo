# R071 — P69: binary-driven tests could silently run a stale `fuigo-pager`

**Packet:** P69 · **Branch:** `strike/p69` · **Parent (gate):** `ae59250998a873305c7b28f32a3d79241bc00312` ·
**Code tip:** `1f00f32186f92855b64d0c5725d9649bb9d10206` (this receipt commit sits on top and changes no code) ·
**Host:** hetzner-dsm, lanes `p69` (demo + mutants, one target dir) and `p69g` (gate, `rpb.sh`) ·
**Toolchain:** rustc 1.94.0, `rustc -vV | sha256sum` = `b75985398e5509a90a7d5d68f8ec6690675f703c5cfa11893b04fc9c3fceca69`.

## Defect
`fuigo-test-support/src/env.rs` `fuigo_binary()` → `ensure_local_fuigo_binary()` returned early when
`<target>/debug/fuigo-pager` existed. Any target dir holding a binary from another commit made every binary-driven test
(`acp_client`, `headless`, `leader` — `leader.rs::role_binary` falls back to `fuigo_binary()`) spawn code not under test.
Shown below: parent-built binary in the target dir, resolver with the parent logic → the test ran `fuigo 1.0.20 (ae59250998a8)`
while HEAD was `d0173169e359`.

## Fix (only `crates/codegen/fuigo-test-support/src/env.rs`)
- `d830c7ac`→`5e2452dc` (amended before any gate): the local fallback ALWAYS runs
  `cargo build --locked -p fuigo-pager-bin --bin fuigo-pager`, once per test process (`OnceLock<Result<PathBuf,String>>`;
  a failed build is latched and panics in every caller — never a fallback to the old file).
- `1f00f321` (Astra round-1 HIGH): the build uses `--message-format=json-render-diagnostics` and the executable is the one
  `compiler-artifact` message for target `fuigo-pager`/kind `bin` (zero or several → error; missing on disk → error). No
  guessed `target/debug` path, so `CARGO_BUILD_TARGET` / `build.target-dir` can no longer return a stale file.
- Unchanged: `FUIGO_BINARY` and `CARGO_BIN_EXE_fuigo-pager` overrides win as before; `FUIGO_BINARY_LEADER/CLIENT` stay
  explicit overrides that otherwise delegate to `fuigo_binary()`.
- Tests (`env::local_binary_tests`, unix): 5 fake-cargo unit tests (`/bin/sh script`, no ETXTBSY) —
  `an_existing_binary_is_rebuilt_not_trusted`, `the_executable_cargo_reports_wins_over_a_stale_file_at_the_default_path`,
  `a_failed_build_is_an_error_even_with_a_stale_binary_present`, `a_build_that_reports_no_executable_is_an_error_even_with_a_stale_binary_present`,
  `a_reported_executable_that_does_not_exist_is_an_error`; plus `#[ignore]` e2e probe
  `resolved_binary_is_built_from_the_checkout` (resolved binary's `--version` commit stamp must equal `git rev-parse HEAD`;
  refuses to run with a binary override set).

### Gates and CI: do they always build binaries fresh?
- **`scripts/strike/final-gate.sh`:** default lane `final-gate-<sha12>` → its own `CARGO_TARGET_DIR=$LANE/target`, unless
  the caller pre-exports `CARGO_TARGET_DIR` (line `export CARGO_TARGET_DIR="${CARGO_TARGET_DIR:-$LANE/target}"`). Workspace
  scope phase 1 (`cargo test --workspace --no-run`) builds the `fuigo-pager` bin from the candidate (fuigo-pager-bin has
  integration tests, so cargo builds and uplifts its bin). So the RELEASE gate was fresh. Exposed before P69: `--pkg`
  scopes that exclude fuigo-pager-bin with a reused or pre-exported target dir — the old resolver took whatever binary
  was there. With P69 every binary-driven test process rebuilds from the candidate tree, and `--network none` works
  (proved above).
- **`rp.sh`** (parent then tip in ONE target dir, no per-side pager build): tip side ran the PARENT's binary whenever
  the tip still had the old resolver. `rpb.sh` closes it from the outside; P69 closes it in-tree once in the parent.
- **CI (`.github/workflows`):** `release.yml` build job runs `cargo build --release --target <t> -p fuigo-pager-bin` and
  ships that artifact (fresh). Its `security` job uses a fresh `CARGO_TARGET_DIR: target/security-checks` and no
  rust-cache. `f13-test-reliability.yml` and `dispatch-policy.yml` use `Swatinem/rust-cache` but run only `--lib`
  tests (`fuigo-shell`, `fuigo-workspace`, `fuigo-extra-ca`, …). No crate's `src/` outside `fuigo-test-support` calls
  `fuigo_binary()`, and `fuigo-test-support` is not tested in CI. So **CI runs no binary-driven tests at all**: it could not
  be fooled by a stale binary, and it gives no coverage of these tests either (proposal 4).

## Proposals (outside P69 ownership)
1. **`crates/build/fuigo-proto-build/src/lib.rs` `emit_rerun_if_changed`** (worth the most): when protoc comes from PATH it
   emits `rerun-if-changed=protoc`, a relative path that never exists. That makes `fuigo-tools-api` and its dependents
   rebuild on every cargo invocation (~70 s per invocation on hetzner; with P69 also once per binary-driven test process).
   Fix: emit the resolved absolute path, or skip the line for a bare PATH lookup. Interim: export `PROTOC=/usr/bin/protoc`
   in `slot-run.sh` / `rp*.sh` / `final-gate.sh` (measured 71 s → 1.3 s).
2. **`scripts/strike/final-gate.sh`** `--network none`: add `CARGO_NET_OFFLINE=true` to the INNER command, so nested cargo
   invocations are offline by flag, not just by cached deps (Astra LOW).
3. **`crates/codegen/fuigo-pager-pty-harness/src/env.rs` `pager_binary()`**: already builds on every call (not stale on
   commit change), but it still guesses `<target>/debug/fuigo-pager` (same HIGH as above) and has no per-process latch.
   Port the P69 JSON-artifact resolution.
4. **CI:** no workflow runs a binary-driven test (`fuigo-shell/tests/*_acp.rs`, leader, headless). Consider a focused job.
5. Retire `rp.sh` in favour of `rpb.sh` until every gate parent contains P69.
