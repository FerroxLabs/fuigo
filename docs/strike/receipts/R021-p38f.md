## 1. The MEDIUM, confirmed

* `manager.pause()` stores `pause_intent`, fires the run's `CancellationToken`, and eagerly sets the tracker
  to `UserPaused`. The host loop (`host_service.rs`) answers what it has queued with `Cancelled`, then ends.
  A request the engine sends into that teardown is dropped with the receiver, stranded (P38), or refused by
  the closed channel. With P38 the engine then ends that call with `RecvError` / send error, which became
  `Fatal("workflow host dropped reply" | "workflow host channel closed")` → `WorkflowOutcome::Failed`.
* The watcher kept the pause only for `Cancelled | Paused`; for `Failed` it called `apply_outcome`, which
  does not protect `UserPaused` (it ignores outcomes only for `Interrupted | Failed | Cancelled`;
  `tracker.rs:506-528`). So the run became `Failed`.
* Stop variant: `cancel()` eagerly sets `Cancelled`, so the tracker status survives (`apply_outcome`
  ignores the `Failed`), but the outcome the watcher reports and sends on `outcome_rx` is `Failed`.
* Shutdown variant: `cancel_all_and_drain` fires the token without touching the tracker, so a lost reply
  there turned the run `Failed`.
* `parallel()` was worse: a lost reply recorded a `dropped_reply` terminal in the journal, which every later
  resume replays as `Failed: workflow host dropped reply`.

The window is not only P38's tokio race: the host breaks out of its loop on cancel but keeps its receiver
until it has drained its children, so anything sent in that time is dropped with the receiver at task end.

## 2. The fix and where it belongs — decided: the engine

`engine.rs`: `Ctx` carries the run's `cancel` token. New `host_gone(ctx, failure)`: if the stop signal has
fired, return `ControlToken::Cancelled` (exactly what `HostError::Cancelled` produces), else
`Fatal(failure)` as before. Used at every place a host request is refused or its reply lost:
`host_call` send and reply, `reserve_agent_calls` send and reply, `parallel()` send. `parallel()`'s
pending-reply loop maps `Err(_)` under a stop to `TERMINAL_CANCELLED` (resumable: nothing recorded,
`release_agent_calls` attempted) instead of `TERMINAL_DROPPED_REPLY`.
`manager.rs`: no behaviour change. The watcher's lifecycle decision moved verbatim into
`settle_finished_run()` so the tests drive the real mapping.

Why the engine and not the manager's watcher:
1. The engine knows the cause; the manager sees only `Failed { error: String }`. A manager-side fix needs
   either string matching on error text or a blanket "stop requested ⇒ not Failed", which would also
   relabel genuine failures that finish after a pause (journal write errors, script errors, executor panic).
2. The journal decision is made in the engine. The `parallel()` `dropped_reply` terminal is written before
   the manager sees anything; a watcher remap would show `UserPaused` while every resume fails.
3. The engine fix also covers session shutdown, where there is no pause intent and no eager tracker state.
4. Matching `HostError::Cancelled` exactly means a lost reply under a stop resumes exactly as a host-answered
   cancel does; no new resume semantics.

The token is fired only by `pause()`, `cancel()`, `cancel_all_and_drain()` (and the watcher after the engine
has returned, which cannot affect it). The host's `cancel_token.cancel()` at `host_service.rs:612` is a
per-child token. So "stop signal fired" while the engine runs means "the user or the session stopped it".

Judgments to audit:
* **Correlation, not proof of cause.** A reply lost for an unrelated reason after the stop fired is also
  reported `Cancelled`. Accepted: the user asked the run to stop; effect-bearing calls keep their dispatch
  intent, so resume still reports the outcome unknown rather than replaying blindly (audit LOW 2).
* **Send refusals included.** The finding names lost replies; a refused send under a stop is the same
  teardown and had the same `Failed` result, so it maps the same way (mutant `send`).
* **Unchanged, still `Failed` under a stop:** a host answer of `Unsupported`/`Failed`, journal errors, and
  replayed `dropped_reply`/unknown terminals already in the journal. These are not transport losses.

## 5. The LOW: weak senders

tokio 1.52.3 (`~/.cargo/registry/.../tokio-1.52.3/src/sync/mpsc`): `WeakUnboundedSender { chan: Arc<Chan> }`
(`unbounded.rs:45`); `Tx::drop` of the last strong sender only closes the list and wakes the receiver
(`chan.rs:225-237`); only `Chan::drop` pops what is left (`chan.rs:555-568`), and `Chan` drops with its
last `Arc`, which weak senders hold. So a stranded request lives until the last strong **and** weak sender
is gone. Search of the workspace (`grep -rn "downgrade()\|WeakUnboundedSender" crates --include=*.rs`):
the only weak senders in production are on `PersistenceMsg` channels (`session/persistence.rs:1300`,
`execution_state.rs:630`, `summary.rs`) and unrelated crates (`fuigo-tools` terminal actor,
`fuigo-computer-hub-sdk`); the host channel (`WorkflowHostRequest`) is created only at
`manager.rs:277` and `validate.rs:71` and never downgraded. The only weak host senders are the test
stranding hosts, which hold their simulated stranded request outside the channel, so they are not affected.
R019 §1.1, §1.2 and §9 are corrected accordingly (`6573717e`, rebased from `191f8e51`).

## 10. Proposals (outside this packet)

* **`journal.rs`: a journal file that was never written should load as a fresh v2 journal**, not as a
  restored legacy one, so a run paused or stopped before its first journaled step can resume (audit
  MEDIUM). Today such a resume fails with `LegacyBoundary` on its first dispatch. Needs its own tests
  (missing file vs. empty legacy file vs. torn header).
* R019 §8's host-side proposal (keep answering `Cancelled` until the engine drops its sender) is no longer
  needed for outcome correctness after P38-F; it would still narrow the window.
* Integrate the manager-test bounded teardown (`e713e086`) so a future wedge fails by name.
