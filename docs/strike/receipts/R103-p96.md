## What is NOT met / open
- **Sessions that broke before this release: healed since the s28 restack, when their `.corrupt` copy is still
  there** (see "Restack s28"; Sean approved the second trigger through the coordinator). Without that copy (deleted
  by hand, or never written because the copy failed) such a session still needs `fuigo/session/repair`.
- **"A clean session is byte-identical" holds for the repair, not for the whole load.** The repair does not touch a
  clean session (unit test, byte comparison, no backup). The load as a whole still rewrites every loaded session's file
  at spawn, as it did before; for the fixture the bytes come out identical (integration scenario 2), for a
  legacy-format file they would not. Pre-existing, Astra r1 MEDIUM 4, not changed.
- **A failed backup blocks every later rewrite of the file in that process, not only the repair.** That is what "do
  not rewrite the disk" needs, because the spawn snapshot would otherwise write the repaired history seconds later.
  Consequence while the backup keeps failing (disk full, read-only volume): a compaction, rewind or image strip in that
  run is not saved to `chat_history.jsonl`; appends continue. The backup is retried on each attempt.
- **The backup is one-time (first copy wins), as approved.** A second tear months later is repaired without a new
  copy; the notice then says an earlier backup was kept and nothing was copied.
- The backup is published with a hard link. A filesystem without hard links makes the backup fail, so the repair
  stays in memory there.
- A session on a filesystem without advisory locks, or one held by any live actor, is not repaired at load.
- The notice is its own update since the s28 restack, `FuigoSessionUpdate::HistoryRepaired { message }` (it was an
  `ImageDropped` note, which the pager logged as "Image dropped: ..."). A client older than this release shows nothing.
- Not covered: subagent resume (`load_chat_history_from_dir`) and forks of a torn session (`copy.rs`) read through
  the same lenient reader and are not repaired.
- The harness showed two slow runs (123 s instead of about 5 s, logs red2 and the first mut-M2) in which scenario 6
  also failed. Cause of the scenario failure: a race in my fixture (the live actor's startup snapshot landing after
  the test damaged the file), fixed in b5e700ba; 5 of 5 runs after the fix pass. The 2 x 60 s stall itself is not
  explained (instrumented reruns did not reproduce it).

## What changed
- `session/storage/jsonl/load_repair.rs` (new): `JsonlStorageAdapter::repair_after_corrupt_load`, called from
  `persistence::load_light`. It runs `compaction_utils::repair_history` only when the reader skipped at least one line
  AND the repair changes the history, only under the exclusive turn-owner lock, and on a fresh read made under it.
- Backup `chat_history.jsonl.pre-repair`: staged under a unique name, flushed, published with a hard link (never
  replaces), directory entry flushed. Only a regular file counts as an existing backup.
- Backup failed: no rewrite; the repaired history is used in memory; the file is marked and
  `load_repair::rewrite_gate` refuses every rewrite of it (`replace_chat_history`, `persist_chat_history_jsonl_sync`)
  until the backup exists.
- Notice: `PersistedInfo::history_repair_notice` -> `SessionCommand::NotifyHistoryRepaired` -> one system note with
  the counts and the backup path, saved in the transcript; plus `tracing::warn!`.
- `read_chat_history_counting_sync` returns the skipped-line count; `PersistedDataLight::skipped_chat_lines`.

## Release note (Sean)
If a crash cuts a line of a session's saved history, Fuigo now repairs the history the next time the session is
opened, keeps the original file as `chat_history.jsonl.pre-repair`, and shows one note saying what it removed; before,
every request in such a session failed until `fuigo/session/repair` was run by hand. Sessions that broke before this
release are repaired too, the next time they are opened, as long as their `chat_history.jsonl.corrupt` file is still
there (without it, `fuigo/session/repair` is still needed).

### NOT met / open

### What is NOT met / open
- **While the backup is owed, rewind (conversation modes) and compaction are refused, manual and automatic.** An
  automatic compaction shows its failure note each time it triggers, so a session near its context limit can stop
  being able to continue until the backup can be made (free space, or clear what sits at `.pre-repair`). Each ask
  retries the backup, so the refusal ends by itself once the copy succeeds. A files-only rewind is not refused.
- Other fire-and-forget rewrites (system prompt swap on model or mode switch, memory reminder injection, goal
  directive removal) are still only logged when the gate refuses them, as before pass 3. They do not drop turns the
  model would get back; a goal directive removed in memory can come back on resume. Not changed; listed here.
- Image strip is not refused up front: it already has a disk acknowledgement and reports `WriteFailed` (Astra r2 found
  no false success there). Memory loses the images, the file keeps them; on resume they are stripped again if needed.
- Known, not changed (pre-existing, Astra r2): **M4** the spawn snapshot (`.sync.tmp` + rename) has no file or
  directory flush; **M5** the reader's `.corrupt` copy uses `exists()` then `copy`, outside the lock, and can overwrite
  earlier evidence or follow a dangling symlink.
- Not run: full `fuigo-shell` and `fuigo-pager` suites, the two-sided gate, macOS, Windows.

Why H2 refuses up front instead of acknowledging the rewrite: the rewrite is sent by the chat-state actor
(`fuigo-chat-state`, outside this packet) after memory has already changed, and an ack would have to roll memory,
the RewindMarker and compaction bookkeeping back on failure. The gate is the only P96 cause of a refused rewrite, it is
per file and process, it only opens (nothing closes it while the session's actor holds the shared lock, because a
repair needs the exclusive one), and asking it retries the backup. So "ask before changing anything" is exact: once
the check passes, the later rewrite passes the same gate. Memory, transcript and disk then stay as they were.
Ordinary I/O failures of those rewrites (disk full mid-write) remain logged only, as before P96.

Test seams (`#[cfg(test)]` only, `load_repair::seams`): hold the next `write_bytes_atomic` of a path; fail the
backup's directory flush. The held write goes on when the test's sender is dropped, so a failing test cannot hang.
