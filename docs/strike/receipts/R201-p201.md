# R201 - P201: hosted-tool rows in a failed, retried attempt

## Problem
P188 tells ACP clients to discard a failed attempt's output (`retry_state` `retrying` with `discardEmitted`), keyed on
`UnacceptedOutput.emitted`. Hosted tools (`web_search`, `x_search`, `code_interpreter`) reach the client as
`tool_call` `in_progress` from `SamplingEvent::BackendToolCallStarted` (`acp_session_impl/sampling_events.rs`), which
never marked the attempt as emitted, so (1) a retry after an attempt whose only output was a hosted row carried no
`discardEmitted`, and (2) the row stayed `in_progress` forever.

## Change
- `session/unaccepted_output.rs`: tracks open hosted rows (`note_hosted_started`, `note_hosted_finished`,
  `take_open_hosted`); both marks also set `emitted`. `accept()` clears them.
- `sampling_events.rs`: Started marks, Completed finishes the row (a Completed with no Started still marks emitted: the client saw an update).
- `updates.rs` (`send_fuigo_notification_with_extra_meta`, the single place every resend path funnels through, incl.
  auto-recovery): before stamping a `Retrying` notice, send `tool_call_update` status `failed` (title kept) for each
  still-open row, then the notice. Rows are taken, so each is closed once; one notice per failed attempt.
- Status choice: `failed`. The ACP `ToolCallStatus` has only pending/in_progress/completed/failed, and P188 sends no
  per-row status at all for ordinary rows (ordinary tool calls only run after an attempt is accepted, so a dead attempt
  has none); `failed` is the only terminal non-success status that exists. No new field or method on the wire.

## retry_only_before_output decision
No change needed. `sampler_retry_only_before_output` is enforced in the sampler, whose `output_observed` flag
(`fuigo-sampler/src/actor/request_task.rs` ~1038) is already set by `BackendToolCallStarted` and `BackendToolCallCompleted`,
so a started hosted tool already counts as output and such attempts are not resent. (Read from code, not separately tested.)

## Tests (`session/acp_session_tests/turn/stream_retry_discard_tests.rs`, mock Responses server)
No existing expectation changed. New: `p201_web_search_row_...`, `p201_code_interpreter_row_...`, `p201_x_search_row_...`
(row, terminal `failed`, ONE notice with `discardEmitted`, resend's row, answer once, nothing spinning),
`p201_hosted_row_and_text_in_a_failed_attempt_...` (one notice, rows closed), `p201_a_failed_attempt_with_no_event_...`
(no discard, no tool rows; guard, passes on red), `p201_a_hosted_row_that_completed_...` (no second terminal update, notice still discards).

## User-visible (release notes)
When a model request fails after a web search, X search or code run has started and is retried, the half-finished
search row no longer stays spinning and is no longer shown twice: it is marked failed and cleared with the rest of the failed attempt.

## Known limits
A hosted row of an attempt that fails terminally (no retry) is still not closed; out of scope. Proposal: close open rows on terminal failure too.

## Round 2 (Grok r1: NOT-LAND-OK, one HIGH, three LOW)

### Mechanism chosen: (b) reorder, and why
Option (a) (consumers ignore a `failed` update without output) is sound on today's producer (a genuine hosted failure
always has `raw_output`: `backend_tool_call_status` yields `Failed` only from a present payload), but it is a convention on an
absent field, and a future producer of a `failed` row with no payload would silently be dropped. (b) needs no new rule: the
consumers already treat an update for a row the discard dropped as void (P188: headless `discarded_tool_ids`; rebuild now the
same), and an orphan update in the pager (`tracker.rs` ~1561) is a no-op.

Wire order now: hosted row `in_progress` ... `retry_state` `retrying` (`discardEmitted`, `streamStartMs`) ... `tool_call_update`
`failed` (title only) for each still-open row ... the resend's rows. Before round 1 fix: row, `failed`, notice. For an external
client that ignores `discardEmitted` (MurageMobile) the row still ends `failed`; it just does so right after the notice.

### Change
- `updates.rs`: `take_open_hosted` is read before the notice; the closing updates are sent by `close_hosted_rows` after the
  notice is queued (both the queued and the direct-delivery branch).
- `storage/mod.rs` (`ChatReducer`): hosted rows (`tool_call` `_meta.backend`) are remembered with their `streamStartMs`; a
  `discardEmitted` naming that stream drops the rows from the pending assistant item (fixes the `agent_tool_calls` that stuck
  to the next assistant item) and a later update for them commits nothing.
- `headless/reducer/messages/mod.rs` (`discard_response`): a deferred hosted `web_search` is dropped and marked discarded too
  (it was not in `blocks`, so before this its closing update would have been folded into the NEXT frame). The other hosted tools
  were already handled by P188's `discarded_tool_ids`.
- LOW ordering (`sampling_events.rs`): the row is registered with `note_hosted_started` after its `in_progress` update is
  queued, so a close can never be queued ahead of its own row. Residual: if the 5 s drain barrier times out inside that await, the
  row is queued after the notice and spins until the next retry notice or accept (same as late text, the not-in-scope class). No
  deterministic test: it needs a cancellation inside one await; explained, not tested.
- LOW (`unaccepted_output.rs`): `note_hosted_finished` no longer sets `emitted`; a row that was shown already set it at its start.
- LOW clippy: `clone` on the `Copy` `ToolCallStatus` in `stream_retry_discard_tests.rs` removed.

### Known limits (kept)
- A hosted row of an attempt that fails with NO retry, a cancel, or a compaction resubmit stays `in_progress` (pre-existing, as text).
- A hosted row that COMPLETED inside an attempt that then fails is already committed by the rebuild at its completion (the
  assistant item is flushed before the discard); only the not-yet-completed rows and the closing update are handled here. Proposal:
  defer a backend row's result in the rebuild until its response is accepted.
- The pager keeps the (now `failed`) hosted row in scrollback; `discard_current_response` removes text and thinking rows only.
