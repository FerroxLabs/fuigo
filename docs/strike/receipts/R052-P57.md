## 1. What was wrong and what changed

### P-4 -- two distinct root causes, both under load
1. `app::edit_highlight_worker::tests::double_submit_prunes_pending_after_latest` (the one the brief named).
   The test waited `2 s` for the worker's first job. That first job builds the process-wide syntect set (`get_syntect()`, a `OnceLock`)
   in a debug build, and under load that alone exceeds 2 s: `edit HL did not settle` at `edit_highlight_worker.rs:644`.
   It was never the coalescing logic. Fix (test only): pin the theme (`pin_theme()`), build the syntect set before the wait, and make the
   bound a 60 s hang guard instead of a latency budget. No retry, no assertion loosened.
2. `app::edit_highlight_worker::tests::run_job_succeeds_on_temp_file` (P46's other P-4 name) fails with `left: TokyoNight, right: FuigoNight`
   (P46 logs `/root/fuigo-builds/p46/logs/f1-parent-bf85-stress-1.log`, `f1-parent-full-11.log`). This is a **product** race in
   `fuigo-pager-render/src/theme/cache.rs`: `current_kind()` seeds lazily from disk, and it did `store_kind(disk)` unconditionally after the
   slow disk read, so it overwrote a `set()` that landed in between. A test that had just pinned `FuigoNight` then read the configured theme.
   Fix: `seed_from()` applies the disk value only if no `set()` marked the cache loaded, under `SEED_LOCK` shared with `set()`.
   Two unit tests pin it (`seed_does_not_clobber_a_set_that_lands_during_the_disk_read`, `seed_applies_the_disk_value_when_nothing_was_set`).

### P-6 -- it is a product defect; the child now gets a deterministic notice
`ensure_mcp_tools_initialized()` (`fuigo-shell/src/session/acp_session_impl/mcp.rs`) called `finish_init()` BEFORE
`register_shared_client_tools()` (a `tools/list` round trip per inherited client) when a child inherits its parent's pool and declares no servers
of its own. `is_initialized()` was therefore true while the inherited tools, the snapshot and the "MCP server connected" reminder did not exist
yet, and the Progressive strategy never waits. Whether the model was told depended on whether the registration beat the first reminder injection.
Decision: the child must be told, deterministically, in its first request. Fix:
- both empty-config branches now register the shared tools before `finish_init()`;
- `await_inherited_mcp_registration()` (new, called in `turn.rs` before `maybe_inject_mcp_reminder`) observes `mcp_state` (poll 10 ms, bounded 10 s,
  only when shared clients exist and the session has no configs of its own). It only observes: init stays owned by the startup task, so a turn cancel
  or the bound expiring cannot strand init (Astra r1 HIGH, closed);
- the stale-generation branch no longer calls `cancel_init()` (Astra r1 MEDIUM, closed; the config-update paths already reset progress when they bump the generation).

### P-7 -- insta wrote `.snap.new` into the source tree
Cause (reproduced): with no cargo on `PATH` (a test binary run directly) insta's `cargo metadata` workspace lookup fails
("cargo metadata failed in .../fuigo-pager: No such file or directory ... will use manifest directory as fallback"), it uses the crate dir as the workspace,
misses every committed snapshot and writes `crates/codegen/fuigo-pager/crates/codegen/fuigo-pager/src/.../*.snap.new`.
Fix: `.cargo/config.toml` `[env] INSTA_WORKSPACE_ROOT = { value = ".", relative = true }` bakes the repository root into every test binary at compile time,
and `.config/insta.yaml` sets `behavior.update: "no"` as the second line of defence (a mismatch fails with its diff and writes nothing).
Two tests in `fuigo-pager/src/lib.rs` (`insta_source_tree_tests`) pin both.

Files changed: `.cargo/config.toml`, `.config/insta.yaml` (new), `fuigo-pager-render/src/theme/cache.rs`, `fuigo-pager/src/app/edit_highlight_worker.rs`,
`fuigo-pager/src/lib.rs`, `fuigo-shell/src/session/acp_session_impl/{mcp.rs,turn.rs}`, `fuigo-shell/tests/inherited_mcp_pool_child_acp.rs`,
