## `effective_peer_mode()`: built in part B (the section below is part A's reason it was stopped)
`acceptEdits` cannot be read at run time, so no accessor was written. What is readable:
- `plan`: yes, `plan_mode.lock().is_active()` (`fuigo-shell/.../hook_dispatch.rs:217`).
- yolo / allow-all: yes, `PermissionHandle::is_yolo_mode` (`fuigo-workspace/src/permission/manager/mod.rs:1121`; `AllowAll` is always true).
- `auto`: yes, `is_auto_mode` (`manager/mod.rs:1128`), seeded from `PromptPolicy::Auto` at spawn (`:1683`).
- `dontAsk`: stored only as the actor-task local `prompt_policy` (`manager/mod.rs:1736`, copied from `PermissionConfig.prompt_policy`); the handle (`:112-133`) has no field for it. It is readable with a small new immutable field on `PermissionHandle::Actor` (3 test constructors in `fuigo-shell/src/session/acp_session.rs:1948,2015,2094` and one at `manager/mod.rs:3002`/`:4124` would change).
- `acceptEdits`: NOT readable. `DefaultPermissionMode::AcceptEdits` (`rules.rs:38-42`) is turned into a synthetic `Allow Edit` rule by `resolution.rs:58-65` and the mode is then discarded; the result is indistinguishable from a user-written `Allow Edit` rule. `PermissionConfig` (`types.rs:538`) keeps only `rules`, `prompt_policy`, `default_mode_configured`.
- `bypassPermissions` via `permissions.defaultMode`: also NOT yolo. `rules.rs:43-46` / `resolution.rs:41-50` turn it into a catch-all `Allow Any` rule; `yolo_state` is not set from it, so design text "bypassPermissions = yolo or allow-all" misses this path.
- `PromptPolicy::Allow` (set by `startupHints.permissionMode=alwaysAllow`, `resolution.rs:345`) auto-approves every prompt (`manager/mod.rs:2652`) and is in none of the design's six modes.
- Fix needs a design decision: record the resolved `DefaultPermissionMode` (and the Allow policy) on `PermissionConfig`/the handle at resolution time, then `effective_peer_mode` becomes exact. Packet 6 touches the same file.

## Design vs code / choices
- Address has three parts (incarnation), per design section 1; the packet brief listed two.
- Tool field is `notify_when_idle` (section 2, the Claude Code reference name). S9.1's `watch` is the same thing (an idle watch on the target); the only name in the code is `notify_when_idle` (`fuigo-peer/src/tools.rs:24`), and `watch`/`Watching` survive only as the outcome and the 12 h expiry constant, not as an argument.
- Reject reasons beyond the design's named ones (`PolicyRefused`, `TooLarge`, `Ambiguous`) are my additions from S4.2/S5.1/section 2 row 7. `held` has no reason for plain policy `hold`; the design's list is mode_mismatch, loop_guard, sender_denied, integrity.
- `[ref]` shape (8 chars, 12 on collision, alphanumeric or `-`) is my reading; the design does not fix the character set.
- Session ids are limited to ASCII alphanumeric, `-`, `_`, 128 chars (design silent).

## Part B: effective_peer_mode (built)
Decision applied: the resolved source mode is recorded at resolution and read from there. No rule changes.
- Recorded: `PermissionConfig.resolved_base: ResolvedBaseMode {Default, AcceptEdits, BypassPermissions}` (`permission/types.rs`, `#[serde(skip)]`), set in `resolution.rs` at three sites: managed `defaultMode` (`resolve_permissions_with_provenance_inner`, only when `synthetic_rules_for_default_mode` did not report `blocked`), user/project settings (`resolve_claude_settings_inner` tail, `Default` when `bypass_blocked`), and the merge that takes the settings value when managed owns none. `DefaultPermissionMode::resolved_base()` is in `rules.rs`.
- Handle: `PermissionHandle::Actor.mode_view: ModeView {base, session_edit_grant}` (`manager/mod.rs`), `base` fixed at spawn from `base_mode_of(config)`; `PermissionHandle::effective_mode()` reads the live atomics on every call. Session: `SessionActor::effective_peer_mode()` (`hook_dispatch.rs`, next to `permission_mode_label`) = `Plan` if `plan_mode.lock().is_active()`, else `permissions.effective_mode()`.
- Enum `EffectivePermissionMode` (`types.rs`) and what each is read from:
  - `Plan`: tracker state `Active` (`plan_mode.rs:137`). `ExitPending` is NOT plan (same as the existing label).
  - `Yolo`: `yolo_state` (set by `initial_yolo` at spawn from the CLI/session flag, `set_yolo_mode`; clamped by the pin). Beats everything, including a configured `dontAsk` (see the warn at spawn).
  - `AllowAll`: the `PermissionHandle::AllowAll` variant.
  - `Auto`: `auto_state` (seeded from `PromptPolicy::Auto`, `set_auto_mode`). Config `auto` with the flag turned off at run time reports `Default`, as the actor then prompts.
  - `DontAsk`: `prompt_policy == Deny`. `AlwaysAllow`: `prompt_policy == Allow` (only `apply_permission_mode_hint`, `resolution.rs:345`).
  - `AcceptEdits` / `BypassPermissions`: `resolved_base`. `defaultMode=bypassPermissions` is its own variant (a catch-all rule, yolo not set).
  - `Default`: everything else. `defaultMode=plan` and unknown values resolve to `Default` (nothing in the code starts plan mode from the setting). A user-written `Allow Edit` / `Allow Any` rule or CLI `--allow` stays `Default`.
  - `SessionEditGrant`, `DontAskEditGrant`: the "allow edits for this session" answer (`allow_edits_for_session`, actor-local, now mirrored in `mode_view.session_edit_grant`, set at the `AllowEditsForSession` arm and cleared on `ResetState`). Edits pass without a prompt, so it must not equal `Default` / `DontAsk`. Under yolo/auto/bypass/acceptEdits/alwaysAllow it changes nothing and is not reported.
- Merged: nothing. `Yolo` and `AllowAll` are kept apart: both are always-approve in `is_yolo_mode`, but they are different code paths and I did not prove them identical. Merging later is a one-line change if the hold rule wants it.
- Run-time change sites (all seen, because the function reads the live state each call): `PermissionHandle::set_yolo_mode` / actor `SetYoloMode` (store at both), `set_auto_mode` / `SetAutoMode`, the `AllowEditsForSession` arm, `ResetState`, plan tracker transitions (`enter_pending`, `activate*`, `deactivate_approved`, `user_exit`, `complete_deferred_exit`, `reset_after_compaction`, `from_snapshot`) all observed through `is_active()`, session commands `SetYoloMode` / `SetAutoMode` (`run_loop.rs:1203-1225`), `slash_exec.rs:22`, startup `permissions.set_auto_mode(true)` (`spawn.rs:521`).
- Tests (red then green): `permission::resolution::tests::base_mode_table_settings_default_mode`, `base_mode_table_managed_default_mode`, `base_mode_bypass_blocked_by_pin_is_default`, `base_mode_startup_hint_always_allow`, `user_allow_edit_rule_is_default_not_accept_edits`; `permission::manager::tests::effective_mode_table_over_config_sources`, `effective_mode_follows_runtime_changes`; shell `permission_auto_mode_tests::effective_peer_mode_sees_plan_and_runtime_toggles`. Red lines kept: first run had two failures, `effective_mode_follows_runtime_changes` (`left: SessionEditGrant, right: Default`, test waited too briefly for the actor's disk write before clearing the grant) and `base_mode_table_managed_default_mode` (env-write guard `rerun_in_own_process` missing); both fixed in the tests.
