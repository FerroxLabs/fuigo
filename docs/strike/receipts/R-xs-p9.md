## Decided differently from the design / not done
- `send_message` is NOT auto-allowed (design row 3a): it is `AccessKind::Tool`, so it prompts unless a rule allows it, and fails under `dontAsk`. Building the auto-allow touches the permission engine (S6 guard ordering); needs a decision.
- Field is `message` (packet-1 type), not `body`; `notify_when_idle` is not in the tool schema (watch is a later packet).
- `/peers held` and `/peers release` do not exist at this base (only `clear-influence`), so nothing to keep.
- `refuse_peer_message` is registered with the flag on and always listed (a dynamic tool list would change the prompt mid-session); it errors until a peer message was received. `PeerRefuseHandle` is not yet fed by the shell.
- Envelope stamping on a recent denial is the packet 7 constructor's job and its tests; no new test here because the production host (8e) is the caller.
- No ACP presentation/telemetry arms for the new input (falls to the wildcard "Tool call").
- `list_agents` pages at most 4 (256 rows).
- The `/peers` slash description and hint are unchanged (they mention only `clear-influence`).

## Round 3 follow-up (relay rule)

Owner decision 57 (P). The rule, in five lines:
1. Nothing parses or rewrites ACP traffic. `observe_ingress`, the `_meta` driver tag, the per-session driver book, the `session/new` stamp and the two pump hooks are removed; the leader pumps in `src/agent/app.rs` forward lines byte for byte as before round 3.
2. One process-level fact, `peer_inbox::driver::remote_attached()` (counter of attach guards; false and never read with the flag off).
3. While it is true: `PeerGate::is_opted_in` is false for every session (not listed, a send answers `unavailable`), `admission_for` opts nothing in for a leader, and `submit_peer_message` answers `unavailable` first.
4. `peer_inbox_status()` is `Unavailable(RemoteClientAttached)` ("peer messaging is unavailable: a remote client is connected to this Fuigo"); `list` and `send` from a session of this process are refused with that text.
5. Fail closed; the pager (leader off), ACP stdio, headless and subagents are unchanged.

Where set and cleared: set in `src/agent/app.rs` `spawn_leader_relay`, right after `spawn_relay_connection` returns, at both install points (eager start and the on-demand task: `handle.hold_peer_attach(driver::attach_remote())`). Cleared when the guard held in `RelayHandle` (`src/agent/relay.rs`, `peer_attach`) is released: on `RelayHandle::stop()` and on drop (leader shutdown drains the slot).

Reading used: "the relay is installed for this leader", NOT "a remote party is connected". The relay session exposes no reliable connected/authenticated state, and once installed the relay socket receives every agent update. A leader with the relay active (eager `fuigo agent leader`, or an on-demand leader after a headless client registered) therefore has no peer messaging. A leader that never installs the relay (the normal pager-spawned leader) is unaffected.

Stated limit: "While a remote client is connected to a Fuigo leader, none of that leader's sessions can send or receive peer messages."

Tests: `peer_inbox::driver::tests::{a_leader_with_a_remote_client_attached_opts_nothing_in_the_pager_is_unchanged, the_fact_follows_the_guard_and_is_never_read_with_the_flag_off, a_remote_client_attached_closes_every_session_and_clearing_it_reopens (session registered before the attach; a local re-opt-in while attached does not reopen; only detach does), the_status_text_is_fixed, no_code_reads_or_writes_the_driver_meta_tag (no `fuigoDriver` in non-test src), the_leader_ingress_pumps_do_not_parse_acp_or_call_the_peer_inbox (source pin on the two pumps, and only arm/shutdown/attach peer_inbox calls in app.rs)}`; `peer_inbox::tool_host_tests::p9c_remote_attached::send_and_list_from_a_session_are_refused_with_the_typed_reason_while_attached`. The old driver-book tests were deleted with the code. The new tests use a thread-local stand-in for the process counter under `cfg(test)`, so parallel tests cannot see each other's fact. Most compile only against the new API, so they have no RED run on 3232dc75.

Not done: `PeerAdmissionConfig::relay_driven` is kept but UNUSED in production (always false; only old tests set it), marked in its doc comment. No test exercises `spawn_leader_relay` setting the fact end to end (it is pinned by source and by the guard tests). The attach is by installed relay, so an installed but idle relay also closes peer messaging.

## Close-out after the last focused audit (owner decision 57)

Three fixes, all behind `features.peer_messaging`:

1. Held and queued messages now honour the remote-attached fact. `Inner::inputs` (the one place admission inputs are built) adds `&& !remote_attached()` to `opted_in`, so the first decision, `decide_live`, the drain recheck and the start-of-turn recheck all see it. `release` answers `Unavailable` and leaves the message held (nothing is removed). `check_at_drain` turns every non-hold decision into a hold while attached, so an approved or queued row goes back to held instead of being dropped.    Tests (`session/peer_admission_tests.rs`): `remote_attached_a_held_message_cannot_be_released_and_stays_held`, `remote_attached_an_approved_row_returns_to_held_at_the_drain_recheck`, `remote_attached_a_queued_row_goes_back_to_held_at_the_turn_start_recheck`.

   Tests (`agent/relay.rs`): `peer_attach_is_held_until_the_relay_task_finishes_and_stop_alone_does_not_clear_it`, `peer_attach_handed_in_after_the_task_finished_is_dropped_at_once`, `dropping_the_handle_alone_keeps_the_fact_and_a_panicking_task_still_releases_it`.
