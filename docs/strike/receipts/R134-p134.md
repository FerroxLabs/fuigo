## Item 1, P120 (row 122): a refused fchmod no longer stops a session from being saved
- `fuigo-shell/src/session/storage/owner_only.rs`: `tighten()` is best effort. Any failure of the platform tightening (EPERM,
  ENOTSUP, EINVAL, anything else) is logged once per process and swallowed. Files are still CREATED 0600 (`mode(0o600)`).
  1.0.20 never changed a session file's mode, so there is no "other error that 1.0.20 failed on": all are non-fatal.
- `fuigo-session-events/src/log.rs`: same for the event log (`open_owner_only_with`); before, a refused `set_permissions`
  left the writer without a file and no events were recorded.
- Seams: `tighten_with(file, path, chmod, warned, warn)` for the unit test, and a thread-local `test_seam::FailChmod` that makes
  the platform call return EPERM, so the real `open`/`create`/`write`/`copy` entry points are exercised.

## Item 2, P117 (row 119): finding partly mistaken; the real residual fixed
- Verified at 15c21ddf: a valid stored access token IS already used while metadata is down. `stored_token_disk_gate`
  (`decide_http_auth_from_disk`, present since 1.0.1) builds an unhydrated manager from the stored credentials, and rmcp's
  `get_access_token` returns an unexpired token with no network call. Test `p134_stored_valid_token_is_used_...` passes at the
  parent (focus-red.log: 2 passed, 1 failed, the failure being the refresh-window assertion of the first test draft).
- Real residual: in non-interactive mode, a token inside rmcp's 30 s refresh window, or expired with a refresh token, plus a
  metadata fetch error or timeout, fell to the anonymous probe, and the server's 401 became `NeedsInteractiveLogin` (a wrong
  "log in again"). Fix (`servers.rs`): after the anonymous probe, an auth challenge yields the retryable `Unreachable` when
  `stored_login_awaits_metadata()` (stored refresh token, or unexpired access token). Anonymous acceptance still wins
  (`NoOauthSupport`); a login with neither refresh token nor live token still gets `NeedsInteractiveLogin`.
- Unchanged and still enforced: `oauth.rs ensure_oauth_ready` never hydrates without validated metadata, so rmcp never guesses
  `{base}/token` and no refresh token, code, secret or verifier is sent. The next attempt re-checks (test: metadata turns
  healthy, the next decision refreshes once against the validated token endpoint).
