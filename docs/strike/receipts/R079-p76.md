Base 917a2cb38e760368d66eec34bdc60e942bd521c1 (control 1, immediate parent). Tip: see `git log` (code tip 1563b7f1c21622a70272dd0c8b3cc4045ed86ae0; later commits are docs only).

## Root causes
1. `rtl_overlay_override_row_copies_whole_stored_text` (and sibling RTL tests): the bidi latch is process-global; any test that builds a scrollback/app view writes it from its bidi-off appearance config, so a concurrent write flipped it off mid-assertion. Fix: `scrollback/bidi_latch.rs` serializes config-driven latch writes against test holds (`hold_latch`), restores on unwind, same-thread re-entry safe; deterministic test `rtl_override_copy_survives_a_concurrent_appearance_write` observes the writer waiting at the lock instead of timing it.
2. `run_hook_passes_correct_env_via_thread`: the shell creates/truncates the redirect target before printf writes, so a poller that reads as soon as the file exists sees an empty file. Fix: test helper `publish_atomically` (write sibling file then `mv`); deterministic test `hook_output_is_visible_only_once_complete` (slow payload).

## (b) hook output observed only once complete: ADDED (test code only)
Changes in `hooks.rs` tests: P6063's inline wait loop is extracted verbatim (same predicate `contains("FUIGO_SESSION_ID=") && ends_with('\n')`, same three assertions, same 30 s hang guard; poll interval 50 ms -> 10 ms) into `wait_for_complete_output(out, complete)`; new test `wait_for_complete_output_does_not_return_an_opened_but_unwritten_file`. The payload `{ while [ ! -e RELEASE ]; do sleep 0.01; done; printf 'done\n'; } > OUT` is held back until the helper has been offered the opened-but-empty file (the predicate records seeing empty content), so the interleaving is forced, not timed. A `ReleaseOnDrop` guard releases the payload on any exit and waits (bounded 10 s) for its last line so no shell is orphaned; paths go through `sh_quote` (apostrophe-safe).
Mutant mutB (helper returns on file existence: `&& complete(&c)` removed), built on the s19 tip: the new test FAILS 3/3; the original `run_hook_passes_correct_env_via_thread` still PASSES 3/3 under mutB (it is only probabilistically sensitive), which is why the deterministic test is worth having.
