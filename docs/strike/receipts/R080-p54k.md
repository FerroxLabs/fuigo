### 1.1 In plain English: what changes for a user or customer at upgrade

Someone who installed Fuigo and signed in sees nothing: their requests go to FluxRouter, which gets the same account,
team and machine identifiers as before, so billing, usage, support look-ups by account, local sessions, forks, worktree
resume and share links all work exactly as they did. Murage and other ACP embedders see nothing either. The change is
felt only by a customer who pointed Fuigo at their **own** auxiliary servers (their own cli-chat-proxy session registry,
session-history backend, storage proxy, internal OTLP collector or Mixpanel project). From this release those servers
stop receiving the real account id, machine id, e-mail or host name in request bodies and get instead a stable
pseudonymous key per machine or account (or nothing). For them that means, **once**, at upgrade: every machine and
account shows up under a new key; their registry no longer learns the host name; their OTLP dashboards lose the user and
team columns; a Mixpanel project starts a fresh user profile per person. The key is deterministic and the recipe is
published, so an operator who holds the old ids can compute the new ones and migrate their rows before rolling out;
Mixpanel is the one place that cannot be bridged (bridging would send the real id). Nothing silently breaks: client
code never compares a raw id with a stored one, derivation cannot fail, and every refusal is logged. The release-note
sentences are in the research doc §6; they are the ones to ship.
