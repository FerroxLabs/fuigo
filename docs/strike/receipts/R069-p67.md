## Root cause: TEST-SIDE, not a product bug
`request_mermaid_render` samples `theme::cache::current_kind()` once and uses it for both the key and the job; it checks `has_pending` before the disk-hit path. No ordering bug.
The test seeds a PNG at the path derived from the process-global theme, then the click re-reads that global. A concurrent `set_theme` test between the two reads changes the key; the hit becomes a miss ("Rendering diagram..." toast). Failure message seen with the pin removed: `a disk hit runs the copy action immediately, got "Rendering diagram…"`.
Fix: hold `pin_theme()` (shared theme test lock) for the whole test; same pin on `mermaid_view_miss_dispatches_then_settles`, which has the same two-read shape. Added `mermaid_cache_path_depends_on_theme` (non-mutating, asserts distinct key and path per theme: the mechanism). Disk-hit test also probes the lock with `try_lock`: it must find it held.

## Scope of the claim (Astra R1/R2)
The race is removed among tests that cooperate on the shared theme lock. Not removed (proposals below): `scrollback/blocks/bg_task.rs:450` and `scrollback/text_selection.rs:3611` set the theme without the lock; theme-cache lazy init (`cache.rs:74`, `LOADED` reset by teardown) can publish a stale value after a pin.

## The forced-interleaving repro: honest account
A "fails before, passes after" repro that forces the interleaving would have to mutate the global theme mid-test. Astra R1 showed that perturbs siblings (and races unlocked writers), so I removed it. The mutant above plus `mermaid_cache_path_depends_on_theme` are the evidence instead; I did NOT deliver a parent-fails/tip-passes forced repro.
