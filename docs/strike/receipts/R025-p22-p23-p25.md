## 2. What changed and why

### P22 — a disk fault after a successful refresh no longer signs the user out

**Before:** the post-exchange `self.write(&records)?` failed, and the record kept `refresh_pending: true` plus the
rotated-away refresh token. The freshly issued tokens were dropped.

**Design chosen: retry, then keep the new credential in memory, fail-closed on disk.**
- **Retry.** The persist is retried twice (50 ms, 250 ms). That covers transient faults.
- **Disk side.** If the write still fails, the disk keeps the latch. After a failed directory fsync it may instead keep
  the renamed new record, which is not yet known to be durable. Either way the rotated-away token can never be presented:
  the latch refuses it, and a reverted rename falls back to the latch.
- **Memory side.** The new credential goes into a process stash keyed by (store root, provider, account). It is returned
  marked `SubscriptionAccess::is_unpersisted()`, with a `tracing::warn!`. `fuigo models` also prints a warning to stderr.
- **Later accesses.** Each one, under the cross-process lock, takes the stash out. It honours the stash only if the disk
  shows exactly what the stash supersedes:
  - the latched record it was rotated from, matched on the same refresh token **and** the same access token (so a later
    latch over an unrotated refresh token does not match); or
  - its own renamed-but-unconfirmed record.
  It then re-writes it. If that fails, the stash is put back and served only while it needs no refresh. It is never
  refreshed from memory.
- **Login and logout.** A fresh login drops the stash. `logout` clears it before and after taking the lock. Every refresh
  holds that lock for its whole take, re-persist and put-back window.
- **Residual.** If the process exits before the disk recovers, the stash is lost and the latch forces a re-login. That is
  the fail-closed outcome.

**Why not the alternatives:**
- Clearing the latch on write failure would leave a rotated-away token usable on disk.
- A non-atomic fallback write is explicitly forbidden by the existing code.
- Keeping the tokens in memory without re-checking the disk would let a later fresh login or a logout be overridden.

**Logout contract, stated precisely** (on `Stash` in `storage.rs`):
- A logout in this process that takes the lock ends this process's stash, even if its disk write then fails.
- A successful logout from any process ends every process's stash, because the superseded record is gone.
- A failed logout from another process changes nothing. That matches what a failed logout already meant for the record on disk.

Audit rounds 2 to 4 tried to make "a logout that cannot take the lock" also win. Every fence opened a new race, because
without the lock that logout cannot change the disk. That attempt was dropped, deliberately.

### P23 — local TLS/CA faults are reported as local configuration and name the file

New `SubscriptionError::LocalTls(detail)`:
- **Message.** "subscription local TLS/CA configuration error: …; no request was sent, and retrying will not help until it is fixed".
- **Detail.** It names the CA bundle file and the variable that selected it (`FUIGO_EXTRA_CA_BUNDLE` / `SSL_CERT_FILE`).
  The path is Debug-escaped, so it cannot inject terminal controls.
- **When it is raised:**
  1. building the subscription HTTPS client fails (`flow.rs` `TokenClient::new`, `inference.rs` `cli_models`); or
  2. a send fails with `rustls::Error::InvalidCertificate` anywhere in the error chain, while an extra bundle is
     configured.

  The loader skips an unreadable or certificate-free bundle and logs it, so case 2 is the realistic broken-bundle failure.
  With no bundle configured, a rejected certificate stays `Network`, so Fuigo never advises trusting another CA.
- **Classification.** `may_have_consumed_refresh_token()` is false for it: nothing was sent.
- **Sampling resolver.** It gets its own message instead of "run fuigo login".

Same commit, from the audit: `exchange_send_error` treats a token-exchange failure as `Network` only for `is_connect()`
(DNS, TCP, TLS handshake) or an egress denial. Any later transport failure is `AmbiguousExchange` and the latch holds.

### P25 — assert the listener drop, not a port re-bind

- **Mechanism.** `LoginAttempt`'s listener is a `CallbackListener`. Its `cfg(test)` `Drop` sets a flag, exposed as
  `listener_drop_probe()`. Outside `cfg(test)` it is a plain field, so production behaviour is unchanged.
- **Tests that used to re-bind a released port.** There are four. Each now asserts the probe is false before `finish`
  and true after it. The PKCE and manual-code tests also record the probe when the provider receives the exchange, which
  proves the listener was released before the exchange.
- **Same flake class, other fixtures.** The released-port fixtures (bind, drop, connect) are replaced by a
  bound-but-not-listening socket that keeps the port reserved. That includes the pre-existing
  `an_undelivered_refresh_does_not_force_a_relogin`; these fixture changes ride in the P23 commit.

## 7. Proposals (outside this lane's allowance)

- **P-A.** Treat exhausted HTTP/2 `REFUSED_STREAM` as never-processed (`Network`), so it does not force a re-login. This
  needs `h2` as a direct dependency to match `h2::Reason::REFUSED_STREAM`, which is a manifest and lockfile change.
- **P-B.** Make `cancelled_refresh_finishes_persistence` hold the provider's response behind a barrier until after
  `abort()`, so it proves persistence survives cancellation mid-exchange.
- **P-C.** `LoginAttempt::finish_with_code_input` maps a `JoinError` of the exchange task to `Network` ("not sent").
  That task may have sent the code exchange; `AmbiguousExchange` or a dedicated variant would be honest. Nothing is
  latched there, so the impact is message accuracy only.
