## 1. Read first: what is NOT met, and the decisions

1. **Needs Sean's yes (user-visible behaviour change for operators of their own relay).** Release-note sentence:
   *"When Fuigo's relay is one you run yourself (not FluxRouter's), the relay now receives a stable per-relay pseudonymous
   id in place of this machine's id, and is no longer told who is signed in (e-mail, name, profile image, team and
   organisation ids and names, cloud-environment owner ids); a FluxRouter relay and the local client are unchanged."*
   Consequences Sean should weigh: a remote client that reaches the agent through such a relay sees no account name or
   e-mail in its account panel (`fuigo/auth/info` answers with roles and flags only), and the relay sees each machine once
   more as a new agent at upgrade (raw id before, pseudonym after; the recipe is P54-K's published one, so an operator can
   migrate their own rows).
2. **The defect is WIDER than the brief stated, and I fixed the wider one.** The brief named the machine id. The same
   bridge also forwarded who is signed in (§3 rows 4–8), and in leader mode the relay receives the responses to LOCAL
   clients too, so it learned the account without ever asking. I applied the P54 decision to those as the brief's item 2
   says ("for a non-FluxRouter relay, apply the P54 decision at the relay writer"), in **separate commits** so the
   account part can be dropped without touching the machine-id part: `148d9fb6` is the machine id alone; `86a7dc56` and
   the production half of `85109ded` are the account. **Coordinator / Sean decision:** keep both (recommended: the
   handshake already withholds `x-userid` from the same relay, P43), or the machine id only.
3. **NOT fixed, different trust class, pre-existing — credentials over the same bridge (Astra round 1: HIGH follow-up).**
   `fuigo/auth/getBearerToken` (`extensions/auth.rs:62`, `result.result.token`: the session token or a static key),
   `fuigo/getApiKey` (`extensions/auth.rs:70`, `result.result.key`: the `FUIGO_API_KEY` of the environment) and the
   cloud-environment `secrets[].value` (`sandbox_types.rs:542`, "values may be redacted" by the backend) are answered to
   whoever asks over ACP, and in leader mode a LOCAL client's answer is copied to the relay. A relay already holds the
   session bearer it was dialled with (P47 admits it), so the session token is not new to it; an environment API key and
   backend secrets are. That is credential delivery (P42 / P47), not identity disclosure; I did not touch it.
   **Coordinator decision: new packet** (proposal 1).
4. **NOT fixed, outside this packet — tearing down an agent within about two seconds of `initialize` aborts the
   process.** Found by my own bridge test (§9, runs `dev-b`, `diag`, `diag3`): dropping the `LocalSet` that owns a just
   initialised `MvpAgent` ends in glibc `tcache_thread_shutdown(): unaligned tcache chunk detected` (SIGABRT) at thread
   exit, 5 runs of 5; leaking the set, or dropping it 3 s later, does not. Production never tears the agent down (it lives
   as long as the process), so I know of no user-facing effect; it is a heap corruption all the same, and a trap for any
   test that initialises an agent and returns at once. Root cause not located (the start-up tasks hold `LocalRef`s whose
   contract is "the agent outlives its `LocalSet`"). My test leaves the set alive, as production does, and says so in a
   comment. **Coordinator decision: new packet** (proposal 2).
5. **Astra never returned a plain LAND for P81.** Round 1: DO-NOT-LAND (one HIGH, fixed). Round 2: LAND-WITH-FOLLOWUPS
   with three LOWs: two were test gaps, closed by `ffe97161` (tests only, after the round); one is a parser limitation I
   left in place and declare (§11). No verdict rule was written into either brief. §8 has both rounds.
6. **Replace-versus-omit for the machine id rests on an inference.** The relay server is not in this repository. I
   replaced the id (rather than omitting the field) because relay sync supplies an `agentId` in every `initialize` it
   answers (`relay/sync.rs:528`), which says the relay protocol keys an agent on that field. Astra: "a reasonable
   compatibility choice … the checkout does not prove the external relay requires it". If the relay does not key on it,
   omitting would disclose even less; say so and it is a one-line change with its mutant.

## 4. What changed (production)

**Rule.** P54's, unchanged: identity in a body goes to a FluxRouter-operated destination only; any other destination gets
the field omitted or, where it needs a stable key, P54's published `destination_pseudonym`. No second scheme.

1. **`fuigo-extra-ca/src/fluxrouter.rs`: `IdentityDisclosure::body_key_for_websocket(destination, value)`.** The WebSocket
   variant of `body_key_for`, which R082 said was missing: the value itself when `for_websocket_destination` permits
   (`wss` to the FluxRouter API host), otherwise `destination_pseudonym(destination, value)`. Same recipe, same domain
   tag; only "is this destination FluxRouter-operated" is asked by the `wss` rule instead of the `https` one. A new test
   pins it, with a vector computed independently by the published Python recipe
   (`wss://relay.example` + `5d1f0c2a-7a7a-4b4b-8c8c-0123456789ab` → `1aee0aad-2c8c-814c-a3bd-c47d513a2170`; Astra
   reproduced it).
2. **`fuigo-shell/src/agent/relay.rs`: the relay socket writer's filter** (P77's place and mechanism).
   - `RelayConfig::body_identity()` → `RelayBodyIdentity::for_relay(&self.ws_url, fuigo_telemetry::id::agent_id)`: the
     disclosure decision and the pseudonym's origin are both derived from the one URL `run_relay_loop` connects to, so they
     cannot come from two URLs. `run_websocket_session` takes it instead of P77's bare `IdentityDisclosure`.
     (`RelayConfig::identity_disclosure()` stays for relay sync.)
   - `relay_outbound_frame`: a FluxRouter-operated relay gets every frame untouched, as before. For any other relay, a
     frame is read only if it contains one of 14 quoted keys, and only a RESPONSE (a `result`, no `method`) is changed:
     `result._meta.agentId` is replaced **in place** by the pseudonym **when its string value equals this machine's id**
     (any other value, relay sync's session-scoped id included, is left alone); the account keys of §3 rows 4–8 are removed
     at exactly those places, whatever their value; P77's host-name removals are unchanged. Everything else is carried as
     raw text and written back byte for byte; requests and notifications are never rewritten; a frame that names one of
     the keys and is not a JSON object is not sent (fail closed), and the writer goes on to the next frame.
   - The machine id is read (`agent_id()`) only when a frame names `agentId`, and only for such a relay.
3. **`docs/destination-trust-policy.md`:** the P54 body table's ACP row said "the local ACP client over stdio"; it now has
   the bridged-relay row and names `fuigo agent serve`.

**Unchanged on the wire (the brief's "default install" condition).** A default install has no relay URL and opens no
relay. A FluxRouter relay: the first statement of the filter returns the original `String` (tests compare bytes, through
the real socket writer too). The local stdio / IPC client: the filter is in the relay socket's writer; the IPC copy is
the same unfiltered line (`app.rs:999`); the bridge test asserts the agent's own line still carries `agent_id()`, the
e-mail and the rest.

`agent/app.rs` and every producer (`acp_agent.rs`, `mvp_agent/mod.rs`, `extensions/auth.rs`) are untouched.

## 11. Unverified, and limits I declare

- **A real third-party relay.** The relay server is not in this repository. Whether it keys agents on `_meta.agentId`
  (§1 item 6), shows a machine twice after the upgrade, or needs the account fields for anything, cannot be seen here.
- **A real restart.** Continuity after a restart is inferred from a pure function of the relay origin and the persisted
  id; no test starts a second process.
- **The bridge loop in `app.rs` itself.** The bridge test reads the agent's stream the way `app.rs` does and uses the
  production decision and filter, and the socket tests drive the real writer; no test runs `run_headless` / `run_leader`
  against a relay.
- **Parser limits (Astra LOW, both rounds; P77's design):** a key spelled with JSON escapes (`"em\u0061il"`-style) is not
  seen by the literal pre-check; with duplicate keys in one object the last wins, and an earlier duplicate would pass.
  `serde_json` writes struct and map keys literally and a map cannot hold duplicates, so no producer in the tree emits
  either; an embedder that hand-writes such a frame into the agent's output could.
- **Backend JSON forwarded as is** (§3 row 16): `fuigo/auto-topup-rule` and backend error texts. A path-specific filter
  cannot cover a field a backend adds later.
- **The response is recognised by its shape, not its method** (JSON-RPC responses carry none, and in leader mode the relay
  sees answers to requests it never sent). Another response with `email` / `teamId` … directly under `result`, an object
  `_meta` / `meta` with `email` / `team_id` / `team_name`, or `environment(s)[…].environment.{userId, teamId}`, would lose
  those fields at such a relay. Both hunts found no such producer today.
- **A configured `FUIGO_AGENT_ID` equal to a relay-sync id** (`tui-<session>`) would be pseudonymised there too (Astra r1).
- **Load.** 14 substring scans per frame for a relay that is not FluxRouter-operated, a shallow parse only on a match; not
  measured.
- **Windows:** nothing here ran on Windows.
- **`ffe97161`** (one test, one guard count) was not put to Astra.
- **The abort of §1 item 4:** root cause not located.
- **`final-gate.sh --network none`** was not run (the coordinator's stacked re-proof). The bridge test binds loopback only

## 12. `fuigo agent serve`: what its remote client receives, and a recommendation (proposal, nothing changed)

**What it is.** `agent/server.rs`: `fuigo agent serve` binds a TCP listener (`:616`; the doc example is `0.0.0.0:9000`),
serves plain `ws://<bind>/ws` (`:617` — there is no TLS in this path), and admits a peer that presents the shared secret
as `Authorization: Bearer <secret>` or as the query parameter `?server-key=<secret>` (`validate_auth`, `:104`). Every line
the agent writes is sent to that peer unfiltered (`:428`).

**What an admitted remote client receives:** exactly what a local stdio client receives — the `initialize` response with
the raw machine id (`agentId`), `agentInstanceId`, the OS `hostname` and the working directory; who is signed in
(`authenticate`, `fuigo/auth/info`, …); the account's other machines' host names in `fuigo/session/list`; and, on request,
the credentials of §1 item 3.

**Should the P54 rule apply?** My recommendation: **no, not as a destination rule — and yes to two smaller things.**

- P54 decides by *who operates the destination Fuigo dials*. Here Fuigo dials nothing: the user starts a server and gives
  a secret to their own client (`--remote ws://… --secret`). There is no URL to classify and no operator other than the
  user; a pseudonym "scoped to the origin" has no origin to be scoped to. The peer is the user's own TUI by design, i.e.
  the same party as the local client, which keeps everything. Withholding by default would blank the user's own session
  picker and account panel for no privacy gain against the party P54 is about. This is the boundary P77 used and Astra
  accepted in R082 round 8.
- **But say it in the policy**, as its own class, so it is a decision and not an omission: "inbound ACP server: the peer
  that presents the server secret is treated as the local client". I added one sentence to
  `docs/destination-trust-policy.md` pointing here; the class itself should be written by whoever owns that decision.
- **The real exposure is the transport, not the classification.** On a non-loopback bind the secret (in a header or, worse,
  in the URL), the machine id, the host name, the account and the whole conversation cross the network in clear text, and
  the secret proves possession, not that the peer is the user's TUI (Astra, R082 round 8). Recommended packet: refuse a
  non-loopback bind without TLS unless an explicit `--allow-insecure-bind` is given, stop accepting the secret in the query
  string (it lands in proxy and access logs), and compare the secret in constant time (`token == expected_secret` today).
- If Sean wants defence in depth beyond that: an opt-in `--withhold-identity` for `agent serve` that runs the same filter
  in always-withhold mode (host name and account omitted; the machine id omitted, since there is no origin to key a
  pseudonym on). Off by default.

## 13. Proposals (outside this packet)

1. **Credentials over ACP, and so over the relay** (§1 item 3): `fuigo/auth/getBearerToken`, `fuigo/getApiKey`, cloud
   environment `secrets[].value`. Decide who may be handed a credential over ACP (the local client only? never over a
   relay socket?) and enforce it at the same writer or at the handlers. P42 / P47 class.
2. **Agent teardown aborts within ~2 s of `initialize`** (§1 item 4): find the start-up task that touches the agent after
   it is freed (`LocalRef` in `spawn_announcements_refresh`, `spawn_heap_profile_monitor`, the 2 s announcements task in
   `initialize`), or cancel the start-up tasks before the agent is dropped. Reproduce with `diag3`'s "plain" variant.
3. **`fuigo agent serve`** (§12): the policy class, TLS / loopback, the secret in the query string, constant-time compare.
4. **The relay protocol's key.** If the relay does not need `_meta.agentId`, omit it instead of sending a pseudonym (§1
   item 6).
5. **A typed boundary instead of a shape filter.** The relay writer recognises responses by shape because the bridge
   forwards serialised lines. A bridge that carried the request's method beside each response (or separate channels for
   the relay and the IPC clients, so the relay stops receiving answers to local requests at all) would let the decision
   be made per method and would remove §11's shape caveat. Larger change, `agent/app.rs`.
6. **The body guard's vocabulary.** It does not list `firstName`, `lastName`, `teamName`, `organizationName`,
   `principalId`, `profileImageUrl` or `owner`; this packet found those by hand. Adding them would re-pin many files; worth
   one mechanical packet.
7. R082's proposals 3 (paths in registrations) and 6 (a keyed pseudonym) stand; its proposals 1 and 2 are closed (P71v2;
   this packet).
