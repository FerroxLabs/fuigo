## Peer messages and a held session
- Base already blocked the SELF case: `maybe_start_running_task` returns at `notification_drain.rs:124` (`is_self_quiesced`, which is true for Parking, Parked and Unparking), so `enqueue_admitted_peer_row` (`peer_admit.rs`) committed the row and reported `Admitted`/`Delivered` without starting a turn. The plan's claim that it "calls it unconditionally" was right, but the callee is gated. Pinned by tests (green on base too): `park_tests::a_peer_message_to_a_held_session_queues_starts_nothing_and_runs_at_unpark`, `the_peer_recheck_still_applies_when_the_held_row_starts_at_unpark` (opt-out while held: row not started), `with_peer_messaging_off_a_held_session_still_refuses_and_stores_nothing`.
- Unpark start: the `QuiesceRelease` handler (`run_loop.rs`, `kick: true`) calls `maybe_start_running_task`, which runs `demote_unqualified_peer_rows(front_only)` first (the packet-4 recheck). Test `the_unpark_release_starts_a_queued_peer_message` drives the real loop. The implicit-unpark release has `kick: false`; the prompt's own intake starts the queue (user first, then the peer row).
- NEW, PARKING: `promote_parent_agent_messages` (`prompt_queue.rs`, `hold_peers = quiesce::is_tree_holding(id)`) skips `PeerMessage` rows while the session or any ancestor is Parking/Parked, so a peer cannot extend the turn being waited on. Tests `a_parking_session_does_not_promote_a_peer_row_into_the_turn_it_waits_for` (with control: promoted again without a park), `a_child_of_a_parking_root_does_not_promote_a_peer_row`. Red (gate off), green. Parent-agent messages are unchanged.
- NEW, CHILD of a held root: `maybe_start_running_task` (`notification_drain.rs`, after the edit-hold check) refuses to start while the front row is a peer row and a strict ancestor is Parking/Parked (`quiesce::is_ancestor_holding`); `peer_admit.rs::wake_peer_rows_after_hold` spawns a local waiter on the park-change watch that starts the queue once the root is released (a child has no park entry of its own, so nothing else would wake it; the waiter ends if the session's `completion_tx` closes). Test `a_peer_message_to_a_child_of_a_held_root_waits_for_the_root` (no turn while held, started after unpark). Red, green.
- `features.peer_messaging` off: `submit_peer_message`/`enqueue_admitted_peer_row` refuse before any of this (tested). A session in no park: `is_tree_holding`/`is_ancestor_holding` are false (unit test), the waiter is not spawned.
- Limit: the root's own Unparking phase does not hold children (`holding` ignores Unparking); a child peer turn may start then, as the root's prompt is already being queued.

Item 6 design. A `session/prompt` whose `promptId` meta starts with `scheduler-fired-` (ticket verified or not) on a session with a park entry (parking, parked or unparking): the ticket is consumed (`cron_fire_tickets::redeem`), the prompt text (without the shell's `<system-reminder>` framing) is recorded in `quiesce::note_folded_fire`, and the prompt returns `Ok(PromptResponse(EndTurn))` at once: no `implicit_unpark`, no scheduler call, no `SessionCommand::Prompt`, no model call. Reply chosen: `end_turn`, the same normal reply the prompt path already returns for an early exit (allowlist case); the pager ends its cron turn and moves on, no retry. The note rides the `reminder` of the next release: implicit unpark (merged with the due-fire fold reminder), explicit unpark, or a withdrawn park; while the entry is Unparking it is sent as a reminder-only release of that op. Only `_fuigo/session/unpark` or a prompt that is not a scheduled fire un-parks.
