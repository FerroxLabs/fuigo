# R130 - P130: relay refusal emitted during session/new reaches the creating client

Base/parent 15c21ddf51302fd0ba3e6bea597a33cc7d6a9b8b. Tip 1a1598ba1a55c679c0f168df416f9ef800374ec8 (branch strike/p130).
Fixes Fable final-audit HIGH-1 (P125): `_fuigo/relay/refused {sessionId}` is emitted by the agent while it handles
`session/new` (agent_ops.rs `spawn_relay_refusal_notice`), before the response that names the session. The leader
(src/leader/server.rs) routes session notifications only to subscribers, so it dropped the notice as relay-owned.

## Commits
- 7844a725 red tests (real leader: tests/test_leader_stdio_integration.rs, 2 tests)
- eb6ec017 fix: the leader holds session-scoped refused/refusal_cleared notices (`pending_relay_notices`, cap 64,
  oldest evicted) and delivers them to the client that subscribes: after its session/new|load response, or on its
  first message carrying the session id.
- 09777b9c clippy: drop a useless `Arc<str>` conversion (gate pass 1 reported clippy new 1)
- 1a1598ba Astra R1 MEDIUM-1: drop a held notice when the first message is a session attach (load/resume), because the
  agent re-checks trust and re-emits a fresh notice; + test `p130_stale_held_refusal_is_not_replayed_on_session_load`

Design choice: hold-and-deliver rather than route to the originating connection, because the agent notification
carries no request id; the leader only learns the owner from the response (or the client's first message).
Other paths: the leader-bridge refusal (`relay_refusal_board`) broadcasts to attached clients and tells new ones on
registration - no race. No agent-side `refusal_cleared` emitter exists.
