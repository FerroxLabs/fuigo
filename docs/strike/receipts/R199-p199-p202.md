## Changes
- `.cargo/config.toml`: aarch64-unknown-linux-gnu `target-cpu=neoverse-v2` -> `target-cpu=generic` (ARMv8.0-A).
  `+lse` left out. N1 (Graviton2, Altra, Hetzner CAX) and Ampere A1 are ARMv8.2 and have LSE (from architecture docs, not run here). A core without LSE (Cortex-A53/A72, Raspberry Pi 4) would SIGILL on the first CAS/LDADD, because `+lse` removes the LL/SC fallback. The generic build still has 45 LSE instructions, all in Rust's outline-atomics helpers behind a runtime check.
- `.github/workflows/release.yml`: Linux jobs build with `scripts/release/build-linux-glibc228.sh <target>` (docker run of a manylinux_2_28 image pinned by digest, on the same native runner), macOS/Windows keep the old Build step (`if: runner.os != 'Linux'`). New step "Linux floor check" runs the self-test and the check on the built binary. rust-cache key gets `-glibc228` on Linux (a cache restored from ubuntu-24.04 would hold glibc-2.39 build-script binaries that cannot run in the container). YAML parses (`yaml.safe_load` ok).
- `scripts/release/check-linux-floor.sh` (+ `--self-test`), `build-linux-glibc228.sh`, `cross-aarch64-glibc228-proof.sh` (proof artefact only, not used by CI).
- Limits chosen: GLIBC <= 2.28, GLIBCXX <= 3.4.25, CXXABI <= 1.3.11 (GCC 8 era: RHEL 8, Debian 10). The binaries need no GLIBCXX/CXXABI at all.

## Approach comparison
- Chosen: native runner + manylinux_2_28 container. Real distro compiler and libc, same native design as the workflow header, C deps (aws-lc-sys via cmake, zstd-sys, libz-sys, mimalloc, jemalloc, ring) build exactly as before. Cost: a container image to pin.
- cargo-zigbuild (`--target ...gnu.2.28`): works for many crates, but is a cross toolchain, which the workflow header rejects; aws-lc-sys/cmake under zig cc is the usual breakage, and zig + zigbuild are two more pins. Not tried.
- musl: static, no glibc floor at all, but changes malloc/DNS/dlopen behaviour for a shipped product and the npm packages are named for gnu. Rejected.

## Round 3 (Astra r2)

### Why the parser was replaced
Rounds 1 and 2 both failed for the same root reason: `check-linux-floor.sh` decided by awk over the text of `readelf` and `objdump`, so any output it did not recognise meant "nothing found" and PASS. Patching the grammar a third time cannot close that class. `scripts/release/check_linux_floor.py` now decodes the ELF bytes directly (Python 3, standard library only). Every offset and size is bounds-checked against the file size, every count must reconcile, and anything it cannot fully account for is exit 2. `check-linux-floor.sh` is a 5-line wrapper (`exec python3 check_linux_floor.py "$@"`): same arguments, exit 0 pass / 1 floor violated / 2 could not inspect. New flag `--allow-no-version-requirements`. `OBJDUMP`/`READELF`/`AWK` env knobs no longer exist.

### Per finding
| finding | action |
|---|---|
| HIGH fails open on unrecognised tool output | no tool output is parsed. A file is PASS only after header, program headers, section headers, dynamic segment, Verneed/Vernaux walk (entries == DT_VERNEEDNUM, aux == each vn_cnt, no extra entries, no short chain) and the `.gnu.version_r` cross-check (sh_addr, sh_offset, sh_info, string table, and the decoded name list equal to the DT_VERNEED decode) all agree. No requirements at all = exit 2 unless the flag is given |
| MEDIUM unparsed instruction lines treated as data | there are no instruction lines. Raw 32-bit words are read from every `SHF_EXECINSTR` section (no section headers: every PF_X PT_LOAD); a word is data only if a `$d` mapping symbol says so; no symbol table = every word is code. Section sizes, alignment, mapping symbols outside their section, and trailing bytes in code regions are exit 2. Zero code words = exit 2 |
| LOW SMSTART/SMSTOP too broad | exactly the six words `d5034[2-7]7f`; `d503409f` (MSR TCO) and neighbours are tested as non-hits |

### Encoding rules (bits of the little-endian word w)
- SVE/SVE2/streaming SVE: `(w >> 25) & 0xF == 0b0010`
- SME/SME2: `w[31] == 1` and `(w >> 25) & 0xF == 0b0000`
- SMSTART/SMSTOP: `w in {d503427f, d503437f, d503447f, d503457f, d503467f, d503477f}` (`d5034[2-7]7f`)
- GLIBC: `GLIBC_a.b[.c]` numeric, integer-tuple compare against the floor (2.9 < 2.28 < 2.100, 2.28.1 > 2.28); any other `GLIBC_*` fails. GLIBCXX `<= 3.4.25`, CXXABI `<= 1.3.11` (unchanged limits; non-numeric tags fail). Other libraries (GCC_*, LIBSELINUX_*) are listed, not judged.
- DT_RELRSZ/DT_RELR/DT_RELRENT = tags 0x23/0x24/0x25 present = fail.
- Mapping symbols: `$x`, `$d`, `$x.N`, `$d.N` in `.symtab`; a section starts in code state (AAELF64).

### Not covered
MRS/MSR accesses to SVE/SME system registers (SVCR, SMCR, ZCR_ELx). Run-time-detected SVE/SME paths are still flagged (static scan). If the binary is stripped the scan cannot separate data from code: a hit is then reported with that caveat. GCC_* / other library version families are not judged. ELF32, big-endian, other machines are exit 2 by design.

### Finding 4: the rule and the evidence

Inspection of the delivered arm64 binary on the build box: ONE PT_LOAD with PF_R|PF_X covers file offsets 0 to 0x932cf84 (lld, no separate rodata segment). Besides `.init/.plt/.text/.fini` (0x714b90 to 0x74b97fc) it contains the ELF header, program headers, `.interp`, notes, `.gnu.hash`, `.dynsym`, `.dynstr`, `.gnu.version*`, `.rela.dyn` (7.4 MB) before the code and 31.9 MB of `.rodata`, `.eh_frame_hdr`, `.eh_frame`, `.gcc_except_table` after it. So the review's first suggestion (scanned sections == PF_X segment, short exception list) cannot hold for real output. The x86_64 binaries inspected (`/bin/ls`, python3, libc.so.6, ssh) have a PF_X segment holding exactly the exec sections plus 2 to 48 bytes of padding.

Rule (the review's sound alternative, with symbol and entry cross-checks): every byte of every PF_X PT_LOAD file image is exactly one of (a) the ELF header, (b) the program header table, (c) a non-executable SHF_ALLOC section whose `sh_addr` maps to its `sh_offset`, (d) a scanned executable section, (e) a gap. Gaps (padding, or bytes no section header claims, which includes the bytes of a section whose type was changed to SHT_NOBITS) are scanned as code, whole aligned words only; leading or trailing bytes that do not fill an aligned word must be zero. Section file ranges that overlap inside the segment are exit 2. A section with SHF_EXECINSTR that is SHT_NOBITS with a size, or lacks SHF_ALLOC, is exit 2. A `$x` mapping symbol in a section that is not scanned is exit 2 (catches a cleared SHF_EXECINSTR when a symtab exists). With section headers, `e_entry` (when non-zero) must lie inside a scanned executable section (catches a cleared flag on the entry section in a stripped file).

Residual hole, stated plainly: in a STRIPPED binary, clearing SHF_EXECINSTR on a code section that does not contain the entry point is indistinguishable from `.rodata` merged into the executable segment. Nothing structural separates them; the release binaries are checked before stripping and keep their symtab (`Cargo.toml` release profile sets no `strip`).

Delivered binary: PASS, max GLIBC 2.28, 0 hits, `28,742,225` code words, identical to the previous count. The scan adds 5 gap regions, 530 words of padding, scanned as code and reported on their own line (they are not counted as code words, so the zero-code-words rule is unchanged). `.text` has 187 data words ($d regions).
