## The problem (verified)
At the parent, `SessionRoutedToolHandler::handle_call` (`fuigo-workspace/src/hub.rs`) checked permission only when
`FUIGO_HITL_PERMISSION_LIVE` was set and the session was not yolo. Without the flag (the default) a hub-routed call went
straight to `session.toolset()`: deny rules, ask rules, protected-edit paths and P165's side-effecting tools were all
skipped. Session MCP tools that the hub configured (`workspace.configure_mcp`, bind-time MCP) were advertised as raw
bridge handlers and skipped even that. Upstream (`xai-grok-workspace/src/hub.rs:476`) has the same design and no fix, so
this is a Fuigo design.

## Threat model
- **Exposure is opt-in.** A workspace is exposed only by `fuigo workspace start [--hub-url]` (leader
  `ControlCommand::WorkspaceStart {hub_url, cwd}`, `leader/server.rs::handle_workspace_start`) or by the
  `fuigo-workspace-server --hub-url` sandbox binary. Fuigo runs no hub: `PROD_COMPUTER_HUB_URL` is empty, so `[hub].url`
  or `--hub-url` is required. `connect_local_workspace` builds the `HubConfig`; `connect_hub` opens one `ToolServer`.
- **Auth.** The leader's credential (session token or API key). `HubDestinationGuard` (P47) sends a session token only to
  a `wss`, non-loopback hub on the configured hub's origin; plaintext `ws` only for loopback/mesh (`allow_insecure_ws`).
- **Who can send a tool call.** The hub, and any party it lets act for that principal: the user's hub-side agent or chat,
  and the hub operator. The hub creates sessions with `session.bind` (it chooses the toolset, the cwd under the root and
  `yolo_mode`), sends `tool_call_request` frames per session, and can start MCP servers for a session. The local user's
  config is the only thing on this machine that the hub does not control.
- **What the hub side gates.** Unknown in general (third-party hub). A Fuigo agent that consumes remote tools gates them
  with its own machine's policy as dynamic tools. Under the flag the workspace sends a `permission_request` hook to the
  bound harness; Fuigo's harness SDK answers only when a host registered a handler, and fuigo-shell registers none, so an
  unanswered prompt fails closed at the 600 s backstop (`HOOK_REQUEST_BACKSTOP_TIMEOUT`).
- **Session modes.** Local manager: ask (default), auto (classifier), always-approve (yolo; pinned off by
  `requirements.toml [ui] disable_bypass_permissions_mode`), and `prompt_policy` dontAsk / bypassPermissions. Hub
  sessions carry only `yolo_mode`, which the hub asserts at bind and at every before-turn hook; no auto or plan state.
  CLI `--deny/--allow` rules belong to one interactive session's spawn and do not exist for an exposure (Astra r2 accepted
  this).

## Design (what a hub-routed call now goes through)
`hub.rs::enforce_hub_policy` runs for every hub-routed call, flag or not, before dispatch:
1. **What the call touches.** The toolset parses the call exactly as for a local call (`FinalizedToolset::try_parse`, after
   parameter renames, for the implementation behind the name) and classifies it with the local `AccessKind::from`;
   `hub_input_accesses` adds every `read_file`/codex `read_file` batch entry and every `apply_patch` target (a parsed
   patch drops the `Edit("apply_patch")` sentinel). Name-based accesses are added only for generic (MCP/runtime) tools
   and unknown names. Arguments that do not parse fail before anything runs. Paths are the path-virtualized real ones; the
   hub prompt shows the model view. Session MCP tools go through `McpPolicyGatedHandler` (via `PolicyGatedRegistry`) as
   `MCPTool{server__tool}`.
2. **The local policy**, resolved per call from the session cwd (`resolve_permission_config_with_fallback`; project tier
   gated by the workspace's folder-trust verdict), in the local manager's order (`hub_policy_verdict`):
   - a deny rule refuses, in every mode;
   - the bash command gate / shell-file gate (a Bash ask rule, or a command it cannot clear) and the protected-path
     floor (`manager::protected_target`, now shared with the manager) need approval in every mode;
   - under always-approve everything else runs (as locally); hub yolo is clamped by the managed pin;
   - otherwise an ask rule needs approval; a P165 side-effecting tool needs approval unless an allow rule names it;
   - what the local manager would prompt for by default (`manager::hub_needs_default_prompt`: safe list, bash request
     floor, narrow-allow write clearance, ambient git scan) is refused under dontAsk, allowed under bypassPermissions,
     sent to the hub prompt under `FUIGO_HITL_PERMISSION_LIVE`, and otherwise left to the hub-side agent;
   - a content search with a patterned Read ask rule, or a Read deny an any-depth `**/` exclude cannot express, is
     judged file by file over what ripgrep would search (ripgrep's walker, same overrides): a denied file refuses it, an
     ask-ruled file needs approval;
   - an OpenCode bash `workdir` is judged in addition to the session cwd;
  - (round 4) a search root is judged and walked where the tools resolve it (`resolve_model_path`) as well as
    absolute-or-joined; each walked file is judged as a `Grep` of it; a search tool that does not apply the Read-deny
    excludes is walked for every patterned deny, without them; everything is read after the parameter renames.
3. **Approval.** Each access that needs approval gets its own `permission_request` through the hub; one refusal (or an
   error/timeout) refuses the call. With no hub connection it is refused with a clear error. Nothing runs silently.
4. **Search.** The policy's Read-deny globs go to that one call (`CallDenyReadGlobs` on the call context, round 4 #9);
   nothing shared is written. Codex `grep_files`, OpenCode `grep` and OpenCode `glob` now honour the Read-deny globs
   like the native grep (local sessions too; `glob` since round 4).
5. The call is judged and dispatched on one toolset snapshot.

Deviation from the coordinator's recommended shape: a protected path *asks* (hub prompt, else refused) instead of
always refusing, because locally it is a prompt and the hub prompt is the consent channel. Local `--always-approve`
waives the protected floor; hub always-approve does not, because the hub asserts it per session (stricter than local, on
purpose; Astra r2/r3 judged it reasonable).

`FUIGO_HITL_PERMISSION_LIVE` keeps its meaning narrowed: the hub also gets the prompts the local manager would show by
default. Explicit local policy no longer depends on it.

## Behaviour changes (for the release notes)
1. Hub-routed calls are judged by the workspace's local permission policy without any flag. A deny rule refuses the
   call, also in a hub always-approve session.
2. An ask rule, a Bash rule the shell gate asks about, a protected path (`.git/hooks`, `.ssh`, shell startup files,
   Fuigo/Claude config, `/etc`, …), a side-effecting tool (`scheduler_create/delete`, `workflow` launch, `image_gen`,
   `image_edit`, `image_to_video`, `reference_to_video`), and a search over files a Read ask rule covers now need approval
   through the hub's `permission_request` prompt. With no hub connection, a refusal, or no answer within 600 s, the call is
   refused (`PermissionDenied`).
3. Hub always-approve honours the managed always-approve pin and does not waive the protected-path floor or the shell gate.
4. `Read`/`Grep` rules apply to hub reads (every batch entry included) and to hub searches: Read-denied files are excluded,
   and a search that would read a denied file the exclude cannot express is refused.
5. Session MCP tools advertised to the hub follow `mcp__server` rules.
6. `dontAsk` refuses hub calls that are not pre-approved, as locally (they ran before).
7. Under `FUIGO_HITL_PERMISSION_LIVE`, hub calls get exactly the local default prompts: safe-listed commands (`ls`,
   `git status` in a clean repo) and calls an allow rule clears no longer prompt; denied calls are refused instead of
   prompting.
8. Local and hub: codex `grep_files`, opencode `grep` and opencode `glob` exclude Read-denied paths like the native
   grep (same basename semantics, see K).
10. A Fuigo harness with no permission handler rejects a hub `permission_request` at once instead of leaving it to the
   600 s backstop.
9. Hub calls with arguments that do not parse fail before dispatch with the parse error.

Does a 1.0.21 hub workflow now need configuration? Yes, one: a hub session that used side-effecting tools, wrote a
protected path, or hit an ask rule, on a hub that does not answer `permission_request` (Fuigo's own harness does not).
Recommendation: no default change; say in the release notes to pre-approve such tools with a bare allow rule
(`[permission] allow = ["image_gen"]`) or use a hub that answers the prompt. Everything else that ran in 1.0.21 and is
not covered by an explicit local rule still runs.
