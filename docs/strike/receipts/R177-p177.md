## Mechanism and fail-closed rules
Same as P158 (entries ride in `SandboxProfile.git_write_deny`): macOS Seatbelt write-deny per entry; Linux read-only
bwrap binds for entries inside a writable root, verified inside bwrap (`verify_git_write_deny_enforced`). New:
- **Missing names (Linux):** a missing startup directory is created empty and bound; a missing file/tool tree is never
  created (placeholders shadow: empty `~/.bash_profile` hides `~/.profile`, empty `~/.cargo/config` shadows
  `config.toml`). Instead its own tool directory is **pinned** (`GitPathKind::PinnedDir`: bound read-only, each
  existing unprotected child re-bound writable, cargo's `registry/`, `git/`, `.package-cache*` made first), or, when the
  directory is shared/the workspace/an ancestor of the missing own directory, the sandbox **refuses** if the workspace,
  a `read_write` grant or the Fuigo home makes it writable. macOS: Seatbelt denies the name, and each missing directory
  on the way is a node deny (`MissingAncestor`).
- **Refuses:** relative home or relocating variable; unreadable entry type; workspace or any writable root inside a
  protected tree; protected file entry inside a root with a second hard link; an unaccounted hard link found in (or
  not fully searchable in) a writable root; an unlistable protected tree being walked; Linux link node inside a root
  (P158 rule, except under a pin).

## Behaviour changes for Sean (each with my recommendation)
- **Linux: a home made writable by the workspace (`fuigo` run in `~`) or a `read_write` grant of `~` / `~/.config`
  refuses to start** (a missing `~/.bash_profile` etc. would be creatable). **Recommendation: keep**; the error says to
  run in a project directory or grant only the needed subdirectory. macOS runs and denies.
- A `read_write` grant of `~/.cargo` keeps working: `~/.cargo` is pinned, builds write the registry/locks (e2e runs a
  real `cargo build` in the sandbox); new top-level names in `~/.cargo` (e.g. a first `cargo-audit` advisory-db)
  cannot be created there. **Recommendation: keep.**
- A workspace inside a protected tree (`~/.config/nvim`, `~/.vim/pack/...`) refuses. **Recommendation: keep** (upstream
  makes it read-only).
- Hard-linked dotfiles (`~/.bashrc` linked into a writable root, or two protected files linked to each other inside a
  root) refuse. **Recommendation: keep**; error names the link.
- With a writable home, ssh `known_hosts`, `gh auth`, `docker login`, gpg keyring writes fail inside the sandbox.
  **Recommendation: keep** (upstream floors the same stores).

**HIGH 1 evidence.** `link(2)` returns `EXDEV` when the old and new names are on different mounts (`do_linkat`:
`old_path.mnt != new_path.mnt`, checked before any LSM hook, so Landlock and its ABI play no part). In the Linux plan
every protected name inside a writable root is its own `--ro-bind` (or lies in a tree bound read-only as one mount), and
every re-bound child of a pin is its own `--bind`; the pin itself is a third mount. A link from a protected inode to any
writable name therefore always crosses a mount. Checked three ways: (1) plain `bwrap` on Hetzner (kernel
6.8.0-137, no Landlock, as root): `ln config.toml registry/alias`, `ln config.toml <outer>/alias` and
`ln <pin child> registry/alias` all `Invalid cross-device link`, `config.toml` unchanged, `st_nlink` 1; (2) the e2e at
the red tip; (3) the e2e at the fix tip, which logs the errno. Outside every writable root the outer Landlock ruleset
already denies the link (ABI >= 2: no `Refer` there; ABI 1: any cross-directory link is denied). An inner Landlock
ruleset (Grok's fix) would re-grant every outer write root to handle write rights at all, and guard a path the VFS
already closes; the ABI < 2 refusal is likewise unneeded. Not added. If the coordinator wants it as defence in depth
anyway, it is a separate packet (risk: cargo's registry writes).

**MEDIUM 4 research (this Mac, macOS 26.3, `sandbox-exec`, no cargo).** `file-link` is a real SBPL operation (an
unknown name fails to parse; Apple's `appsandbox-common.sb` uses it). With nono's layout (`(deny default)`, platform
rules, then `(allow file-write* (subpath <root>))`):
| Setup | `ln protected <ws>/alias` |
|---|---|
| protected file outside every write root, no rule | denied (Seatbelt checks the source for a link) |
| home and workspace writable, no rule | **allowed**, write through the alias changed the file |
| same, P177's existing write-deny set on the literal | denied |
| same, `(deny file-link (literal F))` alone | denied |
| `(allow default)`, `(deny file-link F)` then a later `(allow file-link (subpath ..))` | allowed (nono emits no `file-link` allow) |
So the existing set already blocked it on 26.3 (the `file-write-data`/`-mode`/`-owner`/`-flags`/`-times` denies each
match the link check); `file-link` makes it explicit and independent of that observed overlap. The startup refusal
(protected file sharing `st_dev` with a writable root) is not added: Seatbelt can deny the link, which is the brief's
condition for using the rule instead.

**LOW 6 (accepted limit).** On Linux a protected file outside every read-only bind (outside the writable roots, so
Landlock denies writing it) can still be `chmod`ed: Landlock has no mode-change right and nono's write flags add none.
The content cannot change. What a mode change can do: make an rc file group- or world-writable (another local user on
a shared host could then edit it), set `+x` on a file in a `PATH` directory, or make ssh refuse a group-writable
`~/.ssh/config` (a denial of service). Accepted, as Grok recommends: a path-aware `chmod` deny needs a seccomp filter on
`fchmodat`, which cannot see paths. Inside a writable root the read-only bind returns `EROFS`; macOS denies
`file-write-mode`. New K row below.

## Landing notes (coordinator, 1.0.23) and the accepted `/proc` limit
- Landed WITHOUT a pid namespace, by Sean's decision of 2026-10-08 (DECISIONS-PENDING section 2): branch
  `strike/p177-land` = round S2 tip `253c25c7` rebased onto `strike/integration` `c0be329b4` (patch identical).
  The round S3 commits (`a185c90d`, `1c92c132`: `--unshare-pid` when the effective uid is 0) are NOT landed; they
  stay on `strike/p177-s2` for Wave 4.
- Grok 4.7 round 2 (`codex-audit/grok-p177-r2.md`): the six round-1 findings are closed or accepted (it agrees the
  hard-link HIGH needs no code change: `link`/`rename` across the bind mounts fail before Landlock). One MEDIUM is
  open and ACCEPTED as a known limit until Wave 4:
  **When Fuigo runs as root, a sandboxed command can write a protected file through `/proc/<pid>/root` of another
  uid-0 process that has no capabilities and lives outside the sandbox's mount namespace.** Coordinator probe on
  the build box (root, kernel 6.8, read-only, nothing changed): from
  `bwrap --cap-drop ALL --bind / / --proc /proc`, `readlink /proc/1/root` FAILS (the target holds more
  capabilities than the caller; this is the kernel's capability check, not Yama `ptrace_scope`), but
  `readlink /proc/<P>/root` succeeds when P was started with an empty capability set. So pid 1 is not reachable;
  a capability-less root process outside the sandbox is.
- Why the fix was not landed: Fuigo re-executes its WHOLE process inside bwrap, so with a pid namespace the pids
  repeat across Fuigo instances and pid-based liveness checks can steal a live lock or honour a dead one
  (`fuigo-shell/src/leader/mod.rs` ~1613-1665 and ~2056, `auth/manager/lock.rs` ~114; found by reading, not run
  under root). Wave 4's per-command sandbox puts only the command in the namespace, which closes the gap without
  touching those checks.
- Still unverified on this packet: macOS (`cargo check`, the `home_write_deny` e2e with the relocation cases, the
  `file-link` rule on the oldest supported macOS) and Windows (the crate has no Windows write-deny code). RC
  checklist items.
