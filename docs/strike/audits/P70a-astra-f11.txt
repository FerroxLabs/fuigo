1. **MEDIUM — Concurrent key rotation can give one MCP server inconsistent credentials.**  
   Locations: [servers.rs:5296](/Volumes/Mando/WaylandBots/Fuigo/wt-p70a/crates/codegen/fuigo-mcp/src/servers.rs:5296), [servers.rs:5203](/Volumes/Mando/WaylandBots/Fuigo/wt-p70a/crates/codegen/fuigo-mcp/src/servers.rs:5203), [servers.rs:5365](/Volumes/Mando/WaylandBots/Fuigo/wt-p70a/crates/codegen/fuigo-mcp/src/servers.rs:5365).

   Each argument, environment value, and HTTP header independently reads the mutable key store. Session threads can launch/rebuild MCP servers concurrently with `fuigo/setApiKey`. If rotation occurs between reads, the same child can receive key A in `--key` and key B in `FUIGO_API_KEY`; similarly, two authentication headers can contain different keys. A server requiring matching credentials can reject authentication, and an HTTP client retains those mismatched values until rebuilt.

   **Existing tests do not catch this:** the conformance test keeps one saved key throughout; the resolver tests change keys sequentially. Hooks already avoid this problem by taking one snapshot per child.

   **Follow-up:** capture one key snapshot per MCP server construction and use `read_first_party_key_references` across all its arguments/environment values or headers. Add a deterministic rotation-interleaving regression test.

The reviewed paths otherwise support the stated late-binding and destination restrictions. The conformance harness launches the real binary and records ACP output verbatim; runtime results remain unverified in this audit.
