1. **MEDIUM — Mixed credential spellings can still give one HTTP MCP server two key versions.**

   Locations: [servers.rs:5379](/Volumes/Mando/WaylandBots/Fuigo/wt-p70a/crates/codegen/fuigo-mcp/src/servers.rs:5379), [mcp.rs:496](/Volumes/Mando/WaylandBots/Fuigo/wt-p70a/crates/codegen/fuigo-config-types/src/mcp.rs:496).

   Concrete configuration:
   ```toml
   bearer_token_env_var = "FUIGO_API_KEY"
   headers = { X-Api-Key = "${FUIGO_API_KEY}" }
   ```

   `to_acp_mcp_server` resolves the bearer credential during config conversion, producing `Authorization: Bearer A`. The explicit header remains literal until `start_mcp_server`. If `fuigo/setApiKey` changes the stored key to B between those operations, the new snapshot resolves only `X-Api-Key`, producing a client with **Authorization=A and X-Api-Key=B**. A server requiring matching credentials rejects authentication; the constructed client retains the mismatch.

   The round-11 correction fixes consistency among explicit references, but does not cover this interaction with the existing named-credential path.

   **Existing tests do not catch it:** the conformance test uses one unchanged key and explicit headers; the new snapshot test exercises only `apply_stdio_env`. Neither mixes `bearer_token_env_var` with an explicit header across rotation.

   **Follow-up:** preserve the named bearer binding until construction and resolve it against the same snapshot. Add a deterministic regression that rotates the key between config conversion and server construction.

The inspected paths otherwise support the stated destination restrictions and exclusion of runtime inference keys. The conformance harness launches the real agent binary; runtime results remain unverified in this audit.
