### Procedure (squash; recommended over a history filter)

A squash makes the public branch one commit on top of v1.0.20, so no strike-era blob is reachable. A
`git filter-repo` of the 785 strike commits would also work but rewrites every SHA anyway (receipts cite SHAs
either way), must also be checked for every deleted path, and keeps 785 commits of noise; the squash is simpler to
verify. The full strike history stays private (local repo plus a private archive), where every receipt SHA resolves.

1. After P96, P75, P70a and the bump have landed and the final gate has passed on the release candidate `RC`
   (a private ref; never push it to the public remote):
2. In a throwaway clone: `git clone --no-local --no-checkout --single-branch -b <RC branch> <repo> /tmp/pub && cd /tmp/pub`
3. Write the commit message (`Fuigo 1.0.21` plus a pointer to the release notes) to `msg.txt`.
4. `scripts/release/public-squash.sh <RC> v1.0.20 msg.txt` prints `DROP`/`REDACT` lines and the new commit id `C`.
   It drops every RAW file under `docs/strike/audits/`, replaces that home path with `~` in the files it
   keeps, refuses if any home path remains, and creates no ref.
5. Verify (all must hold): `git diff --name-status <RC> C` shows only `D` of the RAW list and `M` of the redacted
   reports; `git rev-list --objects C` contains none of the dropped blob ids; `git grep -c -F "$HOME" C` (on Sean's Mac) is
   empty; `git log --format=%P -1 C` is v1.0.20.
6. **Sean:** `git branch release/1.0.21 C`, push that one branch, open the PR to `main` (same shape as
   `release/1.0.20`, PR #26), let CI run, merge, tag `v1.0.21` on the merge commit.

     does not cover it; its Windows execution is unproven until a real run. If a verify job fails after npm

## 4. Rollback drill

**Status: written, not yet exercised.** It needs the final release binary; run the exercise in section 4.4 on the
RC before tagging.

### 4.1 Stop new installs (maintainer, Sean)

The release workflow publishes to npm `latest` and has no rollback job.

```sh
for p in fuigo @fuigo/darwin-arm64 @fuigo/darwin-x64 @fuigo/linux-arm64 @fuigo/linux-x64 @fuigo/win32-arm64 @fuigo/win32-x64; do
  npm dist-tag add "$p@1.0.20" latest
done
npm deprecate fuigo@1.0.21 "Withdrawn: install 1.0.20 (npm i -g fuigo@1.0.20)"
```

Do not `npm unpublish`: npm never allows the number again, and an unpublished platform package breaks the meta
package's exact pins. Fix forward as 1.0.22 instead.

The npm installer in Fuigo never downgrades (`installer_allows_downgrade("npm") == false`,
`fuigo-update/src/auto_update.rs:532`), so moving `latest` back stops new upgrades but does not move anyone who
already has 1.0.21. They must downgrade by hand (4.2).

### 4.2 User downgrade

1. Close every Fuigo session.
2. `npm i -g fuigo@1.0.20` (or `fuigo@1.0.17`).
3. Keep the updater from coming back up: in `~/.fuigo/config.toml` set `[cli] maximum_version = "1.0.20"` (exists
   in 1.0.17), or `auto_update = false`, or export `FUIGO_MAXIMUM_VERSION=1.0.20`.
4. Do the per-state steps in 4.3 that apply.
