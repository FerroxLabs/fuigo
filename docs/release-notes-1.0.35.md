# Fuigo 1.0.35 release notes

## Folder trust now covers commands

You now decide once per folder (its git repository, or the folder itself outside a repository) whether to trust it,
and that one answer covers both the folder's settings and its shell commands. See
[Folder trust](../crates/codegen/fuigo-pager/docs/user-guide/22-permissions-and-safety.md#folder-trust).

- **Trusted folders behave as before.** Every rule below applies as in earlier releases, except that the folder's own
  content now counts as yours there: when the repository's git configuration or hooks run for a command, git runs in
  a repository Fuigo could not scan, or a command loads a configuration file from the project (`grep --config` with a
  project `.ugrep`, a project `.npmrc`, `.cargo/config.toml` or `.bazelrc`), the Auto mode model's allow stands
  instead of turning into a question, and such a configuration file no longer takes a command off the read-only lists.
  A steering environment variable still makes these ask.
- **A trusted repository covers its worktrees.** Its linked worktrees (`git worktree add`, wherever they are) and the
  worktrees `fuigo -w` makes are trusted with it, with no question of their own. A repository inside a trusted one
  that is not a submodule (a vendored clone, `node_modules/x/.git`) keeps its own trust: the first time a command runs
  in it, you are asked, until you trust it too.
- **In a folder you have not trusted** no project settings load (MCP and LSP servers, hooks, `.envrc`, permission
  rules, workflows, plugins, instructions, skills), and no shell command runs unless your approval or grant covers the
  command: an approval at the prompt, a remembered command or prefix, "allow all commands", your own config or
  `--allow` rule, or always-approve (in any mode: turning always-approve on leaves Auto mode). Everything else asks (or under `dontAsk` and in headless runs is refused with a
  message naming the fix). The read-only lists, Auto mode (its fast path, routine check and model) and sandbox
  auto-allow approve nothing there, and the Auto mode model is not asked.
- **A folder's trust covers the commands that start there**: the session folder and the tool's working directory.
  Naming another folder in a command (`cd`, `git -C`, `GIT_DIR=`, `make -C`, ...) does not change the answer, as in other coding
  agents.
- **Fuigo runs no git, jj or direnv of its own** in a folder you have not trusted (status line, turn-end checks, goal
  baseline, file watching, `.envrc`); those features stay quiet there. Fuigo's own content search there reads no
  ripgrep configuration file.
- **Folders trusted before 1.0.35 are asked once more**, because trust used to cover settings only. Until you answer,
  and in headless runs and ACP clients that cannot ask, such a folder is not trusted.
- **Folders without project settings are now asked about too**, including folders outside any git repository. A "no"
  is saved and not asked again; it continues the session without trusting the folder (`q` quits).
- **Your home folder and `/` can never be trusted**: no project settings load there and every command asks; the
  full-screen app shows one dim line instead of the question.
- **Headless runs** (`-p`, CI, bots and embedding apps) cannot answer the question. Pass `--trust` once (it is now
  listed in `--help`), or list the checkouts in your own `~/.fuigo/config.toml`; a project's own config cannot:
  `[folder_trust] trusted_folders = ["/srv/checkouts/app"]`. An `--allow` rule also works. A headless run in a folder
  that is not trusted says so once on stderr.
- **ACP clients** ask the trust question only if they advertise `"fuigo/folderTrust": {"v2": true}` and answer with
  scope `configAndCommands`. A client without it is never asked: its sessions use the trust you already gave (from
  the full-screen app, `--trust` or `trusted_folders`), and in other folders each command asks.
- `/trust` and `/untrust` (aliases of `/hooks-trust` and `/hooks-untrust`) trust or stop trusting the whole folder in
  ACP clients; after `/untrust` the next command asks and project rules drop, here and in subagents and on a hub.
- The agent cannot edit the trust store, your `config.toml` or Fuigo's worktree database without asking, and
  `fuigo --trust` always asks, even under "allow all commands". A relative `FUIGO_HOME` is ignored for all settings and
  trust. `[folder_trust] enabled = false` or `FUIGO_FOLDER_TRUST=0` switches the check off with a warning at start.
- A hub judges each command by its own trust store: an untrusted folder's command asks there (it is never left to the
  hub agent or the sandbox card). It serves a folder's project config, skills, instructions and plugins only when it
  trusts that folder.
- **Plugin marketplaces.** `fuigo plugin install NAME@SOURCE`, `fuigo plugin marketplace update` and the plugin
  manager's Install and Refresh fetch the marketplace as before (you asked for them). Background marketplace refreshes
  (a listing Fuigo refreshes on its own) work as before: they clone and fetch into Fuigo's own marketplace cache folder.

## Shell permissions

Grants you give apply in trusted and untrusted folders alike. The rules in this section describe what runs without
asking in a trusted folder.

### In a trusted folder: whose authority counts

Your own environment and dotfiles, any state created by commands you approved, and the content of a folder you trust are your authority. The rules below decide what runs without asking in a trusted folder; the first section lists where a trusted folder's own content now counts as yours.

### What runs without asking

With no grant from you, a shell command runs without a prompt only when it passes every rule in this section. What your own grants cover, and what still asks under them, is in the next section.

- **Strict plain-text rule.** A shell command now runs without asking, with no grant from you, only when it is plain text: simple commands joined by `&&`, `||`, `;`, `|` or a newline; every word either unquoted letters, digits and `._/:=@%+,-`, or one quoted string making up the whole word (no newline inside either kind of quotes; no `$`, backtick, `\` or `!` inside double quotes); a plain program name (no path, no `NAME=value` in front, no wrapper such as `env`, `command`, `timeout`, `nice`, `xargs`, `sudo` or `time`, and not `cd`, `set`, `shopt`, `eval`, `source`, `alias`, `export` or `unset`); and redirects only from or to `/dev/null` (`2>/dev/null`, `&>/dev/null`, `< /dev/null`). The read-only command list and its per-command checks then apply, and pipes between plain commands still run without asking (`git log --oneline | head -5`). Anything richer asks, even when every program is read-only: `ls ~/x`, `cat *.md`, `ls src/*.rs`, `ls {src,tests}`, `echo "$HOME"`, `cd src && git status`, `FOO=1 ls`, `ls 2>&1`. This covers the read-only command list in Ask mode and the Auto mode fast path.
- **Auto mode latency.** A command that is not plain text goes to the Auto mode model instead of the fast path. The commonest case is `cargo test 2>&1 | tail -5`: drop the `2>&1`, or send errors to `/dev/null` (`cargo test 2>/dev/null | tail -5`), to keep it on the fast path. `CARGO_TERM_COLOR=never cargo test` and `cd dir && …` go to the model too. The exact no-op shortcut (`true`, `:`, `false`) is held to the same rule, so `true` followed by a carriage return or a non-breaking space goes to the model.
- **Forms that take a listed command off the list.** Every program on the read-only list and the Auto mode routine list had its options audited. These forms now ask instead of running as read-only or routine (your grants still cover them): `date` setting the clock or reading `-f FILE`; `hostname NAME`/`-F`; `uniq`'s output operand (also after a `-` input or an option value such as `-f 1`); `sort -T`/`--random-source`/`--files0-from`, `wc`/`du --files0-from`, `diff --from-file`/`--to-file`, `file -f`/`-m`/`-C`, `tree --fromfile`/`-R`, `strings @FILE`, `jq --rawfile`/`--slurpfile`; interactive `top`/`htop`; `git branch` other than listing (`-D`, `-f`, `-m`, a new name), `git diff --no-index` or an outside path, `git grep --no-index`, `git blame --contents`; `git commit -F FILE` and `git pull -s` with a custom strategy in Auto mode; `kubectl --cache-dir`, `--log-file` and template files; and build-tool forms that install, publish, change user or registry configuration, or write outside the project (`cargo install`/`publish`/unknown subcommands, `--target-dir /elsewhere`, `make -C /elsewhere`, `make CC=./x`, `cmake --install`, `go env -w`, `go clean -modcache`, `pytest --junitxml=/tmp/x`, `npm config`/`link`/`-g`, `npm version patch`, `uv self update`, `rustup self`, and more). npm, pnpm and yarn forms keep Auto mode routine approval only with options spelled exactly as one of the common install, lockfile and output options (`--save-dev`, `--omit=dev`, `--frozen-lockfile`, `--silent`, ...): npm accepts abbreviations and combined shorthands, so `-gq` or `--prefi=/tmp/out` ask like `-g` and `--prefix`.
- An interpreter run gets Auto mode routine approval only for a lone `--version`, `--help` or the interpreter's own version flag (`python3 --version`, `python3 -V`, `node -v`, `perl -v`, `ruby -v`, `lua -v`, `php -v`; CPython exits on these before it imports `site`, so no `sitecustomize.py` runs; PyPy's forms ask); `python3 script.py` now reaches the Auto mode model instead of the fast path.
- A path-qualified or case-variant program name (`./env ls`, `/tmp/x/timeout 5 ls`, `bin/explorer ls`, `LS`) no longer gets read-only or Auto mode routine approval. Plain names resolve as before.

### What still asks under your grants

- Your own grants are explicit overrides and are not held to the plain-text rule: a remembered prefix or glob grant, "allow all commands" for the session, sandbox auto-allow, a configured catch-all `allow` rule and an approval of the exact whole command. They keep only the floors below.
- "Allow all commands" for the session and sandbox auto-allow now ask for a script with a variable or command substitution (`"$VAR"`, `$(...)`), a loop, a function, a subshell or other structure the classifier cannot decompose, and for a declaration such as `export FOO=1`. Approve that exact script to remember it.
- Commands the shell classifier cannot fully model now ask instead of running unprompted. This covers the read-only command list, remembered prefix and glob grants, "allow all commands" for the session, sandbox auto-allow and the Auto mode fast path. Only approving that exact full command skips the prompt. A configured catch-all `allow` rule (`--allow Bash`) stays an explicit override: it still asks for the cases below and for an argument only the shell resolves, but not for a dangerous-list command or for shell structure the parser cannot decompose.
- Covered: a tool in a mode that runs another program or script (`sed e`, `awk system()`, `xargs`, `rsync -e`, `git grep -O`, `scp -S`, `tar -I`/`--to-command`/`--checkpoint-action=exec`, `man -P`, `go run`/`go install`/`go tool`/`go vet -vettool`, `wget --use-askpass`, and more); redirects to `/dev/tcp` or `/dev/udp`; kubectl Secret reads and an attached `-s` server; `printf -v`, a `printf` format with `%n`, or a format only the shell resolves; a `cd` in a pipeline or subshell, or in an `||` list where git may run after it, before git. Quote fragments, brace expansion and option-capable globs are resolved the way bash resolves them before any check; ANSI-C `$'…'` quoting, brace groups nested deeper than 8, and an empty quote pair next to a `~` or a brace (`''~`) are treated as unknown. A glob inside an option value (`--include=*.rs`, `rg -g *.rs`) asks on every path; quote the whole word (`'--include=*.rs'`) to keep it plain.
- Also covered: a `set` option that changes how bash reads later words (`set +B`, `set -f`, `set -o posix`; `set -euo pipefail` is fine), `shopt`, `alias` and `hash -p`; an abbreviated or unknown option of `timeout`, `nice`, `stdbuf`, `ionice` or `chrt` (`timeout --sig TERM …`); `git grep -O` and `--ext-diff` through a path-qualified `git` or after any global option; `git push` after global options (`git --no-pager push`); an interpreter or shell script operand naming stdin or a descriptor (`python3 /dev/stdin`, `/dev/fd/0`, `/proc/self/fd/0`); a `PATH` or other assignment behind `command env`; and a `cd` that runs only if an earlier command succeeded when more of the script follows (`ls x && cd dir; git status`).
- Interpreter code the command does not show now asks under a broad grant: inline code (`python -c`, `perl -e`/`-E` also inside a cluster such as `-lne`, `node --eval`, `ruby -e`, `php -r`, `lua -e`, `deno eval`, `bun -e`) and a program read from stdin, a heredoc or a here-string. A script file or module run (`python3 script.py`, `python3 -m pytest`, `node build.js`) is unchanged under a matching glob grant (`python3 *`), an exact command grant, "allow all commands" and sandbox auto-allow; a bare interpreter prefix grant stays pinned to the exact command, as in 1.0.34.
- An `awk` program asks unless it is plainly free of `system`, `|`, `getline`, `ENVIRON`, `PROCINFO`, `SYMTAB`, `FUNCTAB`, `>`, `@`, backslashes and string splicing (a quote right next to a letter, digit or `_` outside the string, as in `sy"s"tem`; ordinary strings such as `print "hello"` or `$1=="foo"` are fine). `awk '$3 > 5'` asks too; a program from `-f`, `-e` or `--source` always asks.
- Environment reads always ask, with or without a variable name: `env`, `printenv NAME`, `set`, `export -p`, `declare -p NAME`, `typeset -p`, `jq env`, a `jq` filter file (also `-nf`) or `import`/`include`, awk `ENVIRON`/`SYMTAB`, and `/proc/self/environ` (or `/proc/<pid>/environ`, a glob that can match one such as `/proc/s*/envi*`, or a relative `proc/self` path) read as an operand or a redirect.
- `ssh`, `scp` and `sftp` ask for `-o ProxyCommand`/`LocalCommand`/`PermitLocalCommand`/`KnownHostsCommand` (any case or spelling), `-F` and `-S`; every `sftp` invocation asks.
- Fuigo's own `grep` and `find` are now judged as the tools they run, ugrep and bfs. These ask on every path, your broad grants included: `grep --filter=…`, `--pager`, `--view`, `-Q`/`--query`, `--config`/`---FILE`, `--save-config` and `--from`; `find -rm` (the same as `-delete`), `-f PATH`, `-files0-from`, `-help`/`--help`, and a path after the expression (`find . -name x /etc`). Ordinary `grep -rn` and `find . -name` use is unchanged.
- Build-tool options that run another program now ask under every path, broad grants included: `make --eval`/`-E`/`-f -`/`-p`, `make SHELL=…` or a `$(shell …)` value; `cmake -E`/`-P`/`-C`/`--toolchain`/`--open` and a `-D` naming a compiler or launcher; `cargo --config`, `-Z`, `doc --open`; `rustc -C linker=`/`link-arg=`, `-Z`, `@file`, `--extern` of a library; `pytest --pdb`/`--trace`/`-p NAME`/`-o`; `just --shell`/`-c`/`--chooser`/`--edit`; `bazel --run_under`/`--bazelrc`; npm `--script-shell`/`--node-options`; `uv --python PATH`; `rustup doc`; `go -ldflags=-extld=…`/`-gccgoflags`/`go bug`; `gh --web`, `gh auth status --show-token`, and a `gh --jq` filter reading the environment. Also `kubectl get -f FILE`/`-k DIR` (the file can name a Secret).
- A repository's own configuration can no longer make a command that runs without asking run a program. A git alias in `.git/config` (or a file it includes) for a subcommand that is not part of git asks whatever its text, not only a `!` alias (git always runs its own subcommands before an alias, so `alias.status` changes nothing). A file in the repository that your own git config includes counts like `.git/config`, and a repository's `trace2.*Target` path asks (it makes `git status` write a file); in Auto mode in a trusted folder the model decides such a command, and its allow stands.
- The environment Fuigo started with is judged by what is set, not by what values point at: if your `PATH` has a relative, empty or in-project entry (an activated virtualenv's `.venv/bin`, a direnv `PATH_add bin`), or any variable that changes which program runs or what it loads is set, Fuigo asks before every shell command that has no grant (your grants still apply). Every command: `LD_PRELOAD`, `LD_AUDIT`, `DYLD_INSERT_LIBRARIES` and the other `DYLD_*` that are not library search paths, `GCONV_PATH`, `BASH_ENV`, `ENV`. Per program: git's `GIT_EXTERNAL_DIFF`, `GIT_SSH`, `GIT_SSH_COMMAND`, `GIT_PAGER`, `GIT_EDITOR`, `GIT_SEQUENCE_EDITOR`, `GIT_ASKPASS`, `SSH_ASKPASS`, `GIT_PROXY_COMMAND`, `GIT_EXEC_PATH`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG`, `GIT_DIR`, `GIT_COMMON_DIR`, `GIT_TEMPLATE_DIR`, `LESSCLOSE`; `RIPGREP_CONFIG_PATH`; `MAGIC`; and the config, helper and toolchain variables of `gh`, `docker`, npm-family tools, cargo, `go`, `make` and `cmake` (the permissions and safety guide lists them), and `NODE_OPTIONS` for node, `RUBYOPT` for ruby, `PERL5OPT` for perl. The library search paths `LD_LIBRARY_PATH`, `DYLD_LIBRARY_PATH`, `DYLD_FALLBACK_LIBRARY_PATH`, `DYLD_FRAMEWORK_PATH` and `DYLD_FALLBACK_FRAMEWORK_PATH` are fine when each entry is a plain absolute path outside the project, and `RUSTUP_TOOLCHAIN` when it is a plain toolchain name or such a path. `PAGER`, `LESSOPEN`, `EDITOR`, `VISUAL`, `XDG_CONFIG_HOME`, `KUBECONFIG`, `CARGO_HOME`, `RUSTUP_HOME`, `GOROOT`, `ZDOTDIR`, and Fuigo's own selectors `SHELL`, `FUIGO_SHELL`, `FUIGO_HOME`, `FUIGO_CONFIG_PATH`, `FUIGO_TOOLS_UGREP_PATH`, `FUIGO_TOOLS_BFS_PATH`, `RG_BIN_PATH` and `RUNFILES_DIR` are fine as a plain absolute path outside the project (or, for the pager, editors and shell, a plain name like `less`); anything else asks. A command approved without a grant (read-only lists, or Auto mode on its own: fast path, routine-command check or model; a setup program such as `sleep` no grant names counts too; builtins such as `cd` neither grant nor withhold) is checked again, by the same rules, against the environment its shell will run it in (login shell exports, the agent shell's exports, session variables; an empty or unset `PATH` counts): if that steers it, it does not run and says it needs your approval there. Nothing is remembered between commands, so each is checked on its own; a command you approved, or that a grant, allow rule, "allow all commands" or always-approve covers, is never stopped this way; to run it there, add an allow rule (such as `--allow 'Bash(ls *)'`) or remove the variable. Common setups trip the check (an editor terminal's `GIT_ASKPASS`, a stock Ubuntu `~/.bashrc`'s `LESSOPEN`/`LESSCLOSE`, `EDITOR='code --wait'`, Nix or CI `CC`/`CXX`); the prompt names the variable, and starting Fuigo without it (`env -u GIT_ASKPASS fuigo`, `unset LESSOPEN LESSCLOSE`) keeps the fast path. The ambient git check runs only an absolute `git` from a clean `PATH`, or an absolute `GIT_BIN_PATH` outside the project, that does not resolve into the project; if there is none, git commands ask. A repository `post-index-change` or `fsmonitor-watchman` hook (git runs `post-index-change` on `git status`; on Linux and macOS only an executable one) and `log.showSignature = true` make git commands ask; the hooks LFS, pre-commit or lefthook install do not make read-only commands ask, but a git command that is not a read-only query (`git commit`, `git checkout`, ...) in a repository with any hook of its own is not approved without a grant (Auto mode leaves it to the model, told about the hooks; in a trusted folder the model's allow stands; grants, allow rules, "allow all commands" and sandbox auto-allow still apply). Hook names match in any letter case and, on Windows, with any extension (`post-index-change.exe`), and a `.sample` file is no hook in any letter case (`pre-commit.SAMPLE`). A bash tool that runs its command in another folder (OpenCode bash `workdir`) gets every repository check in that folder too. In Auto mode the model decides commands the plain-text rule cannot read (an opaque or rich script, a routine build). In a trusted folder, content the repository controls (its git configuration or hooks, git in a repository Fuigo could not read, a command naming `git` that is not a git command Fuigo scans such as `env -C dir git status`, a configuration file a command loads from the project such as a repository `.ugrep`, `.npmrc` or `.cargo/config.toml`) is the folder's own, so the model's allow stands; only an environment that steers what runs makes a model allow of a command no grant covers ask you, and Fuigo's grep tool asks in Auto mode when `RG_BIN_PATH` or `RUNFILES_DIR` picks its program from the project. In a folder you have not trusted, no command runs without your approval or grant. On Windows, cmd.exe runs commands with `NoDefaultCurrentDirectoryInExePath` set, so it never takes a bare program name from the project folder.
- Granted paths: a shell's end of options before a stdin path (`bash -- /dev/stdin`) is a program from the pipe; a glob of wildcard-only parts that can match a process environment file (`/pr?c/????/???????`) counts as reading it; the glob check runs in bounded time, and a glob too long to check counts as a match.
- A dangerous-list command (`rm`, `kill`, `git push`, ...) now also asks under a session-wide grant and sandbox auto-allow; the Auto mode fast path already blocked it.
- A glob that starts with a wildcard (`cat *.md`, `ls *`, `wc -l *.rs`) now asks on every path, because a matching file named like an option would become one. A glob that starts with a literal (`cat ./*.md`) still runs under your broad grants, but like every glob it asks without one (plain-text rule).

### Windows: PowerShell and cmd.exe

When Fuigo runs commands in PowerShell (`pwsh` or `powershell.exe`) or cmd.exe, every shell command without a grant asks, read-only ones included, in Ask mode and in Auto mode: Fuigo's plain-text rule and read-only lists judge a command the way bash reads it, and those shells read the same text with other quoting, separators and redirects. Grants, allow rules (`--allow`), your answer at the prompt, "allow all commands" and always-approve still apply. To avoid the prompts, use grants or `--allow`, or run commands in Git Bash with `FUIGO_SHELL=bash`. A hub judges by its own host's shell, so a Unix hub's approval without a grant for a peer that runs PowerShell or cmd.exe is refused at that peer. Git Bash on Windows and every Unix shell are unchanged.

### The agent's shell between commands

- A function or alias named like a program Fuigo approves by name (`ls`, `cat`, `git`, `python3`, ...) no longer persists between the agent's shell commands, whether it came from your startup files or from an earlier command; Fuigo drops it before each command so the name runs the real program. Fuigo's own `grep` and `find` are the only replacements kept. Fuigo also drops functions named after the shell builtins its wrapper uses and the command-not-found hook, and in zsh global aliases, suffix aliases, `TRAP*` functions and the hook functions (`chpwd`, `precmd`, `zshexit`, ...); bash's `DEBUG`/`RETURN`/`ERR`/`EXIT` traps and `PROMPT_COMMAND` are cleared, and tracing and word-reading options (`xtrace`, `histexpand`, `keyword`, zsh `AUTO_CD`, `EQUALS`, `PROMPT_SUBST`) are reset. If such a name cannot be dropped (a `readonly` function, or a startup file that replaces zsh's `functions` hash), Fuigo refuses every agent command with `fuigo: refusing to run: …` until the startup file is changed and the session restarted.
- In Auto mode, routine build and test commands (`make`, `cargo test`, `npm test`, `pytest`, ...) run the repository's own build code without asking, as before; Ask mode never approves them without a grant from you.
- An approved command runs with your full authority, including changing the shell state later commands run in. Approve only what you would run yourself.

### Unchanged

- Ordinary plain read-only commands (`ls -la`, `git status`, `rg pattern`, `cat README.md`, `git log --oneline | head -5`) and ordinary tool use under a broad grant (`sed` substitutions, `awk '{print $1}'`, `kubectl get pods`, `ssh host uptime`, `python3 script.py`) run as before. Exact grants stay explicit overrides. The permissions and safety guide lists what stays un-floored under "Commands the classifier cannot vouch for".

## Session modes, agent files and the always-approve lock

- `session/set_mode` accepts only Fuigo's own mode ids: `default`, `plan`, `ask` and `browser_use` (case-sensitive). Any other id is now refused with `-32602` (`data.error_kind = "invalid_request"`) and the session is left as it was. Before, an unknown id was accepted and handed to agent lookup as an agent name, so a client could switch the session to another agent's instructions by naming it. Fuigo's own clients only ever send the four ids, so nothing changes for them.
- `session/new`, `session/load` and `session/resume` now advertise those four modes in `modes`, with `currentModeId` set to the mode the session is in now (`plan` while plan mode is on, `ask`, else `default`; `browser_use` is reported as `default`). Every accepted switch to `default`, `ask` or `browser_use` also sends a `current_mode_update`, including a switch to the mode the session is already in (for example `default` to `default`), which sent nothing before; clients that track the mode can treat a repeated `currentModeId` as a no-op. A switch to `plan` sends one when it turns plan mode on, and nothing when plan mode is already on.
- Agent files from a repository (`.fuigo/agents/`, `.claude/agents/`) load only in a folder you trust, like the repo's hooks, MCP servers and skills. In an untrusted folder they do not appear in `/agents` and cannot be reached through `FUIGO_AGENT`, `[agent] name`, a model's `agent_type`, the Task tool or a mode switch.
- No agent file replaces a built-in agent any more, in any scope. A project or user file whose file name or frontmatter `name` is a built-in agent name (`explore`, `plan`, `general-purpose`, `codex`, `fuigo-build` and the other built-ins) is ignored and no longer shows as a row in `/agents`. Before 1.0.35 a project file with a built-in name replaced that built-in; it no longer does. If you had such a file, for example a project `explore.md` with `name: explore`, rename both the file and its frontmatter `name` (for example `my-explore.md` with `name: my-explore`) and ask for it by the new name: a file keeps being ignored while either its file name or its `name` is a built-in name.
- An agent name must be a single plain name. A path, `..`, a `/` or `\` separator, a `:` (except the one in `plugin:agent`) or a drive prefix is refused everywhere a name is accepted: `_meta.agentProfile`, a model's `agent_type`, Task `subagent_type`, `FUIGO_AGENT` by name and `[agent] name`. Options that take an explicit file path (`--agent-profile`, `[agent] definition`, an absolute `FUIGO_AGENT`) are unchanged. `--agent <arg>` reads its argument as a file only when it looks like a path (it contains a separator or ends in `.md`, such as `./reviewer.md`); a plain name such as `--agent explore` is always an agent name, even when a file called `explore` sits in the current folder.
- Plugin agents are callable only from a plugin you trust. An enabled but untrusted plugin (for example a project plugin in `.fuigo/plugins/` you have not trusted) still lists its agents in `/agents`, but they are no longer offered to the Task tool and cannot be reached as a model's `agent_type` or by name, qualified (`plugin:agent`) or bare. Trust the plugin to use them. Its skills and commands no longer load either (no skill listing, no skill body), the same as a repository's own skills in an untrusted folder.
- Plugin and project skills, commands and agents load only from their own folder. A plugin `skills/`, `commands/` or `agents/` dir (default or manifest-declared), or any skill folder, `SKILL.md`, command or agent file in a plugin or under a project `.fuigo/`, `.agents/`, `.claude/` or `.cursor/` folder, that is a symlink resolving outside that plugin folder, or outside the folder that project config folder belongs to, is skipped, so neither can pull an arbitrary local file into the model's context; links that stay inside still load, and your own `~/.fuigo/` and `[skills] paths` still follow links. `/plugins` shows how many were skipped per plugin, and symlink loops are walked once.
- That folder is now checked again when each file is read, on the file actually opened, so a link swapped in after Fuigo found the file is refused too. The same holds for a project's `AGENTS.md`, `CLAUDE.md`, `AGENT.md` and `.fuigo`/`.claude`/`.cursor` `rules/` files (they must resolve inside the repository, or the folder you run in outside one), a project's `.fuigo/config.toml`, `.fuigo/sandbox.toml`, `.fuigo/lsp.json`, `.mcp.json`, `.cursor/mcp.json`, `.claude/settings.json` and hook files, a plugin's manifest and its hooks, MCP and LSP files (default ones included), and a plugin folder found in a repository, which must itself sit inside the repository. Your own files in `~/.fuigo`, `~/.claude` and `~/.cursor` still follow links, also when you run Fuigo in your home folder.
- The folder each of those files is held to is resolved once, when the plugin or project is found (or the session starts), and is never resolved again: replacing a whole plugin folder, or the repository, with a symlink after that does not move the boundary, and the reads are refused. On a Unix other than Linux and macOS, where Fuigo cannot ask where an opened file really is, project and plugin files are skipped instead of read unchecked. Beyond those checks (which refuse a link that is already in place when a file is read), containment is not a defence against a program racing Fuigo's reads while it runs, such as swapping a folder for a link between the check and the read: that takes running something on your machine, which the folder trust gate governs (in an untrusted folder every shell command asks first).
- The same containment now covers every remaining project file Fuigo reads on its own: every route that loads a project `.mcp.json` or `.cursor/mcp.json` (live MCP server assembly, the mid-session reload and its change detection, the folder-trust check, `/mcp` origins), project agent memory (`.fuigo/agent-memory/<agent>/MEMORY.md` and `agent-memory-local`), `.fuigo/tool-guidance.toml`, `.cursor/rules/` files added to file reads, `fuigo inspect` / `fuigo mcp remove` lookups of a project `.fuigo/config.toml`, project subagent roles and personas (`.fuigo/roles/`, `.fuigo/personas/`) and the `prompt_file` / `instructions_file` they name, project workflows (`.fuigo/workflows/*.rhai`), the workspace `.fuigo/repos.json`, a project `.github_repo` export mapping (never written through a link either), and hooks imported from a project `.claude/settings.json`. A project agent-memory folder that is a symlink, or sits under one (from `.fuigo` down), is not used as that agent's memory at all, wherever the link points. Your own `~/.cursor/mcp.json` still follows links.
- `[plugins].paths` in a repository's `.fuigo/config.toml` no longer counts as your own setting. Those entries load as project plugins: they must resolve inside the repository (relative entries are resolved against the folder holding `.fuigo/`), stay off until you enable them, and are never trusted automatically for sitting under your home folder. `[plugins].paths` in your own `~/.fuigo/config.toml` is unchanged.
- New: lock always-approve off for yourself with `[ui] disable_bypass_permissions_mode = true` in your own `config.toml` (`~/.fuigo/config.toml`). It works on every OS, survives console sync, and takes effect from the next session start for the session's own always-approve mode; the hub that authorizes tool calls reads the file on every call, so it applies a lock you add, and stops applying one you remove, from the next call. Only your own `config.toml` counts: a project `.fuigo/config.toml`, `FUIGO_CONFIG` and managed config cannot set or clear it. See [Permissions and safety](../crates/codegen/fuigo-pager/docs/user-guide/22-permissions-and-safety.md#disable-always-approve-for-yourself).

## Windows

- Shell commands no longer fail at random with "program not found". On Windows, variable names are not case-sensitive, but Fuigo built each command's environment as if they were. When the environment held both `Path` and `PATH`, which one the command received changed from run to run, and in about one session in three it was the wrong one. Fuigo now keeps one entry per variable: the first spelling in the environment, with the value Windows itself gives for that name. Names are compared the way Windows compares them, including non-ASCII letters (`ö` and `Ö` are one name).
- `[shell_environment_policy]` on Windows: a `set` now replaces every spelling of its name. `exclude` and `include_only` already matched any ASCII spelling; they now also match the non-ASCII spellings Windows treats as the same name, whether the non-ASCII letter is in the pattern or in the variable name. Credential variables are removed in every such spelling.
- Fuigo now starts the shell by its full path, found once at startup. `pwsh.exe` and Git Bash's `bash.exe` are looked up in the folders listed in `PATH`, never in the current folder, so a `pwsh.exe` inside a repository is not picked up. `powershell.exe` and `cmd.exe` come from the system folder Windows reports, not from the `SystemRoot` variable; `ComSpec` is used for `cmd.exe` only when it points inside the Windows folder. Before, Fuigo started a bare `pwsh`, `powershell.exe` or `cmd` and looked it up again on the command's `PATH` each time. The bare name is used only when no path can be found. The chosen path is logged at info level.
- When a shell cannot be started (the bash tool, the terminals, the interactive terminal, hooks and the status line), Fuigo logs a warning with the Windows error code, the program path and whether `PATH` was set for the command. Variable values are never logged.

## macOS and Linux

- `inherit = "core"` in `[shell_environment_policy]` now matches the core variable names exactly, as these systems do: a lower-case `path` or `home` is a different variable and is no longer kept.
